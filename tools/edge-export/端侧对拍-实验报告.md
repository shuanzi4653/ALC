## 2. 口径：先把"什么算一致"钉死

端云一致不是"看起来差不多"，而是以下四条**同时**成立：

1. **树遍历规则**：`forest.py` 是 `vector[idx] <= threshold` 走左、否则走右。
   等于阈值走左边，不许改成 `<`。端侧 `edge_infer.c::edge_leaf_of()` 逐字对应。
2. **叶子聚合**：每棵树先 `c/total`（`total = c0+c1`，`total <= 0` 则整棵树跳过），
   100 棵树累加；最后 `grand = Σtotals`（为 0 时取 1.0）再统一归一。
   运算顺序固定为"先类 0 后类 1"——浮点加法不满足结合律，换顺序就差几个 ulp。
3. **argmax 取首个最大值**：`probs[1] > probs[0]` 才判 POS，并列时判 NEG（与 Python `max()` 同解）。
4. **输入逐位相同**：端侧只有 float32，所以云端也必须吃 float32 量化后的同一组数（见 §5 坑 1）。

不参与 predict 的模型字段（`calibration`、`operatingThreshold`）单独处理，见 §6。

## 4. 用例是怎么来的（评委最容易追问的一节）

### 4.1 数据源

`data/training/national/dataset.json`：open-meteo hourly 抓下来的 **319 个城市 × 30 天逐小时观测**
（真实观测，公开、免密钥）。仓库里 METAR 的 `data/training/metar/series.csv` 被 `.gitignore` 排除、
本机不存在，所以**没有**用它。

### 4.2 特征构造不另写一套

逐条照 `backend-python/ml/nowcast.py::vector_for()`：六个派生量用"过去 6 个观测"、
缺失值填模型 `defaults` 并置 `miss_*`、`stationCode` 用三站真实经纬度做最近站映射
（150 km 内取 0/1/2，否则 -1，与 `STATION_CODE.get(station, -1.0)` 同解）。

脚本还与 `dataset.json` 里已有的同名列做了比对，**唯一差异在 `qnhTendency3h`**
（全国口径最大差 3.6 hPa，三站口径 2.3 hPa）：训练侧那一列是"3 小时变压"，
运行时 `vector_for` 用的是"1 小时变压"（`qnh - pq[0]`）。这是项目里**真实存在的训练/服务口径差**，
本实验按运行时口径复算（端侧将来拿到的就是运行时算的向量），差异如实登记在 §6。

### 4.3 分层抽样（为什么不是随机抽 1000 条）

随机抽会得到一个"几乎全是好天气"的样本，p 全贴在 0 附近——那对拍会显得完美，
但根本没压到判别边界。所以按当前能见度分层，固定随机种子 `20261113`：

| 能见度档 | 配额 | 候选行数 | 实际取 |
| --- | --- | --- | --- |
| `<1000 m` | 120 | 3599 | 120 |
| `1000-2999 m` | 180 | 8399 | 180 |
| `3000-5999 m` | 200 | 18820 | 200 |
| `6000-9999 m` | 200 | 27259 | 200 |
| `>=10000 m` | 300 | 167456 | 300 |

来源：`cases_meta.json` 的 `source.strata`。扫描 227447 行，可用 225533 行
（历史不足 6 个观测的行被跳过）。

站点构成（来源 `cases_meta.json` 的 `stationSampled`）：
用例 A 为 `OTHER=975 / ZYTX=16 / ZYCC=6 / ZYHB=3`，用例 B 为 `ZYTX=539 / ZYCC=270 / ZYHB=191`。
两组并存的原因：模型是**用三站训练**的，`stationCode=-1` 属于训练时没见过的取值，
所以三站口径（B）是"业务真实分布"的那一组，全国口径（A）是"特征空间覆盖更宽"的那一组，
两组都过才算稳。

## 5. 结果

### 5.1 主结果：概率一致性

| 指标 | 全国 A | 三站 B | 来源 |
| --- | --- | --- | --- |
| `max |Δp|` | 6.953e-07 | 5.727e-07 | `out/run-national.txt` / `out/run-metar3.txt` |
| `mean |Δp|` | 2.510e-07 | 2.436e-07 | 同上 |
| `rms |Δp|` | 2.919e-07 | 2.839e-07 | `out/parity-*-*.json` 的 `deltaRaw.rms` |
| `p50 |Δp|` | 2.538e-07 | 2.458e-07 | 同上 `deltaRaw.p50` |
| `p95 |Δp|` | 4.870e-07 | 4.857e-07 | 同上 `deltaRaw.p95` |
| 超差组数（`>1e-4`） | 0 / 1000 | 0 / 1000 | 同上 `deltaRaw.over` |
| 判决一致率（阈值 0.3） | 1000/1000 = 100% | 1000/1000 = 100% | 同上 `levelAgreement` |
| POS 组数（Python / 端侧） | 728 / 728 | 752 / 752 | 同上 |

偏差量级解释：6.953e-07 相当于 ~7 ulp（float32 在 0.5 附近的 ulp 约 6e-8），
全部来自"100 次 float32 累加 + 两次除法"的舍入，与 leaf 翻边无关——
leaf 翻边一次会带来 1e-3 ~ 1e-2 的跳变（见 §5.3 的实测），量级完全不同。

### 5.2 副结果：校准后概率与耗时

| 指标 | 全国 A | 三站 B | 来源 |
| --- | --- | --- | --- |
| 校准后 `max |Δp_cal|` | 1.634e-05 | 6.080e-06 | `out/parity-*-*.json` 的 `deltaCalibrated.max` |
| 校准后超差组数 | 0 | 0 | 同上 |
| 端侧耗时 p50 / 均值 / max（x86） | 4 / 3.9 / 12 us | 4 / 4.2 / 9 us | 同上 `timingEdgeUs` |
| Python 参考耗时（同一台 PC） | 152.4 us | 182.9 us | 同上 `timingPythonUs.mean` |
| 端侧耗时 p50 / 均值 / max（ESP32） | `<FILL>` | `<FILL>` | 期望：`pair_check.py --port COM7` 输出的"单次耗时（端侧）"，或串口 `# SUMMARY ... US_MEAN=` |
| 端侧耗时 p95（ESP32） | `<FILL>` | `<FILL>` | `out/parity-*-esp32.json` 的 `timingEdgeUs.p95` |

校准后仍有 1.6e-05：这是**校准表自身的阶跃**造成的，不是实现差异——
isotonic 的 `x[]` 里存在相邻相等点（例如 `0.209635, 0.209635`），区间跨度为 0，
raw 相差 1e-7 就可能落到阶跃的另一侧。所以主指标只看 raw p，cal 只作量级检查。

x86 的耗时**不是稳定常数**：同一台机器重复跑，均值在 3.0 ~ 4.5 us 之间波动（共享机器上别的进程会抢 CPU），
p50 稳定在 3 ~ 4 us。引用时写"3 ~ 5 us 量级"最稳；`CHECKSUM`（p 的累加和）在多次运行中恒定不变
（全国口径恒为 `557.520912`），说明**输出可复现、波动的只有耗时**。

x86 耗时的意义要讲清楚：它证明"每棵树大约 9 次比较 × 100 棵"的计算量在通用 CPU 上是 3 us 级；
ESP32 是 240 MHz 单核、无 x86 的乱序执行，实测会在 `<FILL>` 量级（预期几十到两百 us，
仍远小于 1 Hz 的观测更新节奏）。**这两个数不可互相替代，材料里各写各的。**

### 5.3 两个被实测抓到的坑（这段是本节最有价值的部分）

**坑 1：Python 侧读用例时没有量化到 float32，导致 40/1000 假失败**

`cases.csv` 里写的是 float32 的最短 round-trip 十进制串，例如 `9.4` 代表 float32 的
`9.3999996185`。`strtof("9.4")` 得到的是那个 float32，而 Python 的 `float("9.4")` 得到的是
float64 的 9.4——**两侧根本不是同一组输入**。首轮对拍结果：

```
超差组数 40 / 1000      max|Δp| 1.109e-02
```

修法：`pair_check.py::f32()` 在读入后统一量化；`gen_cases.py` 生成时就落 float32。
这不是"调容差"，是把输入对齐。修完后同一批用例 `max|Δp|` 掉到 6.953e-07。

**坑 2：阈值量化方向必须是"向下取整"，不是就近也不是向上**

`forest.py` 的判定两边都是 float64，端侧两边都是 float32。阈值怎么量化成 float32，
决定了"特征恰好等于阈值"这类输入会不会翻边。三种取法的实测（同一批 1000 组）：

| 阈值取法 | 超差组数 | `max |Δp|` |
| --- | --- | --- |
| 就近取整（round-nearest） | 2 / 1000 | 1.333e-03 |
| 向上取整（ceil） | 2 / 1000 | 1.333e-03 |
| **向下取整（floor，采用）** | **0 / 1000** | **0.000e+00** |

向下取整的正确性是可证的：设 `thrF` 是不大于 `thr` 的最大 float32，则对任意 float32 的 `x`，
`x <= thrF` 与 `x <= thr` 等价——因为区间 `(thrF, thr]` 里没有任何 float32 可取。
采用后，**float64 遍历在 1000 组真实用例上与 `forest.py` 完全相等（差 0.000e+00）**，
剩下的 6.953e-07 纯粹是 float32 累加误差。

实测反例（用来解释为什么向上取整会错）：`thr = 8497.300048828125`，相邻两个 float32 是
`8497.2998` 与 `8497.3008`。取上界的 `8497.3008` 时，输入 `x = 8497.3008` 本该走右子树
（`x > thr`）却走了左子树，`Δp = 8.4e-02`。取下界 `8497.2998` 则判定正确。

> 复现这两条数字：见 §8 的"阈值方向对照实验"片段。

## 6. 与模型字段/参考实现不一致的地方（必须同时报，不许藏）

| 项 | 情况 | 处理 |
| --- | --- | --- |
| `calibration`（isotonic，92 点） | `forest.py::predict()` **不**使用校准表；`nowcast.py::probability()` 才用 `_interp()` 校准 | 端侧 `edge_predict()` 输出**未校准**原始概率，与 `forest.py` 对齐；另提供 `edge_calibrate()`（语义等于 `nowcast._interp`），单独对拍（§5.2） |
| `operatingThreshold = 0.3` | 模型字段，`forest.py` 不用它做判决 | 端侧只导出为常量，判决仍由上层做；对拍里用它算"判决一致率" |
| `qnhTendency3h` 口径 | 训练集该列 = `qnh - qnh(t-3)`；运行时 `vector_for` = `qnh - qnh(t-1)` | 本实验按**运行时**口径复算（端侧将来吃的是运行时向量），差异量已登记在 §4.2 |
| `stationCode = -1` | 模型训练只见过 0/1/2；全国口径 975 组用例取 -1 | 两组用例并存（A 全国 / B 三站），B 组 1000 组全部落在 0/1/2 内 |
| `trainStats` 为空 | 模型 JSON 里 `trainStats = {}`（`top_factors()` 因此拿不到 z 分数） | 端侧不依赖它；`edge_infer.c` 只用 trees/classes/threshold/leaf |
| `featureImportance` 全 0 的 `miss_*` | 四个 `miss_*` 重要度都是 0 | 仍按 26 维导出，不裁剪：裁了维就与云端特征顺序不一致 |

另有一条**导出侧**的工程约束：叶子上的两个数本模型加起来是 1，理论上可以只存一个数、
另一个用 `1-p` 反推，flash 能省一半。**没有这么做**——`forest.py` 真的做了 `c/total` 和
`t/grand` 两次除法，少存一个数就要多一次减法，端云会在最后几个 ulp 上分叉，
"逐字等价"这句话就不成立了。省 96 KiB 换一个说不清的偏差，不划算。

import export_forest as E
