## 1. 本次核查发现

### 1.1 已确认的问题及影响

| 核查项 | 当前事实 | 更新结论 |
| --- | --- | --- |
| 城市端点 | `backend-python/traffic/service.py` 为飞行汽车端点统一叠加 `(-2000, -1800)` 米偏移，距离城市参考点约 2690.72 米 | 不是简单的视觉偏差，应移除统一偏移，建立城市中心与起降设施的明确关系 |
| 城市目录 | `traffic/catalog.py` 使用硬编码坐标；点不在省内时会自动吸附到边界内侧 | 不应悄悄修改城市位置；改为带来源的坐标目录，异常进入质量检查 |
| 放行时间 | `TrafficWorkbench.vue` 将 `departureMinute` 标成“实际放行”，只要有航迹就展示，未来班次也会出现该值 | 该值实际上是算法计算的计划时隙；必须拆分需求时间、计划放行、实际事件和预计到达 |
| 时间显示 | `clock()` 只有 `T+HH:MM`，向下取整，不含日期、时区、秒和稳定的绝对时间基准 | 增加统一时钟及空值保护，解决跨日、回放和延误展示问题 |
| 三维高度 | 全域视角默认高度放大 60 倍，城市视角为 1 倍；建筑与航迹未使用同一放大规则 | 存在明显的视觉比例误导，先恢复一致的真实比例 |
| 高度分配 | 配送无人机基准高度为 90/170 米，冲突抬升及交叉点抬升可以叠加 | 需要机型高度上限和空域层分配，不能持续累加高度解决冲突 |
| 空间检查 | 已有连续四维冲突检查、速度检查、气象包络和边界检查；但没有真实地形、建筑净空和转弯动力学检查 | 保留已有有效检查，补齐约束，不将“已有四维检查”误写成“完全没有避碰” |
| 路线绘制 | 普通路线主要使用 `THREE.LineBasicMaterial`；选中路线另加不同尺度的圆柱 | 改为稳定屏幕像素宽度，避免只选中时粗、缩放后粗细失真 |
| 参考走廊 | 无可用班次时仍可能显示固定高度的基准路线，缺少起降段 | 与可执行航迹明确区分，不能把未校验走廊画成正常航班路径 |
| 行政边界 | 网络返回三省合并后的范围，丢失内部省界；底图通用边界依赖缩放级别且对比弱 | 独立输出并绘制省际边界和三省外轮廓 |
| 气象风险区 | 禁飞、谨慎区共用低不透明度立体填充，缺少独立醒目边线；前端风险柱高度与后端二维绕避语义不一致 | 分开边界和填充控制，统一规划与显示的高度范围 |
| 气象真实性 | 当前交通气象是种子生成的移动天气单体及合成风场 | 增加公开天气驱动模式，保留可复现模拟模式，并明确标注来源 |
| 既有和风接口 | Java 中已有 JWT、current/hourly 请求，但使用固定经纬度；雷暴值包含基于天气代码或降水概率的估算 | 扩展坐标输入；未经校验的估算不能作为实时雷暴概率展示 |
| 外卖业务 | 每城固定 4 个偏移节点、3 条配送走廊，空间结构高度相似 | 改为城区节点、订单、载具及起降资源共同驱动 |

本次只运行了针对现状的只读诊断，没有重新执行全套测试，也没有重新启动浏览器复现全部视觉问题。对用户反馈的具体“危险路径”，实施第一步应记录班次 ID、时刻和视角，再形成回归样例；不能仅凭投影交叉就判定两架飞行器实际碰撞。

## 3. 时间与调度状态：先修正字段，再改台账

### 3.1 统一时间合同

计划创建时固定 `baseTime`，以带时区的 ISO 8601 UTC 时间保存；界面统一显示北京时间 `Asia/Shanghai`。相对分钟只用于算法内部与推演轴，不再作为唯一时间展示。

| 字段 | 含义与展示规则 |
| --- | --- |
| `requestedDepartureAt` | 订单或运行计划最初希望起飞的时间，对应现有 `scheduledMinute` |
| `plannedReleaseAt` | 当前版本排程允许放行的时隙，对应现有 `departureMinute`；未分配时为空 |
| `actualReleaseAt` | 推演执行中实际签发放行事件的时间，未来事件不提前显示 |
| `actualTakeoffAt` | 实际进入起飞阶段的推演事件时间，与放行可以不同 |
| `estimatedArrivalAt` | 以当前有效航迹计算的预计到达时间 |
| `actualArrivalAt` | 执行到达事件产生的时间，未发生时为空 |
| `planRevision` | 班次属于哪个排程版本，用于防止旧界面操作新计划 |

详情主字段改为“申请起飞 / 计划放行 / 实际放行 / 预计到达”；实际起飞、实际到达可在进程单展开区查看。主界面使用 `09-14 18:30:00`，辅以 `T+00:05:00`；不把空值渲染成 `00:00` 或 `NaN`。

显示到秒时统一舍入规则，不能各组件分别取整。跨零点显示新日期；在 `baseTime` 固定的情况下刷新、恢复会话和回放都不能改变计划时刻。

### 3.2 状态与操作规则

1. 将排程结果与运行阶段分离：排程为 `ACCEPTED / HELD / CLOSED / MANUAL_SUSPEND`，运行阶段为待准备、待放行、起飞、爬升、巡航、下降、到达。
2. 模拟执行事件由推演时钟和操作日志共同驱动。回看过去时只展示该时刻之前的事件，不能泄露未来的“实际时间”。
3. 人工暂停保留原时隙和原航迹供追溯，通过运行状态禁止执行，不再清空全部点后丢失解释信息。
4. 恢复时重新检查原时隙、天气快照、枢纽容量和冲突是否仍有效；原条件失效则进入重排，不能直接放行。
5. 指令提交 `flightId + planRevision + commandId`。重复指令幂等，版本过期返回 409 和明确原因。
6. 已起飞班次重规划从当前实际位置、速度和高度连续接续，不能重置到始发点，也不能突然改变高度。

## 4. 城市中心、行政边界与底图对齐

### 4.1 建立可追溯的 36 城目录

新建 `backend-python/data/traffic/city-centers.json`，每城记录 `cityId`、省份、名称、中心类型、WGS84 经纬度、来源链接、核验日期、质量状态。后端规划和前端标记只使用该目录。

- “城市中心”按城区代表中心选点，不用整个行政区域的几何质心替代城区中心。每个点记录选点依据；与主流底图城区、道路和地名核对。
- 删除所有城际端点统一向西南偏移的逻辑；禁止边界校验失败后自动吸附、悄悄更改城市坐标。
- 重点核查大兴安岭地区参考点：当前坐标靠近塔河，不能直接当作加格达奇的行政驻地。城市服务中心与三省运行边界存在特殊关系时，显式记录并选定合规的服务枢纽，不能靠移动省界或修改坐标掩盖问题。
- 延边等自治州采用明确的州府城区代表点，名称、行政层级和选点类型同时保留。
- 统一 WGS84 → 本地米制规划坐标 → 地图坐标的转换链；来源若为其他坐标系，单独转换一次并留痕，禁止重复偏移。

### 4.2 中心锚点与起降点的关系

城市中心作为用户看到的城际网络基准点。以它建立“城市中心枢纽”，起降设施另设 `padId`、坐标、地面/屋顶高程、容量和可用状态。

若中心点具备已核验的模拟起降条件，使用同一点；否则在中心附近选择可验证的起降位置，并显示中心到起降点的地面接驳关系。**不把落在建筑内部的城市中心强行当成地面起飞点。** 详情中明确“城市中心 / 实际起降点”，偏移必须有原因和距离，不再统一硬编码。

所有班次的首末点必须精确连接其实际起降点；进离场段参与净空、枢纽容量和四维冲突检查。多个城市航线共用中心枢纽时，必须排队占用起降资源。

### 4.3 边界图层

1. 后端保留三省独立多边形，以同一数据源计算内部省界与外轮廓；只给前端简化显示副本，规划仍用原始校验几何。
2. 内部省界共线去重，三省外轮廓整体加粗。东北范围外增加低亮度遮罩，不遮盖必要的相邻省份地名。
3. 初始样式：外轮廓 3.5–4.5 CSS px、内部省界 2–2.5 px、深色描边衬底 1–2 px；随缩放适度变化。
4. 避免与蓝色汽车路线、橙色无人机路线混色，省界使用偏白的浅紫灰。城市内部视角仍可查询所属省份，但不让边线遮挡建筑和起降点。
5. 保留原有地图来源署名。行政边界来源、日期及三省范围与算法边界必须一致。

## 5. 三维航迹：高度有依据，转弯和交叉都要复核

### 5.1 高度合同与显示

统一定义：`groundElevationMSL` 为地面高程，`altitudeMSL` 为飞行高程，`altitudeAGL = altitudeMSL - groundElevationMSL` 为距当地地面的高度；建筑顶高由地面高程与建筑高度共同计算。转换时记录数据的垂直基准，不能混用海拔、椭球高与相对高度。

规划、碰撞检查、地图和高度剖面使用同一份轨迹数据。界面默认展示“距地高度”，详情同时展示海拔高度和数据质量。起点高度来自起降平台，不能一律取零。

- 移除默认全域 60 倍高度放大，默认使用真实比例。
- 全域看不清升降时使用选中航班剖面、局部视窗和高度标签，不靠夸大垂直比例解决。
- 如保留 3 倍展示选项，必须明显标记，并让建筑、地形相对高度、天气体和航迹采用同一展示变换；禁止在放大视图中判断净空通过与否。

### 5.2 飞行性能与分层策略

新增 `aircraft-profiles.json`。以下为首轮调参起点，**属于本项目模拟运行策略，不是现实空域许可或已验证的机型能力**；实施时根据测试调整，并保持配置与界面说明一致。

| 项目 | 配送无人机 | 飞行汽车 |
| --- | --- | --- |
| 常规巡航层起点 | 80 / 160 米 AGL，按方向和走廊分配 | 350 / 500 米 AGL，按方向和走廊分配 |
| 首轮巡航上限 | 200 米 AGL | 600 米 AGL |
| 起降段 | 可低于巡航下界，但必须位于经过检查的进离场空间内 | 同左 |
| 冲突处理 | 优先分侧、预约交叉时隙和地面等待；有余量时使用已分配高度层 | 同左 |
| 无可用层时 | 延后、重新选路或关闭，不能继续叠加 100 米 | 同左 |

保留现有 250 米水平、60 米垂直间隔作为初始模拟检查参数；它们也不是现实监管标准。城市订单增多时先靠资源与时隙调度缓解拥堵，不为了提高吞吐量直接缩小间隔。

另行配置水平速度、爬升/下降速度、加速度、减速度、转弯半径与动力学参数。初期保留现有最大升降速率作为上界，再增加连续性检查。机型数据未经核验时展示“模拟性能参数”。

### 5.3 规划流程

按以下顺序执行一次完整排程：

1. 获取城市/起降点、地形建筑、天气快照、载具能力和运行规则版本。
2. 生成省内或允许的省会跨省走廊；城区配送裁剪到选定城市服务范围。
3. 按航迹有效时段构建天气风险包络，绕开禁飞区及本项目要求绕开的谨慎区。
4. 对候选水平路径处理转弯：使用带曲率约束的连接段，必要时降低转弯速度；不能在短距离内瞬时转向。
5. 生成进离场、爬升、巡航、交汇、下降剖面，检查地形与建筑净空及高度上下限。
6. 预约起降点、交叉区与窄走廊的时间资源；冲突时尝试错时或其他可行路径。
7. 对最终路径重新执行连续四维冲突、天气、边界、净空和动力学检查。平滑后的路径同样要检查，不能只检查平滑前折线。
8. 计算到达、等待及绕行增时。沿用“绕行增时超过 60 分钟关闭”规则；等待时间单独记录，并保留明确的最大等待约束，不能靠无限排队掩盖关闭条件。
9. 写入通过证据或拒绝原因，最后发布新的计划版本。

如果曲线离散成折线用于现有连续检查，须限定最大几何误差，并把误差加入安全缓冲。前端只绘制最终经过校验的线，不能自己平滑出一条偏离后端的曲线。

### 5.4 地形、建筑和缺失数据

城市底图建筑能被显示，不等于已经进入后端避障。目前 V1.2 的历史瓦片核查中，36 城中心瓦片有 33 城包含建筑；这不是全城区建筑完整率。

- 建立后端可复用的 DEM 与建筑数据适配层，按照起降点和航路缓冲范围读取、缓存和版本化，而非只读取当前屏幕内对象。
- 第一阶段先覆盖全部起降点和有效航路，并生成覆盖率报告；随后扩展城市服务区。显示与规划尽量采用相同版本和高度基准。
- 无建筑高度、无 DEM、数据过期、来源许可不明确分别记录质量状态，不把未知区域默认视为无障碍的零高地面。
- 数据不足时允许查看模拟结果，但状态应是“条件未验证”，不能显示为“已通过真实地形净空检查”。现实天气模式与模拟净空假设也要分别标明。
- 演示用公共 DEM 示例服务不能直接视作生产数据源。实际接入前核验区域覆盖、许可、分辨率、服务稳定性和高程基准。

技术路线仍可沿用 MapLibre 的 DEM 地形能力与现有 Three.js 自定义层，无需为实现立体地图全面更换框架。参考 [MapLibre RasterDEMTileSource 官方文档](https://maplibre.org/maplibre-gl-js/docs/API/classes/RasterDEMTileSource/)。

Open-Meteo 官方说明当前条件基于天气模型；东北地区不能因为接口返回 15 分钟时间步就宣称拥有原生 15 分钟观测。全球模型的网格尺度也不能支持街区级雷暴中心精确定位。例如其 ECMWF IFS 产品当前文档标注约 9 公里网格，具体使用哪个模型应在快照中记录。参考 [通用接口说明](https://open-meteo.com/en/docs)、[ECMWF 接口说明](https://open-meteo.com/en/docs/ecmwf-api)。

Open-Meteo 免费服务适用于其条款允许的非商业用途，有调用限额且不保证 SLA；多地点和多变量会影响计量，不能按一次 HTTP 请求等于一次额度估算。实施前根据用途与预计调用量核对 [服务价格和使用限制](https://open-meteo.com/en/pricing)，保留数据署名；本轮不代开付费服务。

和风资料参考 [当前天气](https://dev.qweather.com/docs/api/weather/weather-current/)、[分钟级降水](https://dev.qweather.com/docs/api/minutely/minutely-precipitation/)、[天气预警](https://dev.qweather.com/docs/api/warning/)。现有 Java current/hourly 客户端已使用 `/weather/v1/` 路径，扩展时按相应产品版本处理，不能统一改成旧版路径。

机场数据能力参考 [Aviation Weather Center 官方 API](https://aviationweather.gov/data/api/)。国内数据权限不能凭公开页面推断，风云数据门户也有注册及身份要求，见 [国家卫星气象中心数据门户说明](https://data.nsmc.org.cn/DataPortal/cn/support/faq.html)。

### 6.3 统一气象快照，防止两套天气相互矛盾

Python 作为交通气象快照和派生风险的唯一归一化入口：

1. Open-Meteo 适配器直接访问公开接口；和风适配器调用 Java 内部原始天气读取接口，由现有 Java JWT 服务处理凭据。
2. Java 内部原始天气接口只访问和风，不再回调 Python，避免循环请求；面向前端的统一天气状态由 Python 快照返回。
3. 原始响应、标准单位和质量检查分别保存。Java 原有雷暴估算字段不直接注入新风险引擎。
4. 地图、城市天气、放行规则、台账和智能体读取同一个 `weatherSnapshotId`，不各取一套时间不同的数据。
5. 交通计划缓存键加入天气快照、城市目录、地形建筑、机型参数、规则版本和 `baseTime`，旧缓存不冒充新计划。

快照至少包括：`provider`、`dataType`、`requestedLocation`、`gridLocation`、`retrievedAt`、`validAt`、`validUntil`、`modelRunAt`、`resolution`、`units`、`coverage`、`qualityFlags`。接口不提供模型起报时间时，`modelRunAt` 为未知，不能拿下载时间冒充。

请求设置超时、有限重试、退避、缓存和日额度预算。36 城每 15 分钟更新已有 3456 个“地点请求”每天，尚未计变量权重及航路网格，必须先算账。城市当前天气可每 15 分钟刷新；航路预报按模型更新节奏与缓存有效性复用，按活动航路增量采样，避免地图拖动触发无限 API 请求。

### 6.4 模式、覆盖和过期处理

- **现实天气驱动**：使用最新可用估算、观测和预报；交通仍为模拟。主界面明确“交通模拟 · 公开天气驱动”。
- **天气快照回放**：使用已保存快照及原时间基准，天气与班次共同回放。
- **可复现合成天气**：保留原种子场景，用于压力测试和没有网络时的功能演练。

模式切换显式显示并生成新的计划版本。网络失败时保留最后一次快照、显示数据年龄；不静默替换为随机天气。根据来源的有效期、发布时间与更新周期判断过期，不能简单把每 15 分钟输出理解为模型每 15 分钟更新。

城市天气有数据不等于城际航路全程有数据。只对具备时空覆盖的航路给出相应天气校验结论；缺测、过期或超过预报时域的部分标为未知。新增放行进入等待或关闭，已飞行班次按已验证的备选路径和资源重新评估，不能直接删除轨迹或凭空生成安全盘旋点。

### 6.5 不规则天气场与独立飞行限制

1. 使用预报网格随时间形成风、降水等连续场；按阈值和连通区域提取多处不规则天气范围，并保存阈值与分辨率。
2. 风按矢量分量插值，再恢复速度与方向，避免 359° 与 1° 被平均成 180°。密集风标记采用视口分级采样，避让地名。
3. 天气单体的移动依据相邻有效时刻的场和风向估计；没有细尺度资料时显示粗分辨率范围及不确定性，不制造精确到街区的雷暴轨迹。
4. 雷暴缺少专门观测/预报时显示“雷暴数据不可用”；禁止用降水概率乘一个固定系数后命名为雷暴概率。合成场景则继续明确标为模拟雷暴。
5. 飞行限制由机型阈值、阵风/降水/能见度、提前量、移动趋势和缓冲生成，不再为每个天气单体固定生成同一种禁飞圈。
6. 天气物理范围与禁飞/谨慎范围分别建模，可部分重叠，但不能仅为了视觉错开而任意平移限制区域；差异必须来自风险规则和预测缓冲。
7. 统一风险区 `floor/ceiling` 和有效时段。现有规则要求两类限制都水平绕避，因此本轮默认覆盖全部项目运行高度，不显示一个看似可以从上方跨过的低矮风险柱。
8. 界面使用“系统气象禁飞 / 系统谨慎区”等明确标签；真实气象预警保留发布机构，不能把算法派生结果冒充官方空域管制命令。

采用支持屏幕像素线宽的 `Line2 / LineMaterial` 或同等实现，普通汽车路线初始 4 px、配送 2.5 px，选中额外加 1.5–2 px 和浅色外描边。按当前视口和 DPR 正确维护材质尺寸，避免专注、折叠侧栏及浏览器缩放后错位。参考 [Three.js LineMaterial 官方说明](https://threejs.org/docs/pages/LineMaterial.html)。

- 汽车与配送使用不同颜色、线型和端点符号，不仅靠粗细区分。
- 已飞过路径适度变暗，未来有效路径保持清晰，关闭路径显示关闭状态而非正常飞行效果。
- 普通参考走廊默认关闭或以明确虚线显示，提示“走廊参考，非可执行航迹”。
- 全域优先显示汽车及所选配送；城区显示本城配送密度，避免 36 城所有短路线堆成亮块。
- 地形与建筑遮挡保持正确；需要透视时提供明确开关，不能靠永远关闭深度测试让危险穿楼看起来正常。

| 雷暴物理范围 | 紫色 | 0.12–0.20 | 独立图例与数据来源 |

立体风险区顶面与侧面分别控制透明度，避免叠加成不透明墙。调节器使用“填充不透明度”明确名称，统一控制 2D/3D；最终数值以道路、航迹、地名三者均清晰为准。

## 8. 空管式调度台账与城区配送

### 8.1 电子进程单

默认按待放行、运行中、受限/异常、已完成分组，支持城市、交通类型、时间窗、状态与原因筛选。每张进程单展示：

| 区域 | 内容 |
| --- | --- |
| 标识 | 可读呼号、载具 ID、班次 ID、汽车/配送类型 |
| 路由 | 出发中心与起降点、目的中心与起降点、当前走廊 |
| 时间 | 申请起飞、计划放行、实际放行、预计到达、延误 |
| 空间 | 当前距地高度、海拔高度、目标高度层、升降状态、地速 |
| 约束 | 起降点占用、冲突班次、天气区域、数据质量、关闭原因 |
| 操作 | 定位、跟随、暂停、申请恢复/重排、查看证据和记录 |

地图选中与进程单双向联动。当前放行队列默认关注未来 30 分钟，可切换 60 分钟或全部；完整台账使用分页或虚拟列表，不能一次渲染数千张卡片。

“管制效果”由真实的排队、时隙占用、状态变化和原因解释形成，不只是更换配色。被建筑、天气、容量或冲突关闭的班次不能通过拖动进程单绕过校验。

### 8.2 起降和交叉资源

新增城市枢纽、商家起降点、收货点、交叉区的占用日历。汽车和配送进离场即便巡航层分离，也要检查低高度段与共用资源。地面等待优先于临时悬停；空中等待必须有经校验的空间、持续时间和能量余量。

### 8.3 配送从固定短线升级为订单运行

每城首轮目标 8–16 个可配置业务节点，由城市实际道路、街区范围辅助布点；订单仍合成，商家和收货点名称不冒充真实营业商户。无可靠城区边界时明确标注“模拟服务区”，不把任意圆形称为官方城区范围。

订单状态为“待备货 → 待分配 → 待起飞 → 配送中 → 已送达”，异常另有等待、取消、失败；无人机独立维护可用、装载、飞行、返航、充电、停用状态。订单与载具不能混用一个状态字段。

- 按午晚高峰、节点类型与城市规模配置订单到达率，固定种子可复现，同城布局也不再复制其他城市。
- 城区服务范围使用经核验的多边形；可配置 3/6 公里服务半径用于模拟，但与省界、可用空域取交集。
- 检查返航/下一任务、载重、预计剩余电量、装卸和充电时间；能耗为模型估计，保存参数与余量，不冒充实测续航。
- 天气变化先更新未起飞任务；对在途订单从当前状态重新规划，订单 ETA、进程单和地图同步。
- 展示送达率、超时率、平均等待、起降点利用率、关闭原因分布及数据质量影响，避免只显示总架次。
