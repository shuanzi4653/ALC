## 2. 与 HongSight 部署的关键差异

| 项 | hongsight | **本项目** | 影响 |
|---|---|---|---|
| 域名 | `shuanzi.site` / `www` / `hongsight.shuanzi.site` | **`tianchuang.shuanzi.site`** | 域名上线后两边做法已趋同：都是 80→301 + 443 终结 TLS |
| 公网入口 | `:443`（`:80` 是 `default_server` 兜底） | **`:443`** | `:80` 的 `default_server` **仍归 hongsight**；本项目连 IP 直连出口都没有了（内层只听回环） |
| 443 层反代写法 | `include snippets/hongsight-api.conf`（直连 28080） | `proxy_pass 127.0.0.1:28081`（**双层**：再经本项目的内层站点块） | 多一跳 ⇒ 多一处必须写对的地方：**WebSocket 的 Upgrade/Connection 要透传两层**，见 §7.5 |
| 鉴权 | 无（`/api/` 供鸿蒙客户端直连） | **表单登录 + 会话 Cookie**（内层） | 本项目的 API 有能改写状态的写端点，必须挡 |
| 数据库 | MySQL 8（独立进程） | **H2 嵌入式文件库** | 无独立 DB 进程、不占端口、无 `--with-db`；备份是**文件打包**而非 `mysqldump` |
| 进程数 | 1（Spring Boot） | **2（Java + Python）** | 需要**两个** systemd 单元；Python 由 Java 内部调用 |

> ⚠️ **为什么本项目要在 443 后面再套一层自己的 28081，而不是像 hongsight 那样在 443 块里一次写完？**
> 因为 `sites-available/domains` 是**三个项目共用**的文件 —— 把本项目的鉴权、gzip、
> WebSocket 细节全塞进去，等于让邻居的配置文件承担我们的复杂度。现在的分工是：
> `domains` 只负责「认域名 + 终结 TLS + 原样转发」，本项目的一切业务规则都留在自己的
> `sites-available/AIC-tianchuang` 里。代价就是多一跳，以及 §7.5 那个坑。

> 前端不需要 Node 运行时：`scripts/build.ps1` 把 Vite 产物写进
> `backend-java/target/generated-resources/static` 并**打进 JAR**，云端只跑 JAR。

| **28082** | Java 主服务（Spring Boot，Nginx upstream） | `127.0.0.1` | ❌ 仅回环 |
| **28083** | Python 智能服务（FastAPI，只被 Java 调用） | `127.0.0.1` | ❌ 仅回环 |

> **为什么还要保留 28081 这一层**：见 §2 末尾。`domains` 是三个项目共用的文件，
> 把本项目的鉴权 / gzip / WebSocket 细节全塞进去等于让邻居的配置承担我们的复杂度。
> 现在的分工是「`domains` 认域名 + 终结 TLS + 原样转发」/「本项目站点块管自己的业务规则」。
> **28081 现在只监听回环**（`listen 127.0.0.1:28081`），`0.0.0.0:28081` 已取消。
>
> **为什么必须是三个不同端口**：Nginx 与 Java 不能绑同一端口
> （`0.0.0.0:28081` 与 `127.0.0.1:28081` 会 `EADDRINUSE`）；Python 是独立进程，也需独立端口。
> **公网面上只剩 `22 / 80 / 443` 三条。**

### 4.0 一次发版到底做了什么（2026-10-27 起固化）

```bash
# 1) 先在本地打包（顺序是硬判据：所有编辑之后、跑包↔仓库逐字节对照）
powershell -File .run/build_manual.ps1          # maven clean → vite → build-info → package → 静态自检

# 2) 看一眼计划（不上传任何东西）
python tools/deploy/_deploy_release.py --dry-run --py backend-python/traffic/v2.py

# 3) 真发：快照 → 上传并逐个比 md5 → deploy-remote.sh → 重启 Python → 22 项自检
python tools/deploy/_deploy_release.py --py backend-python/traffic/v2.py
```

四条口径：

1. **`--py` 是显式清单，不靠 mtime 猜。** 时钟与拷贝都会骗人；不确定就不发 Python 侧，
   脚本会在结尾把"这次只发了 jar"说出来。
2. **每一步都先比 md5 再往下走。** 上传 63 MB 的包"看起来成功了"是常事
   （沙箱里 `scp` 曾被代理拦成半截），不比对就等于把混版产物推上线。
3. **`VERSION` 必须跟 Python 文件一起走。** Python 侧读项目根那份，漏传就是
   `FileNotFoundError` 反复重启（0.9.x 真出现过），而界面上只表现为"服务一直起不来"。
4. **收尾自检不绿就不算上线。** `_verify_release.py` 的 22 项是互相咬合的：
   光换 jar（版本号对了）而前端 chunk 没换、或前端换了而 Python 没重启（接口口径还是旧的），
   都会被某一项抓住。退出码 1 时**不要**对外宣布已上线。

补一条**负向自检**（这份脚本存在的前提）：喂一个名字不匹配的包或一个不存在的 py，
必须当场拒绝并且退出码为 1 —— 已实测：

```
FATAL: jar 名 README.md 与 VERSION 0.11.27-beta 不一致 —— 先重新打包，别上传混版产物   (exit 1)
FATAL: 找不到 …/traffic/nope.py                                                      (exit 1)
```

### 4.1 应用配置是怎么被覆盖的（零代码改动）

Spring Boot 的属性优先级是 **环境变量 > 外部 `config/application.yml`**，所以 `.env` 直接盖住配置：

| 配置项 | 外部 yml 的值 | 云端 `.env` 覆盖 |

1. **`.env` 与 `.env.secrets` 分工**：`.env` 装平台配置（端口、时区），由 `install-remote.sh` 从仓库模板**整体覆盖**；`.env.secrets` 装机密，脚本**只保证它存在且是 600，从不读写内容**（「存在即保留」，否则重装会把机密清成空）。两个 systemd 单元都用 `EnvironmentFile=-` 读它，`-` 表示缺失也能启动并干净降级。

> 环境变量本身也不比 600 文件更安全（同用户可经 `/proc/<pid>/environ` 读到）。

### 6.3 口令的分发与「不保存」纪律（2026-10-13 追加 · **2026-10-14 整体作废**）

实测形状：`-rw------- root:root`、**25 字节** = `aic:`(4) + 20 位口令 + 换行。
`/etc/nginx/.htpasswd-AIC-tianchuang` 里**只有 apr1 哈希，看不到口令**，所以只能读上面那个文件。

> **取回后**：私下告知使用者即可；**不要**写进仓库、交付包、聊天收藏或密码管理器
> （同一条"不保存"纪律）。忘了不用慌 —— 服务器上那份随时能再读，实在不行
> 按 §9 的重置片段换一个新的。

**收件人侧要求：口令不许被保存。** 落实手段是启动器默认用**隐私窗口**打开
（`TianChuang/launcher.ps1`，Edge `--inprivate` / Chrome `--incognito` /
Firefox `-private-window`）：

| | 效果 |
|---|---|
| 隐私窗口 | 默认**不提供**"保存密码"；关窗后本次凭据即失效 |
| 启动器文案 | 明确写「**请不要保存这个口令**」，并提示不要勾选"记住 / 保存密码" |
| 代价 | **每次使用都要重新输入一次口令** —— 已明确接受 |

**边界（别写成"已禁止"）**：以上能让口令**不被浏览器留存**，但拦不住一个
**刻意**把口令抄下来的人。所以所有文案一律写「请不要保存」，**不写「已禁止保存」**
—— 后者是一句写在屏幕上的假话。见 `notes/2026-10-13-launcher-and-credential-boundary.md` §二。

### 6.4 每日配额（2026-10-14 晚上线 · 0.9.30（Beta））

拆掉会话门之后，`POST /api/agent/ask`（烧 DeepSeek 额度）与 `POST /api/monitor/run-now`
（改写全机状态）对公网任何人开放。`limit_req` 挡的是**频率**（20 r/m/源 IP），
挡不住**总量** —— 每 3 秒一次、连着发一天，照样把额度烧穿。

| 维度 | 上限 | 为什么是这个数 |
|---|---|---|
| 工作区 | **120 次/天** | 够一个演示者把每个点都点几遍，不够把额度烧穿 |
| 出口 IP | **600 次/天** | 兜底。工作区标识由前端生成、存在客户端，**换一个字符串就是一格新配额**，所以只按工作区计数等于把上限交给调用方决定；反过来 IP 也不能卡太紧，同一 NAT／校园网里可能有多个真实用户，600 ≈ 5 个工作区的量 |

- 覆盖端点：`/api/agent/ask`、`/api/traffic/explain`、`/api/monitor/run-now`。
  **`/api/traffic/session` 等轮询读接口不在内** —— 构建期每 2–3 秒一次，并进来会让
  "页面自己把自己用光"，症状是构建到一半开始 429、看上去像后端挂了。
- 超限返回 **429**，体里有 `dimension` 指明是**哪一格**满了
  （`workspace` = 你的工作区今天用完了；`ip` = 你这个出口地址用完了）。
  合成一句"请求过于频繁"会把"是谁的额度"抹掉，同一个 NAT 下的人会以为是自己的操作出了问题。
- **429 不下发任何 `Set-Cookie`**，与 nginx 的 `@aic-llm-throttled` 落点同一口径。
- 时区：**`Asia/Shanghai`** 切"一天"。刻意写出来 —— 不写就等于把跨天点交给服务器 TZ，
  而"今天用完了"在界面上看起来仍然完全正常。
- 台账落库（H2 `llm_quota` 表，Flyway `V6`），**重启不清零**。放内存里的话，
  一次重启就把配额清零了，等于留了一条「重启即重置」的旁路。保留 7 天，每日 03:45 清理。

**配置只有一个来源**：`QuotaProperties` 的默认值（编进产物、任何机器上都一样、
可从仓库复现）。**刻意没有**往 `config/application.yml` 再抄一份 —— 那份在服务器上
是**去掉密钥的派生物**（见 §4.1），抄一份就有两个来源，本地改了、服务器没改就是一次
静默漂移。要按部署环境调，走已有的覆盖机制：`.env` 里写
`QUOTA_WORKSPACE_PER_DAY=200`（Spring 松绑定直接映射到 `quota.*`）。

**生效值怎么读**（不要读文件，读实际在用的）：

```bash
curl -s https://tianchuang.shuanzi.site/api/quota -H 'X-ALC-Workspace: <你的工作区>'
# {"enabled":true,"day":"2026-10-15","zone":"Asia/Shanghai",
#  "workspace":{"present":true,"used":1,"limit":120,"remaining":119},
#  "ip":{"present":true,"used":1,"limit":600,"remaining":599}}
```

`GET /api/quota` **只读、不扣费**，而且只返回调用方**自己**的两格。未标识的调用方
工作区那格是 `{"present":false}` 而**不是** `used:0` —— 「这个维度不适用于你」与
「这一维今天用了 0 次」是两件事，把前者渲染成 0 会让人以为配额在保护他，
而他其实只被 IP 那格保护着。

> ⚠️ **它不构成身份验证。** 换一个工作区 id 就换一格新额度（所以才要 IP 那格兜底），
> 而 IP 那格对 NAT 后的多个真实用户是共享的。要真正的访问控制，回到
> `docs/安全开关启用评估与回滚.md`；但那个开关的前置条件已经变了（见该文 §0）。

## 7. 三个部署期实测踩到的坑

> 标题里的"三个"是 §7.1–§7.3 当时的数目；后续实测又添了 §7.4 起若干条，
> 标题**没有跟着改** —— 它是历史锚点，改掉会让别处对它的引用失去落点。

### 7.1 ⚠️ 云平台防火墙 ≠ 系统防火墙（**2026-10-14 已解决**）

> ✅ **已解决。** 域名上线后公网入口走 `443`（控制台默认放通），不再依赖任何高位端口规则。
> 之所以保留本节，是因为它给出了一条**至今仍然成立**的判据方法：
> 「包没到机器」与「服务没起」在客户端看起来**一模一样**（都是超时），
> 要靠 **Nginx 访问日志有没有新增那一条**来区分。
> ⚠️ 但**处置动作已经反过来了** —— 当年是去控制台**放通** 28081，
> 现在正确的做法是**让它保持关闭**（§0）。

本机 `sudo ss -lntp` 显示 `0.0.0.0:28081` 在正常监听，`ufw` 也是 `inactive`，
但**从公网访问 `http://62.234.154.34:28081/healthz` 会超时**（`curl` 返回 `HTTP 000`）。
同时 `:80` 返回 200 —— 说明不是网络不通，而是**只有 80 被云平台防火墙放通**。

**判据（怎么区分「包没到」和「服务没起」）**：
请求前后各看一次 Nginx 访问日志的行数 ——

```
before=473    →  请求 28081（超时）  →  after=474
```

只多了一条 `:80` 的请求，**28081 那条根本没进日志** ⇒ 包没到机器，是云防火墙拦的，与后端无关。

**处置（2026-10-14 起）**：**不做任何事** —— 不要再去控制台给 28081 添加放行规则。
（当年那条「添加 TCP 28081 / 来源 `0.0.0.0/0` / 放通后 `curl …/healthz` 应返回 `ok`」的
操作步骤**已按用户要求从本文删除**：它现在是一条会把人引向"重新打开一个已关闭端口"的指令。）

> 上面"包到没到机器"的**判据方法仍然有效**（access.log 行数前后对比）——
> 那是探测手法，与"该不该放通"是两件事。§10.1 有当前的反向自检。

### 7.2 Nginx 指令继承：`location` 里写一条 `proxy_set_header`，会**取消整组**继承

`/ws/` 里原先只写了 3 条 `proxy_set_header`（Upgrade / Connection / Origin），
结果 server 级的 `Host` 等**全部不再继承**，Nginx 回落到默认的 `$proxy_host`，
也就是**上游名 `AIC-tianchuang_backend`** —— 这个名字含下划线，Tomcat 直接拒绝：

```
java.lang.IllegalArgumentException: The character [_] is never valid in a domain name.
```

客户端看到 **400**，日志里是一串 `HttpParser.readHostDomainName` 堆栈。

**规则**：nginx 的指令继承是「**按级别整体替换，不是逐条合并**」——
`location` 里要用 `proxy_set_header`，就得**把整组重写一遍**。
修完 `/ws/` 握手返回 **101**（已在 §8 验证）。

### 7.3 ⚠️ 摘掉 `sites-enabled` 链接 **不等于** 释放端口；而且端口"被占"要说清**是谁占的**

停用本项目时实测到一个会误导人的状态：

```
sites-enabled/            -> 只有 hongsight（我们的站点早就摘掉了）
sudo ss -lntp | grep 28081 -> 0.0.0.0:28081  nginx  ← 端口还占着
我们的单元                 -> active=inactive  enabled=disabled（确实停了）
```

**根因**：nginx 只在 `reload`/`restart` 时重读配置。链接摘掉之后，它**继续持有上一次
已加载的 `listen 28081`**，直到下一次 reload。所以「链接不在」与「端口已释放」是两件事。

所以停用脚本的顺序必须是 **先摘链 → `nginx -t` → `reload` → 再停服务**；
只做前半段会留下一个**看起来已经停干净、实际还占着端口**的状态 ——
而这恰好是本项目最不该出的问题（用户明确要求"不要抢占端口"）。

配套的两条判据纪律：

1. **端口判据必须逐端口给布尔值，并打印属主**：
   `for p in 28081 28082 28083; do ss -lnt | grep -q ":$p\b" && echo HELD || echo free; done`
   —— 只读端口列表（`ss | grep`）会把"nginx 占着"和"我们的服务没停"混成同一个现象，
   于是去查错的对象。`verify-remote.sh` §B 与 `disable-remote.sh` 都已改成逐端口 + 属主。
2. **`grep -r` 不跟随 `sites-enabled` 里的符号链接**（要 `-R`）。
   实测：`grep -rlE 'default_server' /etc/nginx/sites-enabled/` 给出 **0**，
   而 `grep -RlE` 给出 `hongsight` —— 假 0 会让"唯一性"判据永远通过。
3. `default_server` 的不变量是「**只有一个站点文件拥有它**」，不是「行数 = 1」：
   hongsight 里 `listen 80 default_server;` 与 `listen [::]:80 default_server;`
   各一条是合法的 v4+v6 写法（实测 2 行 / 1 属主）。按行数判会把正常状态判红。

### 7.4 ⚠️ `gzip_types` 没配 ⇒ 24 MB 未压缩 ⇒ 前端「请求超时」（2026-10-13 22:20）

**现象**：公网打开后页面能加载、WebSocket 也连上了（Java 日志有「大屏客户端接入」），
但顶部挂着红条 **「请求超时，请稍后重试」**（`api.js:45` 的 `AbortError`）。

**根因（已定位到字节）**：`GET /api/traffic/session` 单次返回 **24,467,362 B（24.5 MB）**
的 JSON，而且**没有压缩**。系统级 `nginx.conf` 只有 `gzip on;`，`gzip_types` 那一行是
**注释掉的** ⇒ 生效的是编译内置默认值（仅 `text/html`）。前端 `api.js` 对这个请求用的是
默认超时 **25 s**（`TrafficWorkbench.vue` 调 `requestJson` 时没传 `timeoutMs`），
24 MB 在公网带宽下必然超时。

**判据（一眼看出来）**：同一次探测里 `/`（html）**有** `Content-Encoding: gzip`、
`/api/traffic/session`（json）**没有** —— 差别就在 `gzip_types`。

**修法**：在本项目自己的 server 块里显式写 `gzip_types`（**不改全局 nginx.conf**，
因此不影响 hongsight / ice-travel）。见 `.run/cloud/AIC-tianchuang.site`：

```nginx
gzip on;
gzip_types application/json text/javascript application/javascript text/css text/plain text/xml application/xml image/svg+xml;
gzip_min_length 256;
gzip_comp_level 5;
gzip_proxied any;
gzip_vary on;
```

**实测收益**（同一份载荷，`Accept-Encoding` 对照）：

| 资源 | 原始 | gzip 后 | 倍数 |
|---|---|---|---|
| `/api/traffic/session` | 24,467,362 B | 3,951,429 B | **6.2×** |
| `/assets/index-*.js` | 2,102,820 B | 588,796 B | 3.6× |
| `/assets/index-*.css` | 177,657 B | 27,644 B | 6.4× |
| `/` (index.html) | 429 B | 349 B | 1.2× |

**踩到的两个坑（都可迁移）**：

1. **静态资源的 `Content-Type` 由后端决定，不是 nginx 的 `mime.types`。**
   本项目 `location /` 是 `proxy_pass` 到 Java，实测 `/assets/index-*.js` 返回的是
   `Content-Type: text/javascript`，而 nginx 自己的 `mime.types` 写的是
   `application/javascript`。只按后者配，主包会**静默地不被压缩**（不报错，只是慢）。
2. **`systemctl reload nginx` 之后立刻测，可能量到"上一代"配置。**
   reload 是优雅重启：老 worker 会把手上的连接服务完。第一次复测时 JS 仍返回
   2,102,820 B（原样），一度被我判成"改了没生效"；稍后重测即 588,796 B。
   ⇒ **改完 nginx 配置后的验收，要么留出老 worker 退场时间，要么只看响应头。**

> **遗留（未做）**：4 MB 对慢速热点仍偏大，且浏览器还要 `JSON.parse` 24 MB（解压后）。
> 可选加固：给 `TrafficWorkbench.vue` 的 session 请求单独调大 `timeoutMs`，
> 或从根上减小该接口的载荷。两者都要改前端并重新构建部署，**尚未执行**。

### 7.5 ⚠️⚠️ 双层反代下 WebSocket 必须在**两层**都透传（2026-10-14 实测踩到）

**现象**：域名上线后，从 `https://tianchuang.shuanzi.site/` 打开大屏，
实时推送不工作（界面上「连接状态」一直重连）；
但**从服务器本机直连 `http://127.0.0.1:28081/ws/dashboard` 却是 101**。

**判据（两条必须一起看，单看任一条都会得出错的结论）**：

```
经 443 域名  →  HTTP/1.1 400    body: Can "Upgrade" only to "WebSocket".
直连 28081   →  HTTP/1.1 101
```

只测后者 ⇒ 会得出「WS 正常，问题在别处」；只测前者 ⇒ 会去怀疑 Java 的 Origin 白名单
（而白名单那会儿确实是过的）。

**根因**：`sites-available/domains` 里 AIC 的 443 块写了

```nginx
proxy_set_header Connection        "";
```

却**没有**透传 `Upgrade`。WebSocket 是**逐跳（hop-by-hop）协议** —— 升级请求要在
**每一跳**重新声明；外层把它掐掉，内层就没有东西可升。
`Connection ""` 这个写法本身是为了关掉向上游的 keep-alive（常见惯例，不是手滑），
它与 WebSocket 共存时的正确写法是让 `Connection` 跟着 `map` 走：

```nginx
# 在 conf.d/AIC-tianchuang-upstream.conf（http 上下文）
map $http_upgrade $AIC_tianchuang_connection { default upgrade; '' close; }
```
```nginx
# 在 443 块 与 snippets 的 /ws/ 里，**两处都要**
proxy_set_header Upgrade    $http_upgrade;
proxy_set_header Connection $AIC_tianchuang_connection;
```

内层 `snippets/AIC-tianchuang-api.conf` 本来就是对的 —— 这正是「只修一处、
且只用直连去测」看不出来的原因。

**可迁移**：凡是「外层反代 → 内层反代 → 应用」这类结构，逐跳头
（`Connection` / `Upgrade` / `Keep-Alive` / `Transfer-Encoding` / `TE` / `Trailer`）
都要在**每一层**显式处理。只在外层或只在内层写对，都是一个**静默的**半成品：
功能看起来在，只是永远不工作。

### 7.6 ⚠️⚠️ reload **返回 0 但配置根本没生效**（2026-10-14 实测踩到，最险的一次）

**场景**：本次改造要把内层监听从 `0.0.0.0:28081` 收窄成 `127.0.0.1:28081`（公网入口收回内网）。
落地脚本跑完，`nginx -t` 通过、`systemctl reload nginx` **退出码 0**、脚本打印「nginx 已 reload」，
**一切看起来都成功了**。

**实际状态：线上仍跑旧配置。** 三条硬证据：

```
# ① error.log（reload 那一刻）
[emerg] bind() to 127.0.0.1:28081 failed (98: Unknown error)
[emerg] bind() to [::1]:28081 failed (98: Unknown error)
[emerg] still could not bind()

# ② 端口还挂在通配上（没收窄）
LISTEN 0 511 0.0.0.0:28081 ... users:(("nginx",pid=…,fd=11))
LISTEN 0 511    [::]:28081 ... users:(("nginx",pid=…,fd=12))

# ③ 行为仍是旧的：`/` 与 `/login` 都返回 401（Basic Auth），
#    而新配置下应当是 302 → /login 与 200。
```

**根因（nginx 的 socket 语义，不是配置写错）**：`0.0.0.0:28081` 是**通配绑定，盖住**
`127.0.0.1:28081`。reload 时新 cycle 要创建**新的** socket，而旧的通配 socket 还在 master
手里（fd 未关），于是 `bind()` 撞 `EADDRINUSE`（日志显示为 `(98: Unknown error)`——
errno 98 就是 EADDRINUSE，被 nginx 印成 "Unknown error"）。
**nginx 在 bind 失败时会保留旧 cycle 继续服务** —— 于是失败被完整地静默掉了。

> **reload 可以复用同一组 socket，但**不能把通配地址收窄成具体地址**。改 `listen` 的
> 地址/端口，必须 `restart`。**

**为什么这次会踩到**：这不是手滑，是**判据选错了**。我原来判的是
「`nginx -t` 过 + `reload` 退出码 0」，而这两条**都对**。要判的是**结果**：

```bash
# 判 listen 有没有真的变（而不是判命令有没有报错）
WANT=$(grep -oE '^[[:space:]]*listen[[:space:]]+[^;]*28081' "$NA" | head -1 | awk '{print $2}')
systemctl reload nginx                      # 退出码恒为 0，不可作为判据
if ss -lntH 'sport = :28081' | grep -q '0\.0\.0\.0:28081'; then
    systemctl restart nginx                 # 收窄通配只能靠 restart
fi
ss -lntH 'sport = :28081' | grep -q '127\.0\.0\.1:28081' || echo "FAIL 没生效"
tail -n +$((N+1)) /var/log/nginx/error.log | grep -q 'could not bind' && echo "FAIL 有配置没生效"
```

现 `.run/cloud/_apply-nginx-remote.sh` 第 6 步就是这么判的：**reload 后核对实际绑定地址 +
扫 error.log 的 `still could not bind()`；发现通配没收窄就自动升级为 restart**。

**可迁移**：`systemctl reload X` 的退出码只说明**信号送达**，不说明**配置生效**。
凡是「改了监听地址 / 端口 / socket 数量」的变更，判据必须是**去量那件事本身**
（`ss` 的绑定地址、error.log 的 bind 结果），而不是量命令的返回码。
**命令报成功、结果没变，正是最需要抓的形态。**

### 7.7 ⚠️ 清理失败会**冒充**成整个脚本的失败（`mktemp` 在 Git Bash 下返回混合路径）

**现象**：`.run/cloud/deploy-nginx-domain.sh` 每一步都打印成功，最后 **`RC=1`**，
并且只多一行莫名其妙的：

```
[safe-delete][SAFE_DELETE_INVALID_PATH] embedded drive prefix is not allowed
```

**根因**：脚本里 `TMP=$(mktemp -d)`，而本机 Git Bash 的 `mktemp` 返回的是
**混合路径**：

```
C:\Users\12921\AppData\Local\Temp/tmp.C3P1FhqNKp     ← 盘符+反斜杠，尾巴却是正斜杠
```

`trap 'rm -rf "$TMP"' EXIT` 被沙箱的 safe-delete 以「embedded drive prefix」拒绝 ⇒
`rm` 返回 1 ⇒ **EXIT trap 的返回值覆盖了脚本的退出码**。

**为什么危险**：`RC=1` 会把人引去查 nginx / 查配置，而真实原因只是"临时目录没删掉"。
**退出码与真实原因无关**，是标准的误导性证据。

**修法**：临时目录建在仓库内的**纯 POSIX 路径**下，且清理失败不许影响退出码：

```bash
mkdir -p "$HERE/tmp"
TMP="$(mktemp -d "$HERE/tmp/nginx-deploy.XXXXXX")"   # 返回 /c/Users/... ⇒ rm 正常
trap 'rm -rf "$TMP" 2>/dev/null || true' EXIT        # 清理失败不参与退出码
```

**可迁移**：任何 `trap … EXIT` 里的清理动作都必须 `|| true`。**清理是收尾，不是判据** ——
它没有资格决定"这次变更成不成功"。（`.run/` 已在 `.gitignore:40`，临时目录不会被提交。）

### 7.8 ⚠️ 302 是对的，**落点**是死的（状态码判据量不到"可达性"）

**现象**：改造完成后 302 正常，但 `Location` 头是：

```
Location: http://tianchuang.shuanzi.site:28081/login
```

`http` + **28081** —— 一个刚刚被收回内网、公网连不上的端口。
真实用户打开 `https://tianchuang.shuanzi.site/` 会被跳到那里，然后**一直转圈**。

**根因**：nginx 默认 `absolute_redirect on`，它生成的跳转拼成
`scheme://$host:<监听端口>/uri`。本层监听端口是 28081，于是端口被带进了 Location。
（本次收窄监听，正好把这个一直存在的毛病**变成了致命的**。）

**修法**：内层 `server` 块加一行，让 nginx 发相对 Location：

```nginx
absolute_redirect off;      # → Location: /login，浏览器留在原 scheme/host
```

**⚠️ 关键教训（判据层面）**：我当时的判据是「`/` 未带会话 → 302」，
**这条判据全绿**。要判的是**落点**：

```bash
LOC=$(curl -sI https://tianchuang.shuanzi.site/ | tr -d '\r' | awk -F': ' '/^Location:/{print $2}')
case "$LOC" in
  /login)   echo PASS ;;
  *:28081*) echo "FAIL 落点指向已收回的端口" ;;
  *)        echo "FAIL 落点异常" ;;
esac
```

这正是 §12/§17 那条老规矩的新实例：**「只验入口不验路径」的判据等于没写**。
状态码只说明"有个跳转"，**不说明跳到的地方还能不能到**。
凡判 3xx，必须连 `Location` 的**值**一起判，且判它**同源 + 相对**。

### 7.9 ⚠️ **判据本身成了变量**（2026-10-14 一轮里连撞三次）

这一节的三个例子是同一件事的三种化身：**被测对象是好的，坏的是量它的那把尺。**
共同症状是"同一件事被两处判据给出相反结论"。

**① 判据读到了注释里。** 段落里为了记录当年的故障，逐字保留着
`proxy_set_header Connection "";`（**注释形式**）。判据若直接对整段做 substring
检查，就会把"已经修好的运行态"读成"仍然坏着"。同一个坑这一轮撞了**四次**：
`.run/_check_nginx_render.py`、`verify-static-remote.sh`、`verify-remote.sh`、
`_apply_domains_aic.py::check_shape`。四处现在都统一成"先剔注释再判"。
> 有意思的是前三次的写法靠"缩进空格数不同"侥幸没误判 —— **那是运气，不是判据**：
> 哪天注释与正文对齐，就会把已修好的读成坏的。

**② 头名大小写取决于协议版本。** 取 `Location` 头时用了 `/^Location:/`：

```
本机 curl（协商 HTTP/1.1）  → Location: /login
服务器 curl（协商 HTTP/2）  → location: /login      ← HTTP/2 规定头名全小写
```

同一条命令在两台机器上**方向相反**。改成 `tolower($1)=="location"` 才是判据。
同类风险：`WWW-Authenticate` / `Set-Cookie` / `Content-Encoding` 一律要用大小写不敏感匹配。

**③ 参照物过期。** "最近 50 行 error.log 里有没有 `still could not bind`"这个判据，
在 20:29 仍被 18:19 那次失败 reload 的旧记录染红 —— 把**已经修好的**现状判成 FAIL。
改成**限定时间窗**（近 15 分钟；日志时间戳 `YYYY/MM/DD HH:MM:SS` 定宽，字典序即时间序）。
判据要问的是"**这次**应用有没有生效"，不是"历史上有没有失败过"。

> **可迁移**：当一个判据红了，先问一句**「是它坏了，还是它在报坏消息」**。
> 本轮 6 个 FAIL 里有 **5 个是判据自己的错**（1 个是我把口令传成了 `aic:aic:…`），
> 只有 1 个是真缺陷（disable 少了 `reset-failed`）。**红了的判据必须先被怀疑一遍。**

### 7.10 「停用」在**共享段落**架构下不再是"摘掉一个链接"

**旧口径**（IP 直连时代）：停用 = `rm sites-enabled/AIC-tianchuang` + 停服务。
**为什么现在不成立**：公网入口换成了 `https://tianchuang.shuanzi.site/`，
而那个 443 块住在**三个项目共享**的 `sites-available/domains` 里。于是：

| 做法 | 后果 |
|---|---|
| 只摘内层站点块 | 443 块还在，往没人听的 `127.0.0.1:28081` 反代 → 公网拿到 **502** |
| 把 AIC 段整个删掉 | 该 `server_name` 无匹配 → 落到全机唯一的 `default_server`（hongsight）→ **别的项目在我们的域名下应答** |
| **换成显式停用段（本次做法）** | 留着 `server_name`、留着证书、正文 `return 503` → 公网拿到 **503**，语义明确 |

所以停用态是一个**显式存在的一块**（`bin/domains-aic-parked.conf`），由同一个
段级替换器换上/换回；`disable-remote.sh` 先把运行态 `--dump` 存档到
`$R/backup/domains-aic-running.txt`（0600），`enable-remote.sh` 据此还原。
**判据**：停用后公网必须是 **503**（502 说明段没换上去、200/302 说明还在跑）。

**附带一个反直觉的权限坑（实测）**：在 `/tmp` 这种粘滞位目录里，
**root 写不了由别的用户创建的文件** ——

```
-rw-r--r-- 1 ubuntu ubuntu ... /tmp/_dm.ub
sudo python3 ... /tmp/_dm.ub      →  PermissionError: [Errno 13] Permission denied
```

root **读**得了 0600 的文件，却**写**不了 644 的别人文件。本项目生产路径不受影响
（写目标一直是 `/etc/nginx/...` 或 root 自己创建的文件），但**测试时**很容易踩到，
并且会把它误读成"脚本坏了"。替换器现在对这种情况给出人话 + 退出码 2。

### 7.11 ⚠️⚠️ 迁移脚本没被执行过一步（2026-10-14 晚，**部署前拦下**）

`V6__llm_quota.sql` 里写了一列 `day VARCHAR(10)`。H2 把 `DAY` 当**保留字**
（INTERVAL 字面量的单位），建表当场语法错误：`expected "identifier"`。

**为什么这一条比 §7.1–§7.10 更值得单列**：前面那些都是"部署之后才看见"，
这一条是**部署前**用真实 H2 跑了一次脚本才发现的。而它的后果**不是回滚能修的**：

- Java 套件跑的是 Mockito 假仓库，**里面没有一句 SQL**，结构上够不着 DDL；
- `mvnw package` 只是把 `.sql` 塞进 jar，从不执行它；
- 一旦上了服务器，Flyway 会把 V6 记成 **failed**，`flyway_schema_history` 就此被污染 ——
  **回滚 jar 也修不好**，因为上一版同样会拒启。

**修法有两层**：① 列名改成 `quota_day`（**不要**改成双引号 `"day"` —— 一带引号 H2 就按
大小写敏感处理，而 Hibernate 生成的是不带引号的小写，两边会指向不同标识符）；
② 新增常驻闸门 `tools/maintenance/_verify_migrations.py`，把每个 `V*.sql` 在**同版本 H2** 上
真跑一遍，并**配一条负向自检** `--self-test`（合法 DDL 必须通过、保留字列名必须被判红）。
配自检的理由和 §7.9 同源：只用合法 DDL 试的话，一个悄悄什么都没执行的 RunScript 也会是绿的。

**另配** `tools/probes/_probe_quota_local.py`：起真 jar + 空库，让 Flyway 真跑 V1–V6，
再用 `--quota.workspace-per-day=1 --quota.ip-per-day=2` 驱动端点，把配额的四条行为
（放行 / 按工作区拒 / 按 IP 拒 / 计数器互不影响）在**一次大模型调用都不花**的情况下验完。
它补的是 `_verify_migrations.py` 明确**不覆盖**的那半：SQL 对不对 ≠ 实体映射对不对。

> 这两条判据第一轮就各抓到一次真错：迁移闸门抓到 `day`；本地探针抓到"jar 是先于修复
> 构建的，里面还是旧 V6"。**两者都是"看起来一切正常"的状态。**

### 10.2 ✅ **已解决**：和风天气「接口契约漂移」（2026-10-16 · 0.9.34（Beta））

**现象**：`/api/config/status` 显示 `effectiveSource=live-public`、`degraded=true`，
即**未走和风首选源**，退回 open-meteo（并在界面上如实标注降级）。

**根因（已定位到字段级）**：和风**凭据在云端完全可用** ——
`GET /api/internal/qweather/current?lat=43.9&lon=125.32` 拿到的是**完整合法响应**：

```json
"metadata": { "tag": "0343de29…", "attributions": ["https://developer.qweather.com/attribution.html"] },
"condition": {...}, "temperature": {...}, "wind": {...}, "windGust": {...},
"precipitation": {...}, "pressure": {...}, "visibility": {...}, "cloudCover": 0.01
```

**`metadata` 里只有 `tag` 和 `attributions`，没有 `obsTime`**；
而 `QweatherClient.java:73` 把它列为**必需字段**：

```java
String time = requiredText(root.path("metadata").path("obsTime"), "metadata.obsTime");
```

取不到 → 抛 `和风字段缺失: metadata.obsTime` → 按既定纪律降级到公共源并标 `degraded`。

**这是应用侧的接口契约漂移，与某一次部署无关，本地环境同样会发生。**

**2026-10-16 处置（0.9.34（Beta））：按上面那条 A 落地。** 把 `metadata.obsTime` 从
**必需**降为**非必需**，缺失时**退回 `ingestedAt`**（本系统收到该响应的时刻），
并把这一情况写进 `qualityFlags`。

> ⚠️ **刻意没有选"用 `now()` 兜底"**：那会让新鲜度判据看起来成立，把「抓取时间是估算的」
> 糊成「数据是新鲜的」—— 属纪律②点的「把『未验证』写成『已通过』」。
> `ingestedAt` 是**真实发生过的时间**、可追溯；`now()` 不是。

**实证**：上线后一次新抓取（`2026-10-16T16:38:42`，runId `7be8bba6`）→
`effectiveSource=live`、`degraded=false`。修复前同一端点长期是 `live-public` / `true`。
（见 §8.4 第 8 项，以及那里关于「`lastAttempt` 是存档不是当前状态」的提醒。）

### 10.3 ✅ **已解决**：WebSocket 白名单（2026-10-14）

**原状**：`WebSocketConfig.java` 只放通回环，靠 Nginx **把 `Origin` 重写成
`http://127.0.0.1:28082`**（零代码改动）打通。代价是请求头不再忠实反映真实来源。

**现在**：白名单里加入了 `https://tianchuang.shuanzi.site`，
`/ws/` 里那行改写换成了**透传真实 Origin**：

```nginx
proxy_set_header Origin $http_origin;
```

```java
.setAllowedOriginPatterns(
        "https://tianchuang.shuanzi.site",
        "http://127.0.0.1:*",     // 保留：隧道/本机探测仍会用到
        "http://localhost:*");
```

**判据**：经域名握手 `HTTP/1.1 101`（§8.1 第 8 条），且带真实 Origin 也过白名单。
> ⚠️ 顺序：新 JAR 里含域名白名单，**先应用后改 nginx**；反过来会有一段 WS 403 的窗口。
> 另：curl / 探针不带 `Origin` 时 Spring 一律放行，所以"探针过了"**不能**证明
> 带 Origin 的浏览器也能过 —— 判据必须带 Origin（这正是 §7.5 的教训）。

### 10.7 🟠 **会影响放行、但地图上没有表示**的气象（2026-10-13 核对，用户提问触发）

用户问："还有什么会影响航班的气象、地图上显示不出来的？"下表是**逐个因子**核对规则配置
（`config/rules-v1.json::factors`）与几何生产者（`traffic/weather.py`）之后的结论，
不是回忆。**六个因子里，两个完全没有几何，两个的量与规则不是同一个数。**

| 因子 | 规则判据（`config/rules-v1.json`） | 地图上的几何 | 后果 |
|---|---|---|---|
| `tempC` 温度 | range：**≤ −20 ℃** 或 **≥ 45 ℃ 禁飞** | **完全没有**（无图层、无箭头、无面） | 因温度被拒的班次，在地图上**一点痕迹都没有** |
| `precipMmh` 降水强度 | high：**≥ 5 mm/h 禁飞** | 只在 **≥ 8 mm/h**（`EXTREME_HOURLY_RAIN_MM`）画 6 km 内核 | **5–8 mm/h 这一档：已禁飞，地图空白** |
| `windSpeed` 平均风速 | high：**≥ 12 m/s 禁飞** | 只有**箭头**（方向与量级），**无风险面** | 看不见"哪片区域已被判禁飞" |
| `windGust` 阵风 | high：**≥ 18 m/s 禁飞** | 在 **≥ 17 m/s**（`EXTREME_WIND_GUST_MPS`）就画内核 | **反向不一致**：17–18 之间"地图禁止进入、规则只是谨慎" |
| `thunderProb` 雷暴概率 | high：**≥ 0.6 禁飞** | 无（且**没有真实数据源**，恒 `None`） | 规则在表里，但既不判也不画 —— 是**弃权**，不是"没有雷暴" |
| `visibilityM` 能见度 | low：**≤ 1000 m 禁飞** | **0.9.28 起**两档灰，**读同一份配置** | 已对齐 ✅ |

**这是同一族问题（M79）**：温度、降水、阵风这三个量，规则侧与地图侧**各写一份**，
两份各自被钉过、谁也不会报警。0.9.28 给能见度做的那次修法（地图侧不再自己写常量，
改从 `config/rules-v1.json` 读）就是这一族的通用解法。

> ⚠️ **但"对齐"不等于"改成同一个数"，动手前必须先回答这个问题。**
> `weather.py` 的注释写明：地图侧那几个阈值（阵风 17 / 降水 8）当初是**故意**与规则不同的
> —— 地图只负责"雷达还没分辨出来的、极端到足以单独禁飞的单个站点读数"，其余交给雷达回波。
> 所以阵风 17 与规则 18 的差、降水 8 与规则 5 的差，**可能是有意的**；真正该补的是
> **把这两套阈值的关系写成一条声明**（哪一套管什么、为什么允许不同），而不是把两个数改成一样。
> 在那之前，上表第 2 行（5–8 mm/h 禁飞但地图空白）是**使用者会真正踩到**的那一条。

### 10.8 ✅ **代码就绪、本轮未上线**：三条免费气象补充源与两个只读端点（0.9.35（Beta），2026-10-17）

> ⚠️ **先看这一句**：本节写的所有东西**只在本地实现并验证过，服务器上仍然是 0.9.34（Beta）**。
> 用户当轮的原话是「以上内容完成更新后**暂时不传云服务器端**」，所以下面的端口/证书/配额表
> **都不需要改**。等要上线时按 §9 走一遍，并**先看本节最后那段「上线前必须补的两件事」**。

**加了什么**（都是**免费、无需密钥**的公开源，全部先实测再落地）：

| 源 | 端点 | 角色 | 实测（2026-10-17，本机） |
| --- | --- | --- | --- |
| MET Norway | `api.met.no/weatherapi/locationforecast/2.0/compact` | **可作主源**（`ALC_WEATHER_PROVIDER=met-no`） | HTTP 200 / **1995 ms**；逐点请求（并发） |
| Aviation Weather Center | `aviationweather.gov/api/data/metar` | **补充观测通道**（机场单点报文） | HTTP 200 / **784 ms**；bbox `38,115,54,136` 实测 **23 站** |
| Open-Meteo GFS / ICON | `api.open-meteo.com/v1/gfs`、`/v1/dwd-icon` | **不确定性对比**（只报差值） | 200 / **978 ms**、**1637 ms** |

**三条口径**（写在这里是因为它们**会决定别人怎么读这些数字**）：

1. **单位用实测报文自证，不是查常数表** —— AWC 的 JSON 是**节**与**法定英里**：
   `wspd=17 / wgst=33` 对应报文 `13009G17MPS`（9/17 m/s），`visib=3.73` 对应报文 `6000` 米。
   换算 `KT_TO_MPS=0.514444`、`SM_TO_M=1609.344`。
2. **`6+` 是下限**（大于 6 英里）→ 后端返回 `visibilityM=None` ＋ `visibilityIsLowerBound=true`，
   界面写「仅报下限（>6 mi）」。写成 9656 m 就是把"至少"读成"正好"。
3. **METAR 不是雷达**：`qualityFlags` 里固定带 `NOT_A_RADAR_ECHO_DO_NOT_CONVERT_TO_DBZ`，
   界面与文案都不许换算成 dBZ（词汇纪律见 `docs/NAMING.md`）。

**两个只读端点**（`GET`，**不进主链路**，各自缓存 10 分钟）：

| 端点 | 返回 | 界面消费点 |
| --- | --- | --- |
| `/api/traffic/weather/observations` | 机场实测报文 + `coverage`（33 城里有几个有邻近站、哪些没有） | 运行台 → 报文情报 → **观测报文**档内的「取实测报文」按钮 |
| `/api/traffic/weather/models` | GFS 与 ICON 的逐城温差/风速差（单模型时 `null`，**不是 0**） | 同一处的「取模型差值」按钮 |

**为什么它们不进主链路**：主链路每轮加载都要抓天气，目标是**不超过 10 秒**；多两个外部请求
等于把别人服务的抖动变成页面加载的抖动。所以做成**按需按钮**，并把覆盖不足如实印在块里
（「23/33 个城市有邻近机场站 · 无邻近站 N 个：… · 机场单点报文，不是面上的气象场」）。

**上线前必须补的两件事**（现在**没做**，别以为已经做了）：

1. **Nginx 层**：两条新路径是 `GET`，`_audit_quota_coverage.py` 的口径里**读接口一律不计费**，
   所以配额 `map` **不需要**加它们；但若日后给它们加 `limit_req`，**只挂自己的 site 块**，
   别动共享的 `domains`（细则见 §6.4 与本文件 §7.10）。
2. **Java 网关**：`DecisionController` 已补两条 `@GetMapping`（路径比 `{resource}` 白名单多一段、
   塞不进去 —— 同一形状的缺失这是**第四次**）。上线前跑一次
   `tools/maintenance/_audit_gateway_routes.py`，确认这两条调用点被认成 `MATCHED` 而不是 `DEAD`。

## 12. 不要回退的五条

1. **`SERVER_ADDRESS=127.0.0.1`；内层监听的 28081/28082/28083 一律只在回环** ——
   改成 `0.0.0.0` 等于把后端（或内层站点）直接裸奔到公网。公网面只应剩 22/80/443。
2. **Nginx `/ws/` 里那组 `proxy_set_header` 必须整组存在，且 443 层也要有一份** ——
   少写 `Host` 就复现 §7.2 的 400；漏了 `Upgrade`/`Connection` 就复现 §7.5 的 400。
   **两层都要，且两层都要测**。
3. **`:80` 的 `default_server` 不归本项目** —— 全机只有一个属主，当前属于 hongsight。
   判据是「属主文件数 = 1」，不是「行数 = 1」（v4+v6 各一行合法）。
4. **`domains` 里的 AIC 段不许直接删掉** —— 删了会让 `tianchuang.shuanzi.site`
   落到 hongsight 的 `default_server`，变成别的项目在我们的域名下应答。
   停用要走 `bin/disable-remote.sh`（换成显式 503 的 parked 段），见 §7.10。
5. **机密一律不明文**（§6.2）—— `config/application.yml` 只许写 `${DEEPSEEK_API_KEY:}`，真值只在
   `.env.secrets`（600）；登录口令不落盘。`install-remote.sh` / `enable-remote.sh`
   均以「命中明文 `api-key: "sk-` 即拒装/拒启」为判据，别把这条降级成一行提示。
