## 2. P0 · 两条，都在评委手上会出事的路径上

### N-1 路由「只写不读」：带 hash 的链接全部回到运行首页

队友的执行记录写「切页 `#/corridor/profile` ✅、刷新保持 ✅、后退不离开站点 ✅」。实测**只有第一项和第三项成立**。

四种进入方式，逐个测：

| 进入方式 | 预期 | 实测 |
|---|---|---|
| 站内点「走廊」 | 切到走廊剖面 | ✅ `#/corridor/profile` |
| 后退 | 回上一页、不出站 | ✅ 仍在 `tianchuang.shuanzi.site`，`history.length=16` |
| **直接打开 `#/corridor/profile`** | 走廊剖面 | ❌ **45 秒内始终停在运行首页** |
| **刷新 `#/corridor/profile`** | 走廊剖面 | ❌ 回运行首页 |
| **页面加载后手动改 hash** | 切到对应页 | ❌ 视图不变 |

（判据不是看 `h1`，是看页面正文有没有「这条走廊几点能飞」这个签名句，以及二级 tab 是否激活。）

**第一个根因（静态可证，不用猜）**：hash 映射表的键名和实际 section 名对不上。

```js
Fd = { home:'situation/home', overview:'situation/overview', weather:'situation/weather',
       profile:'corridor/profile',
       intel:'corridor/intel',        // ← 实际 section 叫 briefing
       alerts:'dispatch/console', schedule:'dispatch/ledger', assistant:'dispatch/evidence',
       model:'model/card',            // ← 实际 section 叫 card
       caliber:'model/caliber',       // ← 实际 section 叫 reference
       counterfactual:'compare/counterfactual',
       divergence:'compare/divergence', // ← 实际 section 叫 ledger
       history:'compare/log' }
```

`Id(section)` 是 `Fd[section] || Fd.home`。四个 section 名不在 `Fd` 里，所以**查不到就静默回落到 `situation/home`**。

这解释了实测里的怪现象：13 个页面只有 9 个不同 hash，而且

- 民航情报 → `#/situation/home`
- 检验结论 → `#/situation/home`
- 口径与来源 → `#/situation/home`
- 分歧台账 → `#/situation/home`

**第二个根因（现象确凿，定位留给队友）**：读入口不跟 `location.hash` 同步。
`mn()` 是唯一读 hash 的地方，输入是 `Me.hash`；而站内点击走的是「直接改 section」的另一条路（`$e` / `et`）。
于是**写生效、读不生效**：URL 变了，视图没动；URL 是别人给的（直达/刷新），视图更不会动。

对评委意味着什么：看完「复盘对照」想回头再看「走廊剖面」，或者你说「我发个链接给你」——**给不了**。

### N-2 调度台账 1010 行，全部「undefined 位模拟乘客」

打开「处置 → 调度台账」，表体每一行的「起降点与任务」都是：

```
CITY-1-01 → CITY-1-05 · undefined 位模拟乘客
```

1010 行，**没有一行例外**（文本节点级扫描，前 20 条全部命中）。

根因明确：`/api/traffic/session?fields=slim` 的字段白名单里**没有 `payload`**。
全量计划里 `payload = 2`（每班 2 位模拟乘客），slim 把它裁掉了，前端 `${payload} 位模拟乘客` 直接取到空。

这是 W-5 的**同类漏项**：那一轮补了 `routeId`（因为事件键要用），没补 `payload`（因为只有台账显示要用）。
修它只要在白名单里加一个词，**10 分钟，收益是 1010 行**。

（对比：上一轮是 `已确认（事件 undefined:WEATHER_BLOCKED:true）`，一条回执里出现一次；这一轮是整张表的每一行。位置上更显眼。）

### N-5 34 / 53 条「四条判据全绿、结论却是需谨慎」

雾案例全量 53 条逐条拉判据：

- **19 条不可飞**：每条至少有一条判据 `passed=false` ✅ 自洽
- **34 条需谨慎**：**四条判据全部 `passed=true`** ❌ 不自洽

以 CAR-1-02-1-08 为例（页面原样）：

```
能见度  2800.3 m   （阈值 < 1000 m）   满足
阵风    1.0 m/s    （阈值 > 10 m/s）   满足
云底高  5000.0 m   （阈值 < 300 m）    满足
概率档  20.2%      （阈值 ≥ 25%）      满足
→ 结论：需谨慎 · verdictSource = BOTH
→ 解释句：「观测判据与概率档同时命中（概率 20.2%），两档结论一致」
```

**根因**：判据区只画了**停飞档**（能见度 <1000 m / 阵风 >10 / 云底 <300 m / 概率 ≥25%），
而结论用的是**停飞 ∪ 谨慎**（能见度 <3000 m、概率 ≥15%）。**两个档位只画了一个。**
所以 2.8 km 按「注意级 <3000 m」是命中，但行里只写「阈值 <1000 m，满足」；20.2% 按谨慎档 0.15 是命中，行里只写「阈值 ≥25%，满足」。

解释句也跟着错：「两档解释与概率档同时命中」在概率只有 20.2% 时，命中的是**谨慎档**，不是停飞档。

**这是上一轮「三条判据全绿却不可飞」的残留形态**——不可飞那一档修好了，需谨慎这一档没修，而且它占了 34/53 = 64%。

## 5. 队友侧发现记录：HistoryRetention 每天 3:30 失败（附我的补充判据）

队友排查到的这条属于**后端**，我按要求记录并补上影响面与验收口径。

**现象**：每天 3:30 的历史清理全部失败，连续 7 天同一个错。

```
历史清理失败: Null return value from advice does not match primitive return type for:
public abstract long com.tianchuang.repository.SfiRecordRepo.deleteByTsBefore(LocalDateTime)
```

**根因（队友已定位，我认同）**：

| | QuotaService（成功） | HistoryRetentionService（失败） |
|---|---|---|
| scheduled 调用 | `cleanup()` 同类自调用 | `cleanup()` 同类自调用 |
| `cleanup()` 上的 `@Transactional` | 没有 | **有** |
| 结果 | 派生 delete 自己开事务，成功 | 注解失效 → 无事务 → 返回 null → NPE |

`@Transactional` 加在方法上但被同类直接调用，不走 Spring 代理，注解完全不生效。

**我要补的两句**：

1. **即使把事务修对，内存问题也没根治。** 派生 `deleteBy...` 是「先 `select` 全部命中行、再逐条 `em.remove()`」，行数一次性进堆。`@Transactional` 只是让它**不崩**，不会让它**不占内存**。真要收敛，得改成 `@Modifying @Query("delete from ... where ts < :t")` 的 bulk 删除。
2. **为什么测试和 8 页扫描都抓不到。** 全是 Mockito 单测（假仓库永远返回你要的数字），这个 bug **在结构上测不出来**；该类又没有 controller 暴露，页面扫描也扫不到。它在系统里属于「静默失效」——只进日志，不进任何界面。

**验收判据（建议并入 W 系列）**：

- ① 次日 3:30 日志必须出现清理成功行，且带删除行数（>0 或明确 0）；
- ② 连续跑 2 天后，H2 数据文件大小与 `/health.planStore.plans` 不呈单调增长；
- ③ 补一条 `@DataJpaTest` + **无事务上下文**调用 `cleanup()` 的用例（假仓库测不出来，必须真库）；
- ④ 若改成 bulk delete，同时断言"删除行数 == 预置行数"，防止 `@Modifying` 忘加 `clearAutomatically` 导致一级缓存脏读。

**我这边的外部观测限制**（如实说明）：线上未暴露 DB 文件大小与堆内存，外部只能拿 `/health` 和冷加载耗时做代理指标。今天 3 次冷加载 2.1–2.3 s 属正常，但进程只跑了 44 分钟，**不足以证伪多日累积**。这条只能靠上面的 ①② 验收。
