### W-01 情景切换：让结论条和 KPI 来自同一个 `planId`（3 h，A）

**现在**：切到"气象中断 → 重新调度"后，屏幕上是这样的（同一屏，上下两处）：

| 位置 | 显示 |
|---|---|
| 顶部结论条 | "全部 40 条城际走廊的不可飞概率低于 50%，**可按计划运行**" |
| 4 个 KPI | 待处置 **0** · 禁飞级 **0** · 提前量 60 分钟 · 模型覆盖 100% |
| 右栏 | 已关闭 **7760** 班 |
| 页脚 | 放行率 **0%** · 停止放行 **7760** |

![情景切换后的自相矛盾](assets/2026-10-19/scenario_bug.png)

**根因**：`conclusion` 和 `kpis` 是两条独立取数的路径。结论条来自**旧快照**（旧 `planId` 的缓存），KPI 才是新计划算的。两句话都是"对的"，但对的不是同一份计划。

**改成什么**——三步，缺一不可：

**① 后端：结论由 KPI 现算，不许单独存一句文本**

```python
# 反例（现在的做法）：结论是缓存里的一句话
return {"conclusion": cache["conclusion"], "kpis": new_kpis}

# 正解：结论是 kpis 的纯函数，同一个 planId 输入 → 同一句话
def render_conclusion(kpis, model, scenario, base_time):
    if scenario == "WEATHER_BLACKOUT":
        return {
            "text": f"气象通道中断，全部 {kpis['flights_total']:,} 班暂停放行，等待人工确认恢复。",
            "tone": "stop",
            "action": "查看处置建议",
        }
    if kpis["pending"] == 0 and kpis["nofly"] == 0:
        return {
            "text": f"未来 3 小时内，已评估的 {kpis['corridors_total']} 条城际走廊不可飞概率均低于 50%，"
                    f"可按计划运行；最差为{kpis['worst_name']}（{kpis['worst_p']:.0%}）。",
            "tone": "ok",
        }
    ...

# 接口返回里必须带上它算的是哪份计划
return {"planId": plan.id, "scenario": scenario, "generatedAt": now,
        "conclusion": render_conclusion(...), "kpis": kpis}
```

**② 前端：切情景的一瞬间把旧结论"作废"，不是留着**

```ts
async function switchScenario(next: Scenario) {
  scenarioStale.value = true;          // 结论条进入「重算中」态
  pendingPlanId.value = null;
  await api.post('/api/traffic/v2/scenario', { scenario: next });
  const ov = await api.get('/api/traffic/v2/overview');
  if (ov.planId !== currentPlanId.value) return;   // 迟到的旧响应，直接丢
  conclusion.value = ov.conclusion;
  kpis.value = ov.kpis;
  scenarioStale.value = false;
}
```

**③ 结论条要有"作废态"，不能只是空白**

| 状态 | 结论条显示 |
|---|---|
| 正常 | 原句 |
| 切换中 | 灰色，"正在按新情景重算…（约 20 秒）" + 一个细进度条 |
| 重算失败 | 橙色，"重算失败 · 当前显示的是 10-19 23:41 的快照，不是最新情景" + "重试" |

**为什么这样改**：评委不会因为"切换要等 20 秒"扣分，但会因为"上面说能飞、下面说全停"直接判系统不可信。**"慢"是可接受的，"矛盾"不是。**

- [ ] 切"气象中断"，结论条 1 秒内变灰显示"重算中"，重算完变"气象通道中断…"，与页脚"停止放行 7760"一致；
- [ ] 切回"公开天气驱动"，结论条回到"可按计划运行"，KPI 归位；

### W-02 全站时间基准：只允许一个 `timeBase`（1 h，A+B）

**现在**：首页已经对齐 10-19，但"民航情报"表逐行还是旧基准：

```
CAR-1-02-1-14-0-122  ...  09/14 20:12:00  有效 15 分钟
CAR-1-02-1-14-0-182  ...  09/14 21:07:00  有效 15 分钟
```

**根因**：这张表读的是 `session.planBaseTime`（旧），首页读的是 `overview.observation.observedAt`（新）。**两个时间源。**

**改成什么**：

**① 后端只暴露一个字段**，加在 `/api/traffic/v2/overview`：

```json
{
  "timeBase": {
    "planBaseTime": "2026-10-19T15:00:00Z",
    "displayTz": "Asia/Shanghai",
    "label": "计划基准时刻（北京时 23:00）"
  }
}
```

**② 前端全局只用一个格式化函数**，禁止就地 `new Date(...)`：

```ts
export const fmtBase = (d: Date) =>
  new Intl.DateTimeFormat('zh-CN', {
    timeZone: 'Asia/Shanghai', month: '2-digit', day: '2-digit',
    hour: '2-digit', minute: '2-digit', hour12: false,
  }).format(d);

// CTOT 一律 = 基准 + 偏移，偏移是计划里的相对分钟数
const ctot = addMinutes(planBaseTime, row.offsetMin);
```

**③ 表格加一列"相对时刻"**，这是顺手赚的分：

| 班次 | CTOT（北京时） | 相对 | 走廊 | 状态 |
|---|---|---|---|---|
| CAR-1-02-…-122 | 10/19 23:12 | **T+12 min** | 长春↔哈尔滨 | 有效 15 分钟 |

> 加"T+xx"这一列的理由：**评委会立刻明白"这是相对计划基准的时刻"**，而不是又一个他不确定时区的绝对时间。同时**顺手解决 P1-4（走廊剖面横轴 UTC 没标）**——全站统一用"北京时 + T+xx"双标。

**④ 提交前跑这条命令，必须 0 结果**：

```bash
grep -rn "09/14\|09-14\|2026-09-14" src/ server/ | grep -v node_modules
grep -rn "planBaseTime" src/ | grep -v "timeBase"   # 应只剩 timeBase 一处消费
```

**验收**：全站任意页面不出现 `09/14`；民航情报 CTOT 与顶栏同一天；剖面横轴标注"北京时（UTC+8）"。

### W-04 模型卡换头条：从 TS 换成"提前量 + 期望代价"（3 h，B+A）

> 这是本方案**分值最高的一张工单**，也是最容易被做错的一张。做错的方式是"把'没赢'改成'赢了'"——那是造假。正确做法是**换一个你们真的赢了的度量**。

#### W-04.1 现在的样子（危险）

默认 tab（注意级）：

> "结论：**赢了基线**。本模型 TS 高出持续性基线 **0.8 个百分点**……"

第二个 tab（禁飞级）：

> "结论：**这一项没赢基线**。本模型 TS 低于持续性基线 **1.2 个百分点**。"

![禁飞级 tab 自认没赢](assets/2026-10-19/modelcard_vis1k.png)

**评委的动作一定是**：看默认 → 觉得还行 → 点第二个 tab → 看到"没赢" → **把这一页从加分项划成减分项**。

**而且 0.8pp 本身站不住**：26,193 样本、6.3% 正例率，0.8pp 大约就是 **20 个样本**的差别，在噪声里。

#### W-04.2 三个目标的真实数字（接口原值，别改）

| 目标 | 正例率 | POD | FAR | TS | AUC | Brier 技巧 | 提前量中位 | n |
|---|---|---|---|---|---|---|---|---|
| 能见度 <3000 m（注意级） | 6.3% | 0.674 | 0.352 | 0.494 | **0.947** | **0.505** | **60 min** | 62 |
| 能见度 <1000 m（禁飞级） | 0.8% | 0.465 | 0.636 | 0.257 | **0.953** | 0.218 | **120 min** | 10 |
| 阵风 >10 m/s | 3.5% | 0.446 | 0.560 | 0.285 | **0.936** | 0.251 | **60 min** | 56 |

**看这张表要抓三件事**：

1. **AUC 全在 0.93–0.95**——排序能力极强，这是模型的真本事；
2. **Brier 技巧 0.505**（注意级）——比气候基准好一半，概率是"校准过的"，不是拍脑袋；
3. **提前量 60/120 分钟**——这是持续性基线**结构上不可能有**的东西。

而 TS 0.257 vs 0.268，**在 202 个正例上根本不是"输"**：POD 的 95% 置信区间约 ±0.07，0.011 的 TS 差完全在噪声内。

#### W-04.3 真正的杀手锏：把"准确率"换成"期望代价"

这是**不需要重训模型**、半小时能算出来、而且**你们确实赢**的指标。

**做法**：把混淆矩阵换算成钱（或"风险当量"）。设：

- `C_miss` = 漏报一次（放了一班穿越禁飞区）的代价；
- `C_fa` = 虚警一次（多停一班）的代价；
- 期望代价 `E = 漏报数 × C_miss + 虚警数 × C_fa`。

用你们接口返回的计数（test 集）直接算，**相对持续性基线的临界代价比**：

| 目标 | 模型（漏/虚警） | 持续性基线（漏/虚警） | **临界代价比** | 代价比 20:1 时 |
|---|---|---|---|---|
| 能见度 <3000 m | 540 / 606 | 738 / 236 | **1.87 : 1** | 期望代价 **−23.9%** |
| 能见度 <1000 m | 108 / 164 | 136 / 44 | **4.29 : 1** | 期望代价 **−15.9%** |
| 阵风 >10 m/s | 508 / 520 | 708 / 206 | **1.57 : 1** | 期望代价 **−25.7%** |

**怎么算的**（把这个公式也写进页脚，评委可以当场验算）：

```
临界代价比 C* = (模型虚警 − 基线虚警) / (基线漏报 − 模型漏报)

注意级：(606 − 236) / (738 − 540) = 370 / 198 = 1.87
禁飞级：(164 −  44) / (136 − 108) = 120 /  28 = 4.29
阵风  ：(520 − 206) / (708 − 508) = 314 / 200 = 1.57
```

> 这个公式的好处：**它只用了混淆矩阵里的四个数，谁都能复算。** 而且它把"TS 差 1.2pp"翻译成了一个业务能听懂的门槛——"漏报比虚警贵 4.3 倍以上，用这个模型就划算"。

**怎么读这张表**（答辩时就这么说）：


> "只要一次漏报的代价高于 **2 次虚警**，本模型的期望代价就低于持续性基线；在禁飞级，这个门槛是 **4.3 比 1**。
> 低空载人飞行器掉一架的代价，显然远高于多停一班——所以在这个业务里，**用虚警换命中率是正确的取舍，TS 不是合适的评价指标**。"

**这句话的杀伤力在于**：它把"TS 低 1.2pp"从"缺陷"变成了"**按业务代价做的有意设计**"，而且给出了可验证的临界点。

**必须同时写上的诚实注脚**（否则会被反将一军）：

> - 阵风目标对 Open-Meteo 的比较：模式命中率更高（POD 0.780 vs 0.446）但虚警 3,046 次；**代价比低于 8.3:1 时本模型更省，高于 8.3:1 时模式更省**。我们不认为模式在所有代价结构下都更差。
> - 上表按 test 集 26,193 样本的混淆矩阵计算，未做代价参数的敏感性以外的调参。

> **这一段主动写出来，比藏着强十倍。** 评委问"你们的基线是不是挑软的捏"，你有答案；不问，他也看得见"我们写了临界点"。

### W-08 能见度 9656.1 与 σ 0.45：两个"不该出现的精确"（2 h，B）

**现在**：

| 项 | 显示 | 问题 |
|---|---|---|
| 三站能见度 | 全部 **9656.1 m** | METAR 报的是 `9999`，意思是"≥10 km"，不是 9656.1 |
| 不确定度 | **σ ≈ 0.4482** | 比概率本身（6%）大 7 倍 |

#### W-08.1 能见度：`9999` 不是 9656.1

`9999` 是 METAR 的"10 km 或以上"编码，**它本身不是 9656.1 米**。而 9656.1 m 恰好等于 **6 法定英里（6 SM ≈ 9656.06 m）**——所以最可能的原因是：解析层把 `9999` 先按美制单位表转成 `6SM`，再乘回去变成米。

**怎么验证（2 分钟）**：`grep -rn "9656\|1609" ` 解析层。如果搜到 `1609.344` 或 `6 * 1609`，就是这个原因。

**不管怎么来的，问题都一样**：它看起来像"精确到 0.1 米的实测"，而实际是"≥10 km"。

**改成什么**：

| 现在 | 改成 |
|---|---|
| `能见度 9656.1 m` | `能见度 ≥10 km（METAR 9999）` |
| 图表上的点 | 画成**右端带箭头的开区间**（`10 km →`），不画成实点 |

并加一句（这句话同时解释了三站同值）：

> "三站均报 9999（≥10 km），已按下界 10 km 取值；**因此本帧的走廊差异主要来自阵风，不是能见度**。"

> 最后半句很值钱：它主动解释了"为什么三条走廊概率只差 5%"，而不是让评委自己犯疑。

#### W-08.2 σ：现在的公式不成立

现在的公式族是 `σ = 0.05 + k × 站距(km)`。要用 18.1 km 算出 **0.4482**，k 必须约 **0.022 /km**——意味**每 10 km 涨 0.22**，站距 40 km 时 σ 就接近 0.93。

这个数的含义是"概率的不确定度是 ±45 个百分点"，**比 6% 的概率本身大 7 倍**，等于在页面上说"这个预测完全没用"。

**改成什么**——用**数据标定**，不要拍公式：

```python
# 用 18.3 万条同时刻样本，做"留一站"插值残差
# 对每个站 s、每个时刻 t：用其余两站插值到 s 的位置，比较 p_hat 与 p_obs
resid = []
for s in stations:
    others = [x for x in stations if x != s]
    for t in frames:
        p_hat = idw(others, s.location, t)
        resid.append((dist_to_nearest(others, s), p_hat - p_obs(s, t)))
# 按站距分箱，取每箱残差的标准差 → σ(d) 的经验曲线
# 再用 σ(d) = a + b·d 拟合（a≈0.03, b≈0.0008 /km 量级）
```

**预期结果**：18 km 站距 → σ 在 **0.04–0.08**；150 km（走廊中段）→ **0.10–0.15**。这才叫"误差带"。

**页面上改成**：

> 不确定度 **σ ≈ 0.06**（插值误差，18.1 km 站距，由三站留一残差标定，n=183,406）
> 90% 误差带：**0% – 16%**（= 6% ± 1.645σ，下界截到 0——**截断这件事也要写出来**，否则曲线会画到负数去）

**顺手把误差带画进剖面图**（现在只有一条线）——**两条浅色边界线 + 中间填充**，这是"科学诚实"最直观的表达，比任何文字都强。

**验收**：σ ≤ 0.15；每条走廊剖面有误差带；口径页写清 σ 的标定方法。

## 附录 C：部署前自检脚本

> 存成 `scripts/predeploy.sh`，每次部署前跑。**它只做三件事：抓禁词、断接口、量首屏。**

```bash
#!/usr/bin/env bash
# 用法: bash scripts/predeploy.sh https://tianchuang.shuanzi.site
set -u
BASE="${1:-https://tianchuang.shuanzi.site}"
FAIL=0
say() { printf '%-52s %s\n' "$1" "$2"; }

echo "=== 1. 禁词（源码级，需在仓库根跑） ==="
for w in "09/14" "不参与放行判定" "始终由规则引擎" "没赢基线" "（不支持）" "9656.1" "学的是判据"; do
  n=$(grep -rn -- "$w" src server 2>/dev/null | wc -l | tr -d ' ')
  [ "$n" != "0" ] && { say "禁词: $w" "FAIL ($n)"; FAIL=$((FAIL+1)); } || say "禁词: $w" "ok"
done

echo "=== 2. 接口一致性 ==="
python - "$BASE" <<'PY'
import json, sys, urllib.request
base = sys.argv[1]
def get(p):
    r = urllib.request.urlopen(urllib.request.Request(base+p, headers={"User-Agent":"Mozilla/5.0"}), timeout=60)
    return json.loads(r.read())

ov = get("/api/traffic/v2/overview")
checks = []
checks.append(("overview.planId 存在", "planId" in ov))
checks.append(("overview.timeBase 存在", "timeBase" in ov))
checks.append(("conclusion 有 derivedFrom", ov.get("conclusion",{}).get("derivedFrom") == "kpis"))
if "conclusion" in ov and "kpis" in ov:
    n = str(ov["corridors"]["total"])
    checks.append(("结论里的走廊数 == total(%s)" % n, n in ov["conclusion"]["text"]))

mc = get("/api/traffic/v2/modelcard")
t = mc["targets"]["vis3k"]
checks.append(("modelcard.costMatrix 存在", "costMatrix" in t))
checks.append(("leadTime 有 n", t.get("leadTime",{}).get("n",0) > 0))

cf = get("/api/traffic/v2/counterfactual?case=fog-20250105&profile=balanced")
checks.append(("案例 counterfactual 非 0", cf.get("status")=="OK" and cf.get("diff") not in (None,{},[])))

bad = 0
for name, ok in checks:
    print(("  ok   " if ok else "  FAIL ") + name)
    bad += 0 if ok else 1
sys.exit(1 if bad else 0)
PY
[ $? -ne 0 ] && FAIL=$((FAIL+1))

echo "=== 3. 首屏与体积 ==="
SIZE=$(curl -sS -o /dev/null -w '%{size_download}' "$BASE/api/traffic/v2/overview")
say "overview 体积 (${SIZE}B, 上限 100KB)" "$([ "$SIZE" -lt 102400 ] && echo ok || echo FAIL)"
[ "$SIZE" -ge 102400 ] && FAIL=$((FAIL+1))

echo "=== 结果: $FAIL 项 FAIL ==="
[ "$FAIL" -eq 0 ] || exit 1
```

**说明**：第 2 段的 `counterfactual?case=` 断言，是**唯一能自动化验证 W-05 的方法**——它要求"案例存在且差值非零"，糊弄不过去。

> 两个环境提醒：① Windows 下把 `python` 换成 `py` 或你们的虚拟环境解释器；② 如果前端是单包构建（没有 `src/`），把第 1 段 grep 的目录改成你们的源码目录名，别改成 `dist/`——**grep 构建产物永远搜不到中文被转义后的字符串**。
