## 1. 批次一 · 止血（1 小时 10 分，两条 P0）

### F-1 路由读入口：让 hash 能读回来

**问题**：站内切页会写 hash，但直达、刷新、手动改 hash 全部回运行首页（复测报告 N-1）。
**判定**：写生效、读不生效。两个根因。

#### 改点 1：`Fd` 键名对齐 section 名

当前有 4 个 section 名在表里查不到，`Id()` 静默回落到 `Fd.home`：

```js
// 现在（错）
Fd = { ..., intel:'corridor/intel', model:'model/card', caliber:'model/caliber', divergence:'compare/divergence' }

// 改成（键 = Md 里的 section key）
Fd = { home:'situation/home', overview:'situation/overview', weather:'situation/weather',
       profile:'corridor/profile', briefing:'corridor/briefing',
       alerts:'dispatch/console', schedule:'dispatch/ledger', assistant:'dispatch/evidence',
       card:'model/card', reference:'model/reference', mechanism:'model/mechanism',
       counterfactual:'compare/counterfactual', ledger:'compare/ledger', history:'compare/log' }
```

顺带加一条断言（开发期就能抓）：

```js
// 启动时断言：每个可导航 section 都能映射到唯一 hash
// （mechanism 是隐藏页，在 Pd 里被过滤，不计入可导航页；可导航页共 13 个）
const seen = new Map();
for (const k of Object.keys(Fd)) {
  if (seen.has(Fd[k])) console.error('hash 冲突', k, seen.get(Fd[k]), Fd[k]);
  seen.set(Fd[k], k);
}
```

**验收**：可导航的 13 个 section 的 hash **互不相同，且不同 hash 数量 = 13**（现在是 9 个）。

#### 改点 2：读入口改读 `location.hash`

现状：`mn()` 读的是 `Me.hash`，而站内点击走的是另一条路（直接改 section），于是 `Me.hash` 从未和地址栏同步。

```js
// 现在
function mn(){ let e = Ld(Me.hash); e && e !== t.value && (t.value = e); }

// 改成
function mn(){ let e = Ld(window.location.hash); e && e !== t.value && (t.value = e); }
```

并在挂载时**先读一次**再注册监听（顺序很重要，反了就会出现"刷新回首页"）：

```js
onMounted(() => {
  mn();                                   // ← 先按地址栏定位
  window.addEventListener('hashchange', mn);
  window.addEventListener('popstate', pn);
});
```

**验收（四种进入方式全过）**：

| 进入方式 | 判据 |
|---|---|
| 直接打开 `#/corridor/profile` | 10 s 内二级 tab 激活「走廊剖面」，正文出现「这条走廊几点能飞」 |
| 刷新 `#/compare/counterfactual` | 刷新后仍在「复盘对照」，不落首页 |
| 站内切页 → 后退 | 回到上一页，不出站 |
| 加载后手动 `location.hash='#/dispatch/console'` | 3 s 内切到「事件处置台」 |

**谁改 / 多久**：前端 1 人 / 1 小时。

## 2. 批次二 · 档位对账（2 小时 40 分，四条 P1）

### F-3 判据区把「两档」都画出来

**问题**：34 / 53 条需谨慎走廊，四条判据全绿、结论却是需谨慎（N-5）。
**根因**：判据区只画停飞档，结论用的是「停飞 ∪ 谨慎」两档。

**做法（不加新功能，只是把已有常量画出来）**：每条判据多带一组"谨慎档"字段。

> **重要**：谨慎档的观测阈值**在后端**（前端打包产物里查不到 3000 这个常量）。
> 实测三条走廊能反推出能见度谨慎档在 **3000 m 附近**：1593.3 / 2800.3 / 2993.4 m 三条都判「需谨慎」，
> 而云底 5000 m、阵风 1–2 m/s 从未触发任何档。
> **所以不要让前端自己猜阈值，要让后端把"命中哪一档"显式传出来。** 否则改完还是两套口径。

```python
# 后端：_observation_criterion() 里把已有的档位判定一起外传
criterion = {
  "metric": "能见度", "value": 2800.3,
  "threshold": 1000.0,        # 停飞档
  "passed": True,             # 未达停飞档
  "watchThreshold": 3000.0,   # ← 用代码里已有的常量，不要新造
  "watchPassed": False,       # ← 已达谨慎档
  "hitTier": "WATCH",         # ← 新增：直接说命中哪一档（NONE / WATCH / BLOCK）
  "display": "2.8 km（停飞 <1.0 km · 谨慎 <3.0 km）",
}
```

前端每行显示两档，命中的那一档标出来：

```
能见度  2.8 km   （停飞 <1.0 km ✅ 未达 · 谨慎档 ⚠ 已达）  METAR ZYTX 实测
阵风    1 m/s    （停飞 >10 m/s ✅ 未达 · 谨慎档 ✅ 未达）
云底高  5000 m   （停飞 <300 m ✅ 未达 · 谨慎档 ✅ 未达）
概率档  20.2%    （停飞 ≥25% ✅ 未达 · 谨慎 ≥15% ⚠ 已达）
→ 结论：需谨慎（命中：能见度谨慎档 + 概率谨慎档）
```

**（上表里阵风/云底的谨慎档写"未达"，是因为这两项在 53 条走廊里从未触发过谨慎 —— 是否有这一档、阈值多少，以代码为准，界面按后端返回的 `hitTier` 渲染即可，不要硬编码。）**

解释句同时修：

```
现在：观测判据与概率档同时命中（概率 20.2%），两档结论一致
改成：观测能见度 2.8 km 已达谨慎档、未达停飞档；概率 20.2% 已达谨慎档（≥15%）、
     未达停飞档 —— 两档都指向「需谨慎」，因此判为「需谨慎」。
```

**验收（一条自动判据，可直接跑）**：

```python
# 对 53 条走廊逐条断言
for cid in corridors:
    d = get(f"/api/traffic/v2/corridor/{cid}?case=fog-20250105")
    if d["verdict"] != "可飞":
        assert any(c["passed"] is False or c.get("watchPassed") is False
                   for c in d["criteria"]), f"{cid} 结论非可飞但判据全绿"
```

**谁改 / 多久**：后端 30 分钟（补字段）+ 前端 1 小时（渲染两档）/ 合计 1.5 小时。

## 4. 队友侧：HistoryRetention 的验收判据（你修，我验）

这条属后端，不占前端工时。复测报告 §5 已记录根因，这里只给**验收**——因为这类"静默失效"最容易被自己的测试骗过去。

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | 3:30 清理不再报错 | 次日日志出现成功行，且带删除行数 |
| 2 | 数据不再只增不减 | 连跑 2 天后，H2 文件大小与 `/health.planStore.plans` 不单调增长 |
| 3 | 结构上能被测出 | 补 `@DataJpaTest` 用例：**无事务上下文**调用 `cleanup()`，断言不抛异常且返回行数 > 0 |
| 4 | 内存真降下来了（不只是不崩） | 派生 `deleteBy…` 是「select 全表 → 逐条 remove」，改成 `@Modifying @Query` 的 bulk delete；断言"删除行数 == 预置行数"，并检查 `clearAutomatically` 防止一级缓存脏读 |

**第 4 条是关键**：把 `@Transactional` 挪到能被代理的路径上，只是让它**不崩**；派生 delete 依然是**全表进堆再逐条删**。要根治内存，必须换 bulk。这两件事别当成一件。

## 5. 明确不做（本轮范围的边界）

| 不做的事 | 理由 |
|---|---|
| **U-2 导航重排 / 去 1-5 编号 / 二级改下划线** | 影响面覆盖全部导航回归判据（`navGroups.test.mjs` 逐条钉着名字与结构）。赛前动这个，等于把已跑通的东西拆了重装。收益是"更好看"，风险是"全站导航崩"。 |
| **演示模式 5 页轮播** | 仓库 2026-10-17 已刻意移除（与「信息密度」下拉做同一件事的两半，双入口会导致"我现在是哪一档取决于先进了哪个门"）。加回来 = 新增功能 + 复活一个已被判定为设计错误的东西。 |
| **新增「概率成因」事件类型** | 属新增事件分类（新功能）。本轮只让缺口可见（处置台的"本案例判据"隔离带已经做到了）。 |
| **信息密度改三段式** | 同 U-2，和导航一起做才有意义。 |

## 7. 答辩话术（按"现在能答 / 改完才答"分档）

### 现在就能答（已实测，可以背）

**Q：你的 AI 到底改变了什么？用 AI 和不用差多少？**

> 同一个案例、同一份计划、同一份气象快照，只换最后一层裁决规则：关掉 AI，**2614 架次**会飞进禁飞级走廊；开启 AI，**0 架次**。总改判 **3044 架次**（观测档 2640、概率档 404），代价是 2848 架次绕飞 + 8 架次延误、合计 320 分钟 —— 占计划总时长 0.1%。**这就是用 0.1% 的延误换掉全部风险暴露。**

**Q：概率 31% 你就停飞，是不是太保守？**

> 停飞判据是 25%，31.3% 确实越过了。但我们不是"一超就停"：先改时隙、再改航绕飞，两者都不可行才停止放行。这个案例里 2856 架次全部是绕飞和延误，**取消 0 架次**。

**Q：你们的阈值是怎么定的？会不会前后不一致？**

> 四个常量只有一份来源：`config/rules-v1.json`。停飞 0.25、谨慎 0.15、暴露 0.25、人工复核下限 0.65，前后端同源，界面上不另写一份 —— 上一版就是因为界面上另写了一份 0.8，才出来"AI 改判 0"这种自相矛盾。
