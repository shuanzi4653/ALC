## 二、报告唯一错的一条：1366 缩放

报告写：

> **1366×768 不再整站缩小**。上一版 `body zoom = 0.577`、最大字 11.5 px；这版 `zoom = 1`、无横向溢出，正文按原生尺寸显示。

实测（Edge headless，`--window-size=1366,768`，视口 1336×673）：

```
body zoom             : 1
.hstage transform     : matrix(0.502778, 0, 0, 0.502778, -1280, -540)
舞台内最小字号         : 9.5 px
横向溢出              : scrollWidth=1336 clientWidth=1336
```

**`body` 的 CSS `zoom` 恒为 1** —— 我们从来没用过 CSS `zoom`，整站缩放是 `.hstage` 上的 `transform: scale()`（`HomeStage.vue:305`，比例由 `runtime.js::stageBox` 算）。所以用 `getComputedStyle(document.body).zoom` 去判"有没有缩小"，**两个版本量出来都会是 1**，这个对比本身无效。

真实比例按 `stageBox` 算（高度固定 1080，比例 = min(容器宽/舞台宽, 容器高/1080)）：

| 容器 | 舞台宽 | scale |
|---|---|---|
| 1366×700 | 2108 | 0.648 |
| 1366×660 | 2235 | 0.611 |
| **1366×640** | 2305 | **0.593** |
| 1366×620 | 2379 | 0.574 |

实测 0.5028 说明容器高只有约 543 px（1366 宽屏下导航+内边距吃掉更多）。**结论：F-10（1366 字号）仍然是开着的**，而且比报告引用的 0.577 更小。这一条不能当"已修"记进任何对外材料。

## 三、P0-1 的根因与最小改法（比方案估的工时小得多）

方案说 2 小时、三层都要改。实测**只有第 1 层是缺的**：

| 层 | 方案判断 | 实际 |
|---|---|---|
| 第 1 层 后端接 minute | 要改 | ✅ 缺的就是它 |
| 第 2 层 前端传 minute | 要改 | ❌ **已经在传**（`SituationBrief.vue:48` 与 `OperationsConsole.vue:73` 的 URL 都带 `minute=`，上一轮 W-1 顺手做的） |
| 第 3 层 横幅标起点 | 二选一 | 独立文案，不属于这一条 |

缺口的准确位置是**两处**：

1. `traffic/v2.py:1013` —— `snapshot = corridors(limit=None, case_id=case_id)`
   漏传 `minute=minute`。上层 `field(case_id=case_id, minute=minute)` 已经拿到该帧观测，但汇总用的还是 T+00 的 53 条。
2. `traffic/v2.py:1251` —— `timeBase` 取 `traffic_cases.describe(case_id).get('timeBase')`（常量）。`snapshot['observation']['observedAt']` 在传了 minute 之后就是该帧时刻，改用它即可。

`conclusion` 里的 `31%` / `19 条` / `corridors.high/watch` / `kpiDetail.definitionPending` **全部是从 `items` 派生的**，所以只要第 1 处传对，它们会一起跟着变 —— 不需要另写一套聚合（方案第 1.2 节说的"别写第二套算法"是对的，我们本来就是一套，只是喂了错的帧）。

**估计工时：0.5–1 小时（含验证），不是 2 小时。**
