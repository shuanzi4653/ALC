### W-3 重做「待处置走廊」口径

**现状**

| 位置 | 值 |
|---|---|
| 首屏卡片 | 22 条（雾案例 53 条） |
| 口径表定义 | 观测判据命中（能见度<1000 / 阵风>阈值 / 云底<300） |
| 口径表分子 | "观测判据命中的走廊" |
| `kpiDetail.observations` | **0** |
| 53 条 `verdictObservation` | 53/53 可飞 |

22 的真实来源是 `p ≥ 0.15`（8 + 14），跟观测判据无关。

**改成什么**

1. 卡片改名：**「需复核走廊」**（比"待处置"准确，且不承诺"已处置"）
2. 口径定义改为：

> 观测判据命中 **或** 不可飞概率 ≥ 谨慎档阈值（当前 0.15）的载客走廊数。两者分别统计并给出并集，不合并成一句。

3. `kpiDetail` 增加结构化字段，前端直接展示三个数：

```json
"kpiDetail": {
  "pending": {
    "observations": 0,
    "probabilityWatch": 22,
    "union": 22,
    "watchThreshold": 0.15
  }
}
```

4. 口径表对应行同步改（定义 / 分子 / 分母 / 来源四处必须一致）

**验收**

- 卡片数值 == 口径表分子 == 点进去列表条数（三个数必须相等，可脚本断言）
- 雾案例：卡片数与口径表一致（当前 53 vs 18）
- 全站不再出现"待处置走廊（观测判据命中）"配一个非 0 的数

**工时**：1.0 h（后端 + 前端文案）

> **不要走捷径**：备选方案是"直接填 `observations`"，数字变 0，诚实但难看。只在你时间不够、且愿意接受"22 条变成 0 条"时用。推荐方案 A。

### W-4 走廊详情加「概率档」判据行

**现状**

```
判据（3 条）
能见度  ≥ 9.7 km（阈值 < 1000 m）   满足
阵风    8.23 m/s（阈值 > 10 m/s）   满足
云底高  5000 m（阈值 < 300 m）      满足
── 顶部：不可飞概率 37% · 不可飞 ──
```

三条全绿，结论不可飞，页面一个字没解释。

**改成什么**

1. 判据区标题改：**「观测判据（3 条）· 全部满足」**
2. 下面新增一行（仅在 `verdictSource == PROBABILITY` 时出现）：

```
概率档    不可飞概率 37%（阈值 ≥ 25%）   触发
          → 观测判据全部满足，由概率档改判为「不可飞」
          模型 v2 · σ≈0.15 · 最近站 ZYHB 18.1 km
```

3. 顶部结论旁加一个 chip：`概率档判定`（和"观测判定"区分开）
4. 若 `verdictObservation != verdict`，在判据区底部固定一句话：

> 本走廊的最终判定来自概率档，观测判据未命中二级阈值。两者的差异已记入分歧台账。

**验收**

- 任取一条 `verdict=不可飞 && verdictObservation=可飞` 的走廊：页面必须出现"概率档"字样，且能看到阈值 25%
- 三条"满足"与"不可飞"同屏时，中间必须有解释句（人工肉眼确认）
- 截图存档（`t16_corridor.png` 作为改造前对比）

**工时**：1.0 h（纯前端）

> 这是**性价比最高的一张**。1 小时，把"系统坏了"变成"系统在解释自己"。

### W-5 清掉 `undefined` 泄漏

**现状**

```
对象：undefined:WEATHER_BLOCKED:true
明细：已确认（事件 undefined:WEATHER_BLOCKED:true）
```

运行日志同样落这条。原因：拼接 `event.id` 时对象上没有该字段。

**改成什么**

1. 定位事件对象实际字段名（`eventId` / `eventKey` / `id`），三处引用统一
2. 回执、运行日志、CSV 导出**共用一个 formatter**：

```js
const s = (v) => (v === null || v === undefined || v === '' ? '—' : String(v));
```

3. 后端日志同样做空值兜底（不接受 `undefined` 字符串入库）

**验收**

- 点确认后：`document.body.innerText.includes('undefined') === false`
- 运行日志全文 grep `undefined` = 0
- 回执"对象"一栏显示真实事件 id（如 `WEATHER_BLOCKED:3-02:3-13`）

**工时**：0.5 h

### W-6 操作者身份刷新后仍生效

**现状**

- `localStorage['alc-operator'] = 'admin'`，设置面板下拉显示"管理员"
- 点确认后落账 **人物：absent**
- 同一次会话用 `fetch` 打 `weather/mode`，后端回"你当前是「观察员」"

角色值只在"当场改下拉"时写进请求头，刷新后失效。

**改成什么**

1. 应用启动时：`operator = localStorage.getItem('alc-operator') || 'observer'`，写进响应式变量（当前初值为空）
2. 统一请求拦截器：所有写请求注入 `X-ALC-Operator`
3. 后端：写操作缺 `X-ALC-Operator` 时**拒绝**（401/403），不要静默记成 `absent`

**验收**

- 刷新后直接点"确认"，落账人物 = 当前角色（admin/duty）
- 清空 localStorage 再点，后端回 403 并提示"请先在设置里选择角色"（而不是记 `absent`）
- 台账里不再出现 `人物：absent`

**工时**：0.5 h

### W-10 结论句措辞

**现状**

> 未来 3 小时内，长春 ↔ 哈尔滨（CAR-2-01-3-01）不可飞概率 37%，8 条走廊**处于禁飞级**

37% 与"禁飞级"并置，两种读法都不利。

**改成什么**

> 未来 3 小时内，长春 ↔ 哈尔滨（CAR-2-01-3-01）不可飞概率最高（37%）；**8 条走廊已触发停飞判据**，建议先处置 CAR-2-01-3-01。

规则（全站统一，写进文案规范）：

| 词 | 只用于 |
|---|---|
| 禁飞级 | `p ≥ 0.8` 或观测命中禁飞阈值 |
| 触发停飞判据 | `p ≥ 0.25` 复合口径 |
| 需谨慎 | `p ≥ 0.15` |

**验收**

- 结论句里"禁飞级"与小于 80% 的概率不再同句
- 全文三个词与三个阈值一一对应

**工时**：0.5 h

## 2. 批次二「立信」4 小时

**目标：让"用 AI 和不用，差多少"有一个非零的答案。**

这是唯一会改变结论口径的一批。改完"关掉 AI / 开启 AI"必须真的不一样。

### W-1 阈值收敛到单一来源

**现状**

| 用途 | 阈值 | 出处 |
|---|---|---|
| 走廊判不可飞 | 0.25 | `kpiDetail.probabilityThreshold` / `P_PROB_BLOCK` |
| 走廊判需谨慎 | 0.15 | `kpiDetail.probabilityWatchThreshold` / `P_PROB_WATCH` |
| 反事实暴露与改判 | **0.80** | `counterfactual.note`（硬编码，0.11.3 起） |

53 条里 `p ≥ 0.8` 的是 **0 条**（最高 0.3701），所以反事实永远算出 0。

**改成什么**

1. `config/rules-v1.json` 增加一段作为唯一真源：

```json
"probability": {
  "block": 0.25,
  "watch": 0.15,
  "exposure": 0.25,
  "humanReviewBelow": 0.65,
  "source": "config/rules-v1.json::probability"
}
```

2. 后端三处读同一常量，**删掉 0.80 这个字面量**：
   - 走廊判定（现在就是 0.25，确认走配置）
   - `counterfactual.a/b.exposure` 判据：`p >= probability.exposure`
   - `delta.diverged` 统计口径同上
3. `counterfactual.note` 文案同步改：

> 「暴露」的判据 = 走廊概率 ≥ 概率档阈值（当前 0.25，与走廊判定同源）**或** 走廊中点最近站观测已达禁飞级。

4. 前端所有阈值展示只读 `kpiDetail`，禁止硬编码（0.11.16 已做到，保持）

**验收**

- 同一快照：`counterfactual.a.exposure` 与"落在 verdict=不可飞 走廊上的班次数"量级一致（当前 64/1006 抽样 ≈ 494 全量）
- `delta.diverged > 0`
- 全仓 grep：`0.8` / `80%` 不再出现在暴露判据附近

**风险（必须读）**

改成 0.25 后"暴露"数会从 626 跳很大（可能 1500+）。**这不是 bug，是之前被 0.8 藏住的真实暴露量。** 要在复盘页把这句话写清：

> 此前按 0.8 口径统计，导致暴露量被低估；自 0.11.17 起与走廊判定同源。

**工时**：2.0 h

### W-2 概率档判定传导到班次与改判台账

**现状**

走廊层判了 8 条"不可飞"，处置层一条没动：

- 8 条不可飞走廊上的抽样班次 **64 班**（折算全量约 494 班）
- 其中 CLOSED 11 班，气象原因仅 3 班
- `delta.diverged = 0`，复盘页写"没有任何一班被判为必须改航或取消"

**改成什么**

对 `verdict == 不可飞` 且 `verdictSource == PROBABILITY` 的走廊，把走廊结论**逐班下发**：

1. 未起飞班次（`departureMinute > 推演时刻`）→ 生成 `PROBABILITY_REVIEW` 决策，进入 `counterfactual.b`：
   - `confidence >= 0.65` → 按 policy 处置（均衡档：转人工复核；保守档：停止放行）
   - `confidence < 0.65` → 留痕不改判（这个分支已有，保留）
2. 已起飞班次 → 不改判，但计入 `exposure`
3. 台账写入一条 `source=PROBABILITY` 的裁决记录，带走廊号、p、σ、规则档、生效档

**验收**

- `delta.diverged >= 1`，且 `divergedProbability > 0`
- 处置台出现"概率成因"事件（当前只有"气象成因 / 非气象成因"两类）
- 复盘页"改判明细"能筛出这 8 条走廊的班次（当前 20 条全是低概率留痕，看不到主线）
- 台账非空，每条带 `依据=概率档 ≥0.25`

**自查**：`a.exposure - b.exposure` 与 `diverged` 的数量级要对得上。对不上说明传导只做了一半。

**工时**：2.0 h

## 7. 答辩话术（10 问预演）

这一节按"现在能不能答"分三档。**评委问 3 个问题，2 个答不上来就降档。**

### 现在就能答的 5 个

**Q1 这个系统给谁用？**

> 给省级低空运行控制中心的值班员。东北三省 33 个城市、每天 7760 个班次（飞行汽车 848、无人机配送 6912），他们要在起飞前判断哪些走廊能飞。我们做的是"走廊级的气象风险判据 + 人工复核闸门"，不是替代空管——页脚写着"不构成飞行许可结论"，这条边界我们很在意。

> 改完 U-1 之后，这句话会直接印在首屏标题下面，你不用背。

**Q2 37% 的概率，你凭什么判不可飞？**

> 我们把概率分两档：≥25% 进"停飞判据"，≥80% 才叫"禁飞级"。25% 这一档的处置动作不是直接取消，而是**转人工复核**——页面上三个按钮（采纳 / 否决 / 转人工）就是给人用的，否决和回滚必须填理由，会进分歧台账。
> 之所以定在 25%，是因为我们只有 3 个机场站，走廊远端最近站距 18 km，插值不确定度 σ≈0.15，宁可让系统多说一句"你看看"，也不要漏掉。

**Q8 模型准确率多少？63% 的误报率还敢用？**

> 低能见度禁飞级的 POD 0.465、FAR 0.636。误报率高是因为只有 3 站 METAR，空间插值本身有上限——这个我们在模型卡里主动写出来了。
> 关键是**误报的后果不是停飞**：0.25 这一档触发的是人工复核，人看到 9.7 km 能见度 + 8 m/s 阵风会直接放行，一行否决就过去了。漏报的后果才是事故。所以阈值选的是保守点，不是最优 F1 点。
> （改完 W-13 之后，这里可以加一句"0.25 处精确率 __%、召回率 __%"。）

**Q10 换个天气会怎么样？验证过吗？**

> 有两条验证路径：一是历史回放（`?case=fog-20250105`，2025-01-05 的雾案例），二是消融开关（`?ablate=obs|prob|loss`，分别关掉观测项、概率项、损失项）。回放页明确标了"回放不重跑调度、无处置数字"，不拿实时数字冒充历史。

**Q11 你们和现有空管系统什么关系？**

> 上游。我们输出的是"这条走廊现在该不该飞"的建议 + 可追溯的理由，进的是运行控制中心的复核流程。页面上每一个数字都能点进去看到来源接口，口径总账里连"分母 53、阈值 0.25、数据源 /v2/corridors"都写出来了。我们不接管放行权。

### 改完才答得了的 4 个

**Q3 用 AI 和不用，到底差多少？（最致命的一问）**

**Q4 待处置 22 条是怎么算的？**

## 9. 不建议做的事

做技术方案容易贪，这一节比前面所有工单都重要。

### 1. 不要重组信息架构（5 步并成 3 区）

收益是"不再乱"，代价是全站导航回归测试。赛前一周做这个，最大的风险不是做不好，是**做完没时间验证**。留到赛后。

### 2. 不要加新功能

3D 地图、AI 对话、更多图层、更多指标——这些都不会让评委加分，但每一个都会引入新的口径，新的口径就会带来新的自相矛盾。**你现在的问题不是功能不够，是已有的功能互相不对账。**

### 3. 不要改成滚动长页

单屏不滚动 + 地图优先，在投屏演示场景下是对的。改成滚动页会失去"一眼看到全景"的优势。

### 4. 不要把阈值调回 0.8（这是最危险的"假修复"）

把 `exposure` 改回 0.8，矛盾确实消失了——但等于把 AI 从决策链里摘出去，`verdictSource=PROBABILITY` 会退回"不参与"，K-3 从"已修"退回"未修"。**这是用自欺换自洽，评委会问"那你的 AI 到底改了什么"，你答不出来。**

正确方向是反的：把 0.8 降到 0.25，让 AI 真的改判。

### 5. 不要在没有 U-5 的情况下现场演示"跳来跳去"

13 个页面没有地址，后退会跳出站点。**答辩时千万不要按浏览器后退按钮**，只用页面内的导航。如果要做 U-5，优先做。

### 6. 不要在答辩材料里放"AI 改判 0"那一页

如果 W-1/W-2 没做完，复盘对照页是你最该避开的页面。被问到就看口径总账（那页做得好），不要主动点复盘。

### 7. 不要试图解释 `undefined`

改掉它只要 0.5 小时。解释它要 5 分钟，而且解释不清。
