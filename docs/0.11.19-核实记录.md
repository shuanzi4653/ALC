## 二、唯一一处报告算错：P1-3「28 vs 34」

报告说「34 条需谨慎里有 6 条不在 28 条需复核里」（34 − 28 = 6）。**实际是 25 条，不是 6 条。**

实测（`/api/traffic/v2/corridors?limit=53&case=fog-20250105`）：

```
走廊总数              53
观测不可飞（verdictObservation）  18
概率 ≥ 0.15           28
概率 ≥ 0.25           12
两者并集（= pending）  28      ← 18 条观测不可飞全部落在"概率≥0.15"里，所以并集恰等于 28
结论「需谨慎」         34      ← 其中 25 条概率 < 0.15（只靠观测谨慎档进的谨慎）
```

实现是对的（`v2.py:1052-1056` 明确算 `obs ∪ watch`，注释还写了"不能再用 `len(high)+len(watch)` 代替"）。问题在于**两个数是两套口径**：

- `pending=28`：观测不可飞 **∪** 概率≥0.15
- `34`：结论="需谨慎"的条数（含 25 条只靠观测谨慎档的）

两者**没有包含关系**，差值不是 6 而是"25 条在 34 里、不在 28 里；18 条在 28 里、不在 34 里"。

**结论：这条不是数字错误，是口径未标注。** 方案 W-5 的选项 A（KPI 下加一行「按概率档 ≥15% 计；另有 25 条仅观测判据命中谨慎档」）是正解，但**小字里的数字要写 25，不是 6**。

## 三、两条需要知道的背景

### 1. P0-1 不是本版引入的

拿改动前的备份对照：

```
backups/0.11.18-pre-scan-20261025/backend-python/traffic/v2.py:679
    def corridor(route_id: str, case_id: Optional[str] = None)
```

**与当前完全一致**——`minute` 从来没进过走廊端点。这条脱钩是 0.11.1x 就有的结构性问题，只是本版把别的修好了，它才显出来。

所以「上一版刚修好的可信又被撕开」这个说法要修正：**它一直在，只是现在旁边有了对照物**（气象页会随时间变）。

### 2. 方案 W-1 的第三层可能比预估重

方案的改法写的是「`frame = resolve_frame(case, minute, ws)`，复用天气端点里已有的取帧函数」。核实到的实情：

- 天气端点确实有取帧逻辑（`minute` 生效，实测 997.8 → 2993.4）
- 但走廊的判定链是 `corridors()` → `corridor()` → `_criteria(field_payload, centre)`，其中 `field_payload` 来自 `field(case_id=...)`——**一次性取整个案例的观测，与 minute 无关**
- 要让走廊跟时间走，得让 `field()` / `_nearest_observation_level()` 接受时刻，并把该时刻的帧观测传进 `_criteria`

**这不是"加一个参数"，是改观测取数的入口。** 2.5 小时的估算里，后端 1.5 小时偏乐观，建议按 2–2.5 小时算后端，或者分两步：先让 `observedAt` 跟 minute 变（可验证的最小改动），再让判据跟。
