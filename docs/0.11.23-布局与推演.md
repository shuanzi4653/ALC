## 一、D-1：点「查看航班」→ 地图报错

### 现象（复现于线上 0.11.22）

处置台任一事件卡点「查看航班」：

```
CONSOLE TypeError: Cannot read properties of undefined (reading 'length')
地图 canvas: 0
地图错误条: 无法创建三维城市地图：Invalid type: 'container' must be a String or HTMLElement.
右栏选中: （没选中）
```

### 根因：`?.` 只保护一层

0.11.11（G-6）为减包把 `points` 从 `flights`（表格用的 slim 列表）挪到了 `mapFlights`
（每班 6 点），全量轨迹改成单班补取（`ensureFullFlight`，一次往返）。

于是"刚点选、补取还没回来"这一帧里 `selected.points` 是 `undefined`，而下有五处写的是
`selected?.points.length` —— **`?.` 只保护 `selected` 本身，不保护 `.points`**：

| 位置 | 写法 |
|---|---|
| `TrafficWorkbench.vue:152` | `location` computed |
| `TrafficWorkbench.vue:161` | `locateDelivery()`（副作用：这个按钮一直静默失效） |
| `CityTrafficMap.vue:908` | `follow()` |
| `CityTrafficMap.vue:1402` | `minute` 的 watch |
| `CityTrafficMap.vue` 模板 | `:disabled="!selected?.points.length"` |

抛 TypeError 之后**整棵组件树渲染中断**，地图容器的 `ref` 根本没挂上 ——
MapLibre 拿到 `undefined` 当容器，于是报 `container must be a String or HTMLElement`。
**地图那句报错是结果，不是原因。**

### 修法

1. `runtime.js` 新增纯函数，取轨迹统一走它，**永远返回数组**：

```js
export function trajectoryOf(flight){
  const points=flight&&flight.points
  return Array.isArray(points)?points:[]
}
```

2. `selected` 加兜底链：**全量轨迹 → 地图行（6 点）→ 空数组**。
   中间那层让"刚点选"这一帧地图上仍有线可画；最后一层保证调用方判 `.length` 不会抛。
3. 五处 `?.points.length` 全部换成 `trajectoryOf(...).length`。
4. `locateDelivery()` 改从 `mapFlights` 取轨迹 —— 原来那句既会抛错，
   即使不抛也永远筛不出一班（`flights` 里没有 `points`），「定位配送航班」一直是死的。

### 判据（改后实测）

| 项 | 值 |
|---|---|
| 点击后 console 异常 / error | **0** |
| 地图 canvas | **1** |
| 地图错误条 | 无 |
| 右栏选中 | 长春 · 长春商家节点1 |

新增 `frontend/tests/trajectory.test.mjs`（4 条）：
`trajectoryOf` 的形状约束 + 两个 `.vue` 源码里不许再出现裸的 `xxx.points.length`
（剥注释后扫，带 `Array.isArray` 短路的写法放行）。

## 二、L-1：导航整体搬到左侧

### 结构

```
main.traffic-workbench
├── header.wb-top        顶栏 47 px：天窗智巡 · 副名 · 当前区域 · 时间基准 · 雷达 · 收起导航
└── div.wb-shell         左栏 176 px ＋ 内容区（1 行 flex）
    ├── nav.operations-nav   五组 ＋ 子视图 ＋ 区域下拉 ＋ 投影/演示/设置（沉底）
    └── div.wb-body          原内容，自己滚（不再是整页滚）
```

原来这一条要装：品牌、五组、子视图、区域、时间基准、投影、演示、设置 ——
1680 宽刚好，1366 就要折行，折完从 56 px 涨到 96 px，涨出来的高度压的正是地图。
现在顶栏只报"这是什么"，其余竖向排。

**判据钩子一个没动**：`data-nav-groups` / `data-group` / `data-section` / `data-entry-tab` /
`data-time-basis` / `data-projection-toggle` / `data-settings-toggle` / `data-radar-relay`
全部保留 —— 测试、探针、命令面板都靠它们找元素，改布局不该改这些。

### 折叠（为 1366）

左栏占 176 px 是实打实的宽度损失，所以给一个「收起导航」：
收起后 56 px，只留 ①–⑤ 的编号（`title` 仍在），偏好存 `localStorage`。
`≤1000 px` 视口自动收起。

| 状态 | 左栏 | 地图宽（1680 视口） |
|---|---|---|
| 展开 | 176 | **1124** |
| 收起 | 56 | **1244** |

横向溢出：`doc 1650/1650` —— 没有。

### 踩到的坑（值得记）

第一次改完，屏幕上是 **地图 350 px、三个面板并排**。原因不是 CSS，
是**插错了嵌套**：`<header>` 和 `.wb-shell` 是插在"原 `<nav>` 的位置"，
而 `<nav>` 在模板里排在工具栏**之后**，于是 `.wb-body` 把 header 和 shell 一起包了进去，
`wb-shell` 又成了 row flex 容器，`traffic-main / DispatchBoard / playback` 就并排了。

诊断只用了三行计算样式：

```
wb-body 子元素: ["traffic-toolbar","wb-top","wb-shell"]   ← 一眼看出
body 计算样式: flex / column / w=1650
traffic-main 样式: grid / 422.234px 300px
```

**教训**：改嵌套后要打印"某个容器的直接子元素"，而不是看截图猜。
截图告诉我"三栏"，DOM 才告诉我"为什么是三栏"。

## 三、S-1：推演改成一步一步走

### 为什么改

原来七块一次铺满。问题不在信息量，在**读者没有顺序**：七块同时可读，
等于没有一块是"下一步的依据"。而这一页要证明的恰恰是"结论是一条链推出来的"。

### 现在的形态

- 顶部步骤条七个：**数据 · 插值 · 概率 · 判据 · 裁决 · 对照 · 七帧**，
  走过的打勾、当前加亮、未到压暗，可点回任意一步。
- 默认只展开第 1 步；「下一步」推进；走到底变「展开全部」。
- **走过的步骤折成一行结论**（折的是状态，不是内容，随时能点回去）：

| 步 | 折叠后那一行 |
|---|---|
| 1 | 4 站读数，最低能见度 998 m |
| 2 | 最近站 4.7 km，最高权重 96.4% |
| 3 | 不可飞概率 31%（最差采样点） |
| 4 | 1 条命中，结论 不可飞 |
| 5 | 选中 绕飞，损失 539 |
| 6 | 规则与 AI 一致：不可飞 |
| 7 | 7% – 31%：雾在散 |

- 每步都有 **本步输入 → 本步输出** 两栏（`ded-io`）。这是"把数据写出来"的落点：

```
第 1 步  输入：4 站 METAR 实测，观测 01-05 01:00Z
         输出：每站的能见度与档位 —— 走廊本身还没有结论
第 3 步  输入：p_vis 0.156 · p_gust 0.000
         输出：p = 1−(1−p₁)(1−p₂) = 0.156；沿走廊取最差段 31%
第 5 步  输入：31% + 四个门限（事故 10000 · 绕飞 25 · 取消 180 · 延误 1）
         输出：选中 绕飞，期望损失 539
```

- **换走廊 / 拖时间轴 = 重新推演一遍**，一律回到第 1 步。
  停在原来的第 5 步，读者会以为那是新走廊的结论 —— 这种错不报错、不红测试。

### 第 1 步：从"画条形图"改成"摊一张表"

`observation.stations` 与 `deduction.stations` 讲的是同一批站，但**字段各占一半**：
距离与权重只在后者上。只读一份，表里就有一列永远是「—」（看着像数据缺失，
其实是读错了来源）。按站号合并后：站号 / 距走廊中点 / 能见度（带迷你条）/ 阵风 / 云底 / 档位。

### 第 2 步：三次试错，最后改成"距离轴"不是地图

这条走廊 62.9 km，三个加权站分别在 **44.7 / 321.5 / 338.2 km** 外。

| 试法 | 结果 |
|---|---|
| ① 只画权重 ≥5% 的站 | 只剩 1 站（96.4 / 1.9 / 1.7），"三站加权"看不出 |
| ② 三站全画（真实经纬度） | 338 km 的站把走廊压成二十几像素，读者以为走廊没画 |
| ③ 按"走廊至少 110 px"裁 | 又只剩 1 站 —— 换了算法，同一个毛病 |
| ④ **距离轴**（采用） | 横轴按权重排序、间距均分；**纵轴是真实距离**，每 100 km 一格；连线粗细＝权重 |

①②③ 的共同毛病是**图省事但把数据藏了**。④ 把数字全留着，只在图的说明里写清
"横轴不是方位"——数字是真的，取景是可读的。
