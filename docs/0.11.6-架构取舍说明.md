# 为什么我们不用 Kafka，也不整包引若依

> 这一页回答一个一定会被问的问题：**"你们这套系统，为什么不上消息队列 / 不上现成的后台框架？"**
> 答案不是"我们不会"，是"**在我们的规模与时间坐标里，它们不解决我们的问题，还会带来新的问题**"。

---

## 一、Kafka：我们缺的不是"解耦"，是"别在一个请求里组装 7.5 MB"

### 我们实测到的瓶颈

| 现象 | 实测值（2026-10-21） |
|---|---|
| `GET /traffic/session`（slim） | **11.8 s / 7.5 MB** |
| 同上（full） | **42.0 s / 25.3 MB** |
| 首字节时间（ttfb） | 仅 1.3–4.0 s |

**ttfb 只有几秒，总时长几乎全在"服务端组装 + 序列化 + 传输"**。而这三段里，**没有任何一段是"两个服务之间需要异步通知"**。

Kafka 解决的是"生产者与消费者彼此不知道对方"的问题——订单服务发一条消息，库存服务、风控服务各取所需。**我们的问题是"一个用户要一份 7760 条的计划"，它是同步的、点对点的、单消费者。**

### 如果硬上 Kafka，会发生什么

```
浏览器 → Java → 发一条"生成计划"消息 → 立刻返回"已受理"
                                        ↓
                              Python 消费、构建 40 秒
                                        ↓
                              结果写回某个地方 → 浏览器轮询
```

**这不叫异步化，这叫把"一个 11.8 秒的请求"改成"11.8 秒 + 一次消息往返 + 一次轮询"。** 而我们已经有了轮询（`BUILDING` → `READY`），只是那一次 `READY` 响应偏重。

### 我们实际做的（同一次迭代里）

| 手段 | 效果 |
|---|---|
| 分层字段（`fields=slim`，白名单 20 字段 + 航迹抽稀到 8 点，首末必保） | 25.3 MB → **7.15 MB（−70%）** |
| **预序列化 + ETag** | 重复请求 11.8 s → **0.48 s / 0 B**（304） |
| 下一步：分页（7760 → 100 条） | 目标 < 300 KB |

**三件加起来是 1 万元以内的工程量，Kafka 是零 —— 因为它一秒都省不下来。**

### 什么时候我们真的该上 Kafka

写在这里，是为了说明这不是"永远不上"：

- 当**多个下游要同一份计划**（比如同时喂给调度器、可视化、离线评估三套消费者）；
- 当**构建任务需要横向扩展到多台机器**（单机 Python 进程扛不住时）；
- 当**需要重放历史事件**来复现某次事故。

**现在一条都不满足。**

## 二、若依（RuoYi）：它值钱的是那三个"形状"，不是那 200 个文件

### 它会带进来什么

| 会带进来 | 我们的现状 | 后果 |
|---|---|---|
| 登录态 + Session/JWT | **2026-10-14 已拆除登录门**，靠匿名工作区（`X-ALC-Workspace`）隔离 | 现场第一次点"否决"就跳 401 / 登录页 —— **致命** |
| RBAC + 菜单 + 权限表 | 没有账号体系 | 要么造 40 个测试账号，要么写一堆 `permitAll` 把权限层架空（**架空之后它就是纯负担**） |
| 数据库表迁移 | 计划存文件（`traffic.store`），无业务库 | 为一个演示系统引入 Flyway + 表结构，回滚成本陡增 |
| 前端脚手架（Vue2 + Element UI） | Vue 3 + 自绘组件，已经有 16 个视图 | **等于重写整个前端** |

### 我们实际需要的"三个形状"，各 1 小时就能自己写

| 若依里的东西 | 我们缺的部分 | 我们的做法 | 工时 |
|---|---|---|---|
| `/monitor/server` 健康监控 | `/healthz` 只是 nginx 的 `return 200 "ok\n"`，后端全挂也说 ok | `GET /health` 结构化健康（逐项列出 planStore / weather / llm，区分 `ok/degraded/down`） | 1.5 h |
| 操作日志 | 否决记录有，但没有统一 `actor/role/requestId` | `journal` 字段只增不改地追加审计列 + `X-Request-Id` 贯穿三层 | 3 h |
| 分页表格 | 无（7760 条一次下发） | `/traffic/flights?page=&size=` + 前端分页 | 4 h |

**抄形状 8 小时；搬文件 3 周，且演示当天 401。**

## 三、我们这次补的到底是什么

方案里叫"工程化补强"，说白了是**把"能跑"补成"能被人运维、能被人追问"**：

| 维度 | 补强前 | 补强后 |
|---|---|---|
| 健康 | `/healthz` 恒回 `ok` | `/health` 逐项检查，down 才 503 |
| 指标 | 无 | `/metrics`（Prometheus 文本）：运行时长、session 请求数、预序列化命中、各通道取帧数 |
| 追踪 | 无 | `X-Request-Id` 贯穿 nginx → Java → Python，日志可串 |
| 载荷 | 25.3 MB / 42 s | 7.15 MB / 11.8 s；**重复请求 304 / 0 B / 0.48 s** |
| 审计 | 只有"谁否决了" | 追加 `actor / role / requestId`，且**只增不改**旧字段 |
| 文档 | 无 | 这一页 + 三份核实结论 |

---

## 四、一句话总结

> **我们不上中间件，是因为我们缺的是"中间件想给你的那个结果"，不是中间件本身。**
>
> 结果可以自己写，8 小时；中间件搬进来，3 周，还会在演示当天变成 401。
>
> **而 13.7 秒的响应时间，Kafka 一秒都省不下来 —— 能省下它的是预序列化与分页。**
