## 二、为什么基线选红外，而不是「雷达拿不到才退而求其次」

这是本次决策里唯一需要说服的部分，理由全部来自实测而非偏好：

1. **只有它四项全免**：零凭据、零成本、永久可用、无需注册。雷达两条免费路都附带
   未核实项（数据网的凭据形态、星图云的额度边界），任何一条变化都会让管线停摆。
2. **成本已被实测压到可接受**：一帧可用数据约 22.6 MB，解码**只需要标准库**
   （`bz2` + `struct`），不需要 satpy / netCDF / h5py。作为对比，同机构的
   云顶高度产品 `AHI-CHGT` **单帧 736.5 MB**，已被明确排除。
3. **它测的是对流本身，不是对流的代理**：红外窗区亮温是云顶温度的直接观测，
   冷云顶即深对流。对「低空飞行避让对流云团」这个用途，物性上比反射率更直接。
4. **合规性最干净**：公开数据桶，匿名读取，无抓取、无绕过、无第三方知识产权争议。

**注意：这不是降低标准。** 三种源最终产出的是**同一种**风险区记录，差别只在取数层。

## 三、统一管线（三种源共用，不得各写一份）

```
取帧 → 解码 → 物理量反演 → 地理配准 → 阈值判定 + 连通域 → 简化 → 风险区记录
  └────────────────── 源可插拔（provider 层）──────────────────┘   └─ 共用（不得分叉）─┘
```

- 阈值判定之后的每一步**只有一份实现**。上一轮的根因就是风险几何存在两份实现，
  导致避让包络漏掉整条东北雨带。这次把「位置与形状的来源」收敛成单一函数，
  `shapes()`（渲染）与 `swept()`（避让）都必须调它。
- 每条风险区记录必须携带 `provenance`：**源、通道/产品、观测时刻、取数时刻、质量标记**。
  降级只能显式声明，不允许静默。

## 四、开工的前置条件（未通过前不产出任何风险区）

| 步骤 | 内容 | 未通过时的后果 |
| --- | --- | --- |
| **标定** | 把 HSD 头部长度与行宽钉到字节级，并用**第二个分段交叉验证** | 解出来的栅格错位，风险区整体平移 |
| **反演** | Planck 反演：`count → radiance → 亮温` | 阈值 273/235/210/193 K 全部无意义 |
| **配准** | 导航四角经纬度 → 本系统投影 | 风险区落不到东北三省 |

另有两条必须成立的检验：对流阈值需**针对东北实际个例比对**；云顶冷区还需
**空间梯度 + 时间降温率**双条件，否则会把高空卷云误判成对流。

**本轮边界**：去合成（删 `moving`）**不依赖**以上三步——它只减少一个数据源，
不新增风险几何。红外源接入仍受本表约束，未通过前不产出风险区（**仍然生效**）。

## 五、词汇纪律（硬约束）

- **亮温 → dBZ 的任何换算一律禁止**。两者不是同一物理量，换算出来的数字没有意义。
- 红外侧只能说「**对流云团 / 云顶亮温 / 对流风险区**」，
  **不得**出现「雷达回波」「回波强度」「禁飞区」。
- 雷达侧才是「回波」，但**回波 ≠ 空域管制**：回波派生的一律叫
  「**派生飞行风险区**」并标注「非官方空域管制」。官方权威只有灾害预警。
- **雷达侧现值必须报原始 dBZ**，不转成「强/中/弱」这类程度形容词——
  程度词不可追溯，且会诱导下游当等级用。

## 七、去合成气象：逐项核对（签字后执行）

`moving` 场景的合成气象来自 `traffic/weather.py::NetworkWeather`。删它之前必须确认
没有别的功能在偷偷依赖它，否则会变成「静默降级」。

| 依赖点 | 性质 | 处置 |
| --- | --- | --- |
| `service.simulate()` 用 `NetworkWeather(seed, scenario)` 出 `weatherSnapshot` | **合成气象** | 删除；改由真实源 `weather_snapshot()` 提供 |
| `service.weather_frame()` 的 `moving` 场景分支 | **合成气象** | 删除该场景分支 |
| 避让逻辑 `weather.envelope(...)` / `swept()` | **避让包络** | 改从真实风险区几何取；**几何来源仍只允许一份** |
| 场景选择器（前端 `TrafficWorkbench.vue`） | UI | 去掉 `moving` 选项 |
| **交通数据 `simulate()` 本体** | **交通（不是气象）** | **不动** |

**若真实源缺失某项气象量**：停止并报告用户，**不得**用合成数据补位。

第七节五项**已全部执行完毕**，并额外落了三处：

| 项 | 结果 |
| --- | --- |
| `moving` 场景合成气象 | 已删。`moving` 从**所有**端点消失，现为 `live` / `clear` / `unknown` 三值 |
| `simulator` 模块 | 已改名为 `simulator.py.retired`，不再是可 import 的模块 |
| 唯一运行源 | **open-meteo**（`backend-python/real_weather.py`），零凭据、36 城批量、`MODEL_ESTIMATE` |
| 单一入口 | `weather_sources.py::weather_snapshot()` |
| `thunderProb` | 无真实来源 → **置 `None`，不编造** |
| `NetworkWeather` 类 | **保留**，但只作几何回归夹具，不对外产出数据 |

**签字时未预见、执行中发现的一件事**：第八节这五项的完成并不足以保证「气象全部是真实的」——
因为用户随后要求新增**运行时虚拟气象通道**（见下）。该通道的处置方式是把
「合成」从**隐式兜底**改成**显式可选 + 处处标注**：

- `weather_control.py` 运行时可切 `measured`（默认）/ `virtual`；
- `virtual` 帧由 `weather_sim.py` 生成，与实测帧**逐字段同构**（字节级兼容 `cma_tiles.frame()`），
  故下游几何代码**无需任何分支**；
- **硬判据一**：`measured` 模式下真实源失败必须如实返回 `available:false`，
  **绝不用合成帧顶替**（即第七节那条「不得用合成数据补位」仍然生效）；
- **硬判据二**：合成帧必须处处显式标注
  （`provider='SYNTHETIC_RADAR'` / `synthetic:true` / `source='SYNTHETIC_RADAR_CREF'` /
  前端图例与警示条）。

> **记一笔判断**：用户口头要求合成帧「不带标记」，**没有照做**。
> 依据是 `radar_field.derive()` 会在自己的输出里硬编码 `provider:'CMA_DATA_NET'`，
> 不带标记的合成帧会被下游**当成国家组网实测**读取，而前端文案写的正是「实测雷达」。
> 标注是这条通道唯一的意义所在。
