## 1. 你队友补报的两个 bug（本报告最重要的部分）

### 1.1 BUG-A：T+2 之后地图上没有飞机 —— 成立

**现象复现**：在首页拖时间轴，逐档数地图上的载具：

| 推演时刻 | 地图上可见载具 | 右侧面板"在空" |
|---|---|---|
| T+00:00 | 9 | — |
| T+00:30 | 25 | — |
| T+01:00 | 13 | 41 |
| T+01:30 | 8 | — |
| **T+02:00** | **0** | **51** |
| T+02:30 | 0 | — |
| T+03:20 | 0 | — |
| T+05:00 | 0 | — |
| T+07:50 | 0 | — |

**T+02:00 那一屏的矛盾最刺眼**：右侧「运行序列」明明写着"在空 51 架 · 未起飞 549 · 已到达 255 · 已关闭 346"，地图上一架都画不出来。

**根因（数据层，铁证）**：

| 数据源 | 条数 | 起飞时间范围 | 到达时间范围 | 该数据覆盖的在空时段 |
|---|---|---|---|---|
| `mapFlights`（**地图唯一数据源**） | 600 | T+0 ~ **T+47** | T+3.9 ~ **T+127.3** | T+0 到 T+127，之后为 0 |
| `flights`（列表 / 右侧面板） | 1201 | T+0 ~ T+438 | T+3.9 ~ T+479.8 | 全程 50–113 架 |

逐 30 分钟统计"在空架数"：

```
mapFlights（地图）      flights（列表）
T+  0    24            T+  0    24
T+ 30   147            T+ 30    88
T+ 60    36            T+ 60    41
T+ 90    17            T+ 90   108
T+120     1            T+120    51
T+150     0            T+150   109
T+180     0            T+180    49
T+210     0            T+210   109
...                    T+450    62
T+480     0            T+480     0
```

**为什么只到 127 分钟**：`mapFlights` 是"按起飞时间流式取前 600 条"。航班按起飞时间排好序，前 600 条自然就是最早起飞的那一批，全部落在头两小时。时间轴开到 480 分钟，后 353 分钟是空的。

**这是 0.11.13 第 5 项优化（首屏 1.2 MB → 896 KB）的副作用**：为了瘦身加了 `mapFlights`，取数时只切了"前 600 条"，没做"按时间分层抽样"。

**修复方向**：把 `mapFlights` 的取样方式从"前 600 条"改成"每 30 分钟抽 40 条"（16 段 × 40 = 640 条，体积不变），保证 480 分钟全程都有样本。

### 1.2 BUG-B：切换推演后计划不更新、手动更新失效 —— 成立

**现象复现**：在「气象监测」页点「虚拟气象」→ 提示"已切换到虚拟气象" → 但页面随即弹出：

> 本计划按「实测气象」生成，而地图当前显示「虚拟气象」：画面上的回波不是这份计划避让的那一片，绕飞的缺席属于口径差异，不是算法失效。**点击「重新调度」可按当前通道重建计划。**

点「重新调度」（或"按虚拟通道重新调度"）→ **画面不变**。等 8 秒、再点，还是不变。

**关键证据一：浏览器根本没去问服务器**

我用 CDP 监听网络，切换通道后前端只发了一个 session 请求：

```
请求  GET /api/traffic/session?seed=42&scenario=live&fields=slim
状态  200
fromDiskCache: true          ← 直接读本地磁盘缓存
encodedDataLength: 0         ← 一个字节都没从网络传
```

**关键证据二：后端其实是好的**

切通道后我用接口直接问（同一个工作区、同样参数）：

| | 切换前（实测） | 切换后（虚拟） |
|---|---|---|
| `weatherMode` | measured | **virtual** |
| `sessionId` | `67901b4f7ed3…` | **`7f7c5fae3015…`**（换了新会话） |
| `flights` | 1201 | **1673**（多 472 班） |
| `radarAvoidance.included` | false（403 取不到） | **true**（49 个采样时次） |
| `planRevision` | `traffic-plan-v1.3` | `traffic-plan-v1.3`（**没变**） |

**后端按通道重建了，前端拿的是旧缓存。**

**关键证据三：三重原因叠加**

| # | 原因 | 证据位置 |
|---|---|---|
| ① | 重建请求的 URL **不含通道参数** | `tn()` 里写死 `seed=${e}&scenario=${O}&fields=slim` |
| ② | 响应头允许缓存 **600 秒**，前端 `es()` 又没传 `cache:'no-store'` | `Cache-Control: private, max-age=600`；`fetch(e,{...o,headers,credentials})` 无 cache 字段 |
| ③ | `planRevision` 是**固定字符串**而非递增数字，前端的 `watch(plan-revision)` 判断不出"变了" | 实际值 `traffic-plan-v1.3`；而设置面板文案写"重新构建会递增" |

**旁证**：我点「重新调度」后采样，**0.5 秒就显示"已用 0 秒"、1 秒后整个流程结束**。真正的冷建要 **7–30 秒**。说明它确实什么都没做，直接命中缓存返回了。

**为什么这个 bug 特别危险**：页面**自己给出了正确的解释和正确的行动指引**（"点击重新调度可按当前通道重建计划"），然后**这个指引一头撞在缓存上**。评委或用户会认为"系统知道自己错了，但改不过来"——这比单纯不提示更伤信任。

## 3. 我必须更正上一版报告的一个错误

**0.11.10 报告里写的"首页叶子节点 946 → 189（−80%）"，是错的。**

我这次回头看了上一版的首页截图，发现那张图是**建场进行中**（屏幕中央一块 `RUNNING PLAN 62%` 遮罩）——因为航班列表和地图载具还没渲染，DOM 元素自然少。**189 是中间态，不是稳态。**

用同一口径在稳态下重测：

| 版本 | 全部元素 | textContent 非空 | 其中 < 12px |
|---|---|---|---|
| 0.11.7 | 946 | — | 191 |
| 0.11.10（**我上次报的，实为中间态**） | 189 | — | 49 |
| **0.11.13（本次，稳态）** | **936** | 899 | **188** |

叶子文本节点口径：**547 个，其中 172 个小于 12px**。

**结论**：首页的信息密度**从 0.11.7 到现在基本没变**（946 → 936）。这版之所以"看起来清爽"，靠的是**视觉改造**（大色块消失、航线变主角、KPI 从 4 张减到 3 张），不是**元素变少**。

这个更正对你没坏处，反而有用：**"看起来乱"的病根还没除**，只是被更好的配色和层级暂时盖住了。下一轮如果要继续治"乱"，方向是**合并面板、减少同屏并列的可读区块**，而不是继续调颜色。
