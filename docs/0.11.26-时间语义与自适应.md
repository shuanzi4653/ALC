## 一、那条「连接线」是什么：走廊带，而且只画了 3 条

用户指着运行态势的地图问「这个里面还没加载呢，这个连接线是什么？」

查下来是两件事叠在一起：

| 事实 | 说明 |
|---|---|
| 图上那几条橙线 | **走廊带**（`verdict='需谨慎'` 的琥珀色带子），不是航迹。航迹是青（飞行汽车）/淡紫（无人机）/橙（绕行） |
| 为什么像"没加载" | `HomeStage.loadRibbon` 只取 `limit=8` 再 `slice(0, 3)` —— **全图只画 3 条**，而 KPI 写着「31 条需复核」。三根没有任何标注的裸线，确实像草图 |
| 为什么图例没起作用 | 图例在 `<details>` 里、且是 30 多字的长句，扫描时被跳过 |

### 改法

1. **画 12 条**（仍排除不可飞），按概率降序，带 `name`；
2. **每条打概率标签**：`20% 沈阳 ↔ 本溪`（HTML 覆盖层 + `map.project()`，与雾圈标签同一套，
   因为这个 style 没配 `glyphs`，symbol 层会安静地什么都不画）；
3. 面板标题加计数 `走廊带 12 / 53` —— 这个数是"画了几条 / 共几条"，
   读者一眼知道它没漏；
4. `overview.corridors.ribbon`：**运行态势那张地图现在也有走廊带了**。
   数据从 `items` 里派生（同一份算 KPI 的数组），**零额外请求、零额外计算**。

> 为什么不是"干脆画满 53 条"：不可飞不画是既定口径，剩下 40 条全画会把城市名和航迹一起埋掉。
> 12 条 + 标签 + 计数是"看得懂"和"看得全"之间的取舍，取舍本身写在面板上。

## 二、时间不再是关闭理由：撤掉 4 处闸门，123 班 → 0 班

用户原话：「把那些超出计划时间的，全部优化，不可能出现超时的情况，能飞就是能飞，
绕道就是绕，禁飞就是禁飞。」

改前实测（seed 42 / live / 7760 班）：

```
状态: {'SCHEDULED': 7637, 'CLOSED': 123}
关闭原因: {'SEPARATION_RESOURCE_OR_TIME_LIMIT': 58, 'BEYOND_PLANNING_HORIZON': 65}
```

**123 班全是时间原因，气象阻断 0 条** —— 处置台上那句「停止放行 123 班，其中气象成因 0 班」
就是这么来的。那不是运行态势，那是排程器的内部约束漏到了业务语义里。

### 四处闸门

| # | 位置 | 判据 | 后果 |
|---|---|---|---|
| 1 | `_plan_trajectory` 开跑前 | `scheduled + base_duration > 480` | 直接关，理由 `BEYOND_PLANNING_HORIZON` |
| 2 | 候选循环内 | `points[-1][3] > TIMELINE_MINUTES` | 同上 |
| 3 | 候选循环内 | 总延误 > `maxExtraMinutes` / 单班时长 > `maxFlightMinutes` | 关，理由 `SEPARATION_RESOURCE_OR_TIME_LIMIT` |
| 4 | **候发起飞时间循环** | `begin + base_duration > TIMELINE_MINUTES` → `continue` | **最隐蔽**：连 offset=0 都越界时整个循环一次不执行，`path` 留空，落到 `if not path:` 被记成 `WEATHER_BLOCKED` |

第 4 处是这一轮最难找的一条：它不是"拒绝"，是"没试"。表现是一批**从未经过任何气象判据**
的班次在报表上写着"气象阻断"。定位它靠的是给 `weather_clear_at` 的每个失败分支加计数，
结果**四个分支的计数全是 0**，而关闭数仍为 65 —— 于是问题必然在"根本没调用判据"那一侧。

### 改后

```
状态: {'SCHEDULED': 7760}
关闭原因: {}
绕行 0 班 | 延误>0 3638 班 | max 延误 100 min
推演视界: 787 | 最晚到达 776
```

- 结论只剩三种：**能飞 / 绕飞 / 气象阻断**；
- 「绕飞」仍然按几何航程算（`detourMinutes`），不在这一轮改变；
- 视界不再写死 480：由后端按**实际最晚到达**算出 `timelineMinutes` 一起下发，
  前端滑块读它。否则长航线（齐齐哈尔↔大兴安岭 1034 km、约 5.9 小时）会被砍掉，
  或者永远"到不了"。

### 连带修复：三处误标

`if not path:` 那一支原来把"没有位置可放"一律记成 `WEATHER_BLOCKED`。
现在它只在**真的**有气象几何时才那样记；纯几何不可达留给 `NO_GEOMETRIC_PATH`。

### 判据随语义更新（4 条）

| 测试 | 原来守什么 | 现在守什么 |
|---|---|---|
| `test_traffic_network`（2 条） | `delay + detour <= 60`、`points[-1][3] <= 480` | 读配置 `maxExtraMinutes`、读计划 `timelineMinutes` |
| `test_traffic_network::determinism` | `closed > 0` | 关闭**原因**只能是气象类，不得出现时间类代码 |
| `test_traffic_v13` | `delay + detour <= 60` | 读配置上限；绕行增时不得为负 |

> 那三条 `<= 60` 的共同问题：**没有任何一条代码把 60 当规则**。计划器读的是
> `aircraft-profiles.json::separation.maxExtraMinutes`（120）。60 之所以长期成立，
> 是因为越界的班次先被视界闸门关掉了 —— 判据守的是一个不存在的常量，而它一直是绿的。

## 三、建场 20.1 秒 → 0.34 秒：计划跨工作区共享

先量（服务器，不是本机）：

```
新工作区首次请求   20.1s（BUILDING 2% → 10% → … → READY）
同 key 二次请求    0.00s
本地 cProfile      建场 14.7s：conflict 6.9s / shapely 4.6s / 气象 HTTP 4.5s
```

20 秒不是"算得慢"，是**每个访客都要重算一遍同一份计划**。计划内容只取决于
（种子, 场景, 快照, 通道, 雷达帧, **配置**），与工作区无关；工作区进键是为了隔离
**操作状态**（日志、处置记录），不是为了隔离"天气算出来的航路"。

### 做法

- 建场成功后，把「内容键 → 计划文件」写进 `STORE/_share.json`（只留最近 24 条）；
- 新工作区请求时，若索引里有同内容键、且指纹 / 算法版本 / 通道 / 场景 / 种子逐条相同
  → 直接读那份 JSON，**换掉 `sessionId`**（它是操作日志的命名空间，沿用会让两个人的
  处置记录混在一起），只放内存不落盘；
- 索引里加了**配置指纹**（`_config_digest`：机队档案 + 运行参数）。

配置指纹不是保险丝而是必需项：没有它，改一次阈值之后新访客仍会拿到按旧阈值算的计划，
而两份计划的 `fingerprint` 可能是同一个常量。它也是测试需要的 —— 第一轮全量套件里
`K10` 在整套里红、单独跑绿，原因正是用例 `monkeypatch` 阈值后命中了上一个用例的计划。

### 实测

```
share-a    12.93s | 班次 7760 | sharedFrom=None
share-b     0.34s | 班次 7760 | sharedFrom=449b4c18eee8…
share-c     0.30s | 班次 7760 | sharedFrom=449b4c18eee8…
```

服务器上单独量建场（含撤闸门后的增量）：**26.0s**（改前 20.1s）。多出来的部分是那些
原本被关掉的长航线真的去选路了。

> 部署后第一次量到 **121s**，一度以为改坏了。查下来是**排队**：`POOL` 是
> `max_workers=1`，服务重启后启动预热要连做实测/虚拟两个通道（2×26s），
> 新访客的建场排在它们后面。判据要读「服务空闲时建场多久」，不是「重启后立刻建场多久」。

闸门 `ALC_PLAN_SHARE=0` 可关闭共享，退回"每个工作区各算一遍"。

## 四、「叠层不完整」：底框只包住半屏

用户给的气象页截图里，卡片一路排到屏幕底部之外。扫描器量出来的数字：

```
.operations-console   框 1198×726   scrollHeight 2849   差 2123 px
```

机制：`.wb-body` 是 `display:flex; flex-direction:column`，而 flex 子项默认 `flex-shrink:1`。
子项内容（2849）超过容器（726）时，**它被压缩到容器高度**，内容溢出而底板不跟着长。
日志页还有第二处：末段 `margin-bottom:20px` 塌出父级，少 29 px。

```
.wb-body>.operations-console{flex:0 0 auto}
.operations-console{display:flow-root}
```

复扫 11 页 × 1440×900：**0 处**（改前：气象页下越 2123、日志页下越 29）。

> 这一类问题不报错、不改状态码、不让任何测试变红 —— 只有量 `scrollHeight` 才看得见。
> 探针第一版量到"全 0"，原因同样值得记：**它每页新开 URL 只等 11 秒，而建场要 20 秒**，
> 量到的是空骨架。第二版改成"一次加载、等计划就绪、切 hash 逐页扫"，才看见真问题。

## 六、城市气象：像 ice.shuanzi.site 那样"看得出在滚"

原来 `setInterval(60ms, +0.9px)` ≈ **15 px/s** —— 一屏 400 px 要 26 秒才滚完一行，
看起来像没动；而且 `setInterval` 在后台标签页被节流，切回来会一顿一顿。

现在 `requestAnimationFrame` + **按真实帧间隔**推进：约 **46 px/s（一秒一行）**，
内容渲染两遍、滚过一半减掉一半实现无缝循环；悬停 / 滚轮 / 触摸时暂停，离开 1.6 秒续；
头部加了「Ⅱ 暂停 / ▶ 继续滚动」按钮（滚动状态要能被说清，也要能停）。

## 九、没做的与已知

1. **耗时闸门撤掉之后，长航线的末班落在 T+12:56**（1034 km / 5.9 小时）。
   视界跟着放宽到 T+13:07，滑块与说明都改成数据驱动。
   如果更希望"时刻表本身不发越界班次"，那是**发班器**的事，需要重排时刻表并重测全部数字。
2. **延误上限仍是 120 分钟**（配置口径），实测最长 100 分钟。要不要压到 60 属于产品选择，
   但压下去就会有班次因等不及而被关 —— 与"不可能出现超时"直接冲突。
3. `maxFlightMinutes` 这条配置项现在**不参与裁决**（只作为档案记录）。留着是因为
   删掉它会让人以为"这条规则从来没存在过"。

## 十、三处"以为是文案、其实是机制"的坑

### ① 城市气象第一版用 rAF，实测会停

第一版 `requestAnimationFrame` + 按帧间隔推进。量出来的滚动位置停在 92 / 112 / 97
（每次不同），而**手动设 `scrollTop=400` 又能停住** —— 说明不是被别处重置，是循环没在推进。
rAF 在后台标签页会被节流；而我那一版还把 hover 当**硬暂停**，一个卡住的 hover 状态
就能让它永远不动。

现在：`setInterval(32ms)` + **小数累加器**（`scrollTop` 按整数落位，每帧加 0.7 px 会被抹平，
等于没动）+ 悬停只减速 0.15×。暂停只有按钮一个入口 —— 任何状态卡住，最坏是"滚得慢"，
不会变成"看起来没做"。实测 298 → 448（3 秒），约 50 px/s。

### ② 走廊带计数写成 `12 / 24`

`limit=24` 是**载荷**上限，不是走廊总数。第一版拿 `items.length` 当分母，页面上写
"走廊带 12 / 24"，而全网是 53 条 —— 一个自己造出来的数。改成读 `payload.total`。

### ③ 走廊带标签"有数没字"

后端只下发了 `id`，标签上就显示 `CAR-2-01-3-01`。补 `name` 之后才是
`4% 长春 ↔ 哈尔滨` —— 这一页存在的意义是让人看懂那条线是什么，编号做不到这件事。
