## 一、先把这一屏的数字逐个对上账

用户指的那一屏是「运行首页」。它上面**确实有两组数**，来自两次不同的求值：

| 位置 | 数字 | 来源 | 帧 |
|---|---|---|---|
| 结论条 | 53 条载客走廊 · 低于 25% · 最差 长春↔哈尔滨 4% · 另有 216 条货运 | `GET /v2/overview` | 三站 METAR 观测（11:30Z），**每 5 分钟轮询** |
| 顶部三格 | 需复核走廊 · 已触发停飞判据的走廊 · 平均提前量 | 同上（`kpis[]`） | 前两格＝本帧计数；**第三格＝离线回放中位数** |
| 口径小字 | 需复核 N 条（观测命中或概率 ≥15%）· 判定需谨慎 M 条 | 同上 `kpiDetail.definitionPending` | 同上 |
| 地图状态条 | 运行事件 N 个 · 停止放行 M 班 | 前端 `groupAlerts(抽样 flights)` | 本场景计划，随推演时刻 |
| 右栏四态 | 在空 / 已到达 / 已关闭 / 四态合计 1568 · 全量 7760 | 前端 `dispatchSummaryRows(抽样)` | 同上 |
| 页脚 | 放行率 89% · 时隙重排 3674 · 改航绕飞 18 · 停止放行 854 | `session.stats`（**建场时算定**） | 本场景计划 |

结论：**上面的数不是"这一轮处置的结果"，下面的数也不是"走廊判据的结果"。** 它们两个域、
两份气象输入（三站 METAR / Open-Meteo 模式估计），各自都对，只是一直被并排读。

用户的判断是对的 —— 屏幕没有把这个差别说出来，那就是屏幕的问题。

## 二、真错的是这四处

### ① 「平均提前量 60 分钟」混在本帧计数里（真误导）

`kpis[lead]` 读的是 `data/training/metar/model-v2-metrics.json` →
`targets.vis3k.leadTime.medianMin = 60`，样本是 **2019–2025 三站 METAR 的 62 次跨阈事件**。
它是离线回测指标，**不是本帧读数**。

而它原来长这样：`{label:'平均提前量', value:60, direction:'up', baseline:'规则基线 0（无预报能力）'}` ——
没有一处说"离线"，还挂着一个 ▲。本帧 0 条触发时，三格连起来读就是
「提前 60 分钟发出了 0 次报警」。

改（`traffic/v2.py`）：

```python
{'key':'lead', ..., 'scope':'offline', 'direction':None,
 'baseline':'离线回放：三站 METAR 的 62 次跨阈事件中位值（能见度 <3000 m）；本帧触发 0 条，非本帧读数'}
```

前端按 `scope` 在卡面打「离线」角标（**不在前端判断**，否则又是第二套口径）。

> 基线里的"本帧触发 N 条"与 `kpis[high].value` **必须同源**，测试直接比对这两个数。

### ② 页脚的「停止放行」不说气象成因

`停止放行 854` 与顶部的 `已触发停飞判据 0 条` 并排，读者只能得出"其中一个错了"。
854 里有几班是气象成因，`stats.closedByWeather` 本来就有，只是没写出来。

改（`runtime.js::dispositionSummary`）：`停止放行 854（气象 0）`。
没有关闭时不写"（气象 0）"—— 0 班时补一句"其中零"是两遍同一件事。

### ③ 两组数缺一句分工说明（这一条是用户要的核心）

新增一行小字，落在三格与口径小字之间（`data-brief-scope`）：

> 上方三格为走廊级判据（三站 METAR 观测帧）；页脚为班次级处置（全量 7760 班，停止放行 854 班
> （其中气象成因 37 班））—— 两组数分别求值。

**只在真有气象停飞时**再补第二句：

> 班次放行由派生风险区几何、固定管制区与间隔时隙判据决定，走廊概率不参与排程。

这句不是措辞：`service.py` 的排程只读 `crossingZone` / `riskCeilingAglM` / `maxFlightMinutes`
与固定管制区几何，**不读** `P_PROB_*` 概率阈值。所以"0 条走廊触发判据 + 37 班气象停飞"
是结构上成立的，不是矛盾。

### ④ 首页的时间轴上限还写死 480（**真 bug**，不是文案）

0.11.26 把首页之外的 `playbackMax` 改成读 `session.timelineMinutes`（实测 787），
**首页这一份漏改**。于是同一份计划：首页滑块标 **T+08:00**，工作台标 **T+13:07**。
首页拖到底，07:00 之后落地的班次永远画不出来 —— 屏幕上它们一直挂在空中。

改（`HomeStage.vue`）：案例窗口优先 → 否则读 `plan.timelineMinutes` → 才回落 480。
实测滑块 `max=787`、尾部标签 `T+13:07`，与工作台一致。

## 三、顺带修的三处口径表（它自己写错了）

`CALIBER_LEDGER`（「口径与来源」页那张表）有三行的"更新"列与实际行为不符，
而评委正是拿这张表来核对 KPI 的：

| 行 | 原写 | 实际 | 改为 |
|---|---|---|---|
| 放行率 | 每 5 分钟 | 建场时算定，换情景/换通道才重算 | 每次建场（换情景 / 换气象通道时重算） |
| 需复核 / 已触发停飞 / 概率档 / 模型覆盖 | 每 10 分钟 | `SituationBrief` 300 s 轮询 | 每 5 分钟（页面轮询） |
| 可飞性带段数 | 每 10 分钟 | 进页面取一次、拖时轴重取 | 每次进入页面 · 拖时轴重取 |

「平均提前量」那行的定义也补了"不是本帧读数，本帧触发数见 `kpis[high]`"。

- `backend-python/tests/test_overview_kpi_scope.py` —— `lead` 必须带 `scope='offline'`，

  「离线」角标读后端 `scope`、分工说明与分母、`planId` 变化要重取、
  **首页与工作台的时间轴上限同源**。

## 五、没做的一件事（记在这里，不假装做了）

`/v2/overview` 与建场**用的不是同一份气象**：前者是三站 METAR 实测 11:30Z，
后者是 Open-Meteo 模式估计 20:00（本场）。要把它们真正统一，得让 `overview` 接受
"计划所用的快照 id" 并据此取帧 —— 那是数据链路的改动，牵到 `v2.field()` 的缓存键。

本轮先做的是**让屏幕说清这件事**（分工说明 + 各带各的帧标记 + 计划换了立刻重取），
而不是把两个数硬凑成一个。硬凑出来的那个数，没有任何一方能对上。

### 顺带补齐的两件"流程"事

发版这件事过去一直靠现敲命令，`docs/云端部署与运维说明.md` 里写的

1. `tools/deploy/_deploy_release.py` —— 一条命令走完
   快照 → 上传（逐个比 md5）→ `deploy-remote.sh` → 重启 Python → 自检。

   版本号对了但 jar 没换、jar 换了但首页仍指着旧 chunk、前端换了但 Python 没重启，
   三种"看起来成功"各有一项抓它。退出码 0/1/2。
   负向对照已做：喂错参照物 → 4 项 FAIL + exit 1。
