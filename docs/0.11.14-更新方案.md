### 1.1 报告没写、但我复核时发现的一条

`mapFlights` 的 600 条里，**配送 494 条 / 载客 106 条**。

上一轮（0.11.12）我在文档里写的是"**载客优先**再补配送"，并把它当作"防回归"的措施。实际实现是
**单遍扫描 + 提前 break**：

```python
for flight in flights:                       # flights 的顺序是配送在前
    if len(car_rows) + len(delivery_rows) >= MAP_FLIGHTS: break
    ...
```

遍历遇到 494 条配送后名额已满，载客只挤进 106 条 —— **"优先"没有实现，只是写在注释里**。
这也是为什么地图上 T+0 只有 24 架、T+60 有 36 架：楼层里 88% 的名额给了配送，而配送航迹
集中在头两小时。

⇒ BUG-A 的真实成因比报告写的更具体：**不是"没做时间分层"，是"分层和分层内优先级都没落地"**。

## 二、思路（一句话）

**上一版为了省 320 KB，把"地图要跟着时间轴走"和"切了通道要重新算"这两个演示动作弄坏了。**
本轮不再省体积，改成"**用同样的体积换回时间覆盖**"，并且把两个 P0 的验收钉成
**网络层可测的证据**（`arrivalMinute ≥ 470`、`fromDiskCache === false`），而不是"看起来对了"。

三条原则：

1. **体积只允许小幅上涨**（≤ 1.0 MB），不允许回到 1.2 MB；
2. **每个 P0 的验收必须是机器可判的**（一个数、一个布尔），不是肉眼；
3. **不动调度算法、不动雾圈参数、不动已成立的 7 项**。

## 三、工单

### H-1（P0）：让地图在 480 分钟里都有飞机

**现状**（实测，见 §1）

| 数据源 | 条数 | 覆盖 | 载客占比 |
|---|---|---|---|
| `mapFlights` | 600 | T+0 ~ **T+127** | 106 / 600 = 17.7% |
| `flights` | 1201 | T+0 ~ T+480 | 848 / 1201 = 70.6% |

**改法**：`session` 收口处，把 `mapFlights` 的取样从"单遍取前 600"换成
**两层保证**：① 载客全量入图；② 时间分桶兜底。

```python
MAP_BUCKET_MINUTES = 30          # 480 / 30 = 16 个桶
MAP_MAX_ROWS = 900               # 硬上限，防体积失控
MAP_FILL_PER_BUCKET = 8          # 空桶补配送的条数

def sample_map_flights(flights):
    """① 载客全量；② 每个 30 分钟桶至少有样本；③ 超出上限时按桶均匀裁剪。"""
    car = [f for f in flights if (f.get('mode') or '') == 'CAR'
           and f.get('departureMinute') is not None]
    delivery = [f for f in flights if (f.get('mode') or '') != 'CAR'
                and f.get('departureMinute') is not None]

    def bucket(f):
        return int((f.get('departureMinute') or 0) // MAP_BUCKET_MINUTES)

    picked = list(car)                       # 载客全量：848 条，覆盖 0~450 分钟
    have = {bucket(f) for f in car}
    for b in range(0, 480 // MAP_BUCKET_MINUTES + 1):
        if b in have:
            continue
        pool = [f for f in delivery if bucket(f) == b]
        picked.extend(pool[:MAP_FILL_PER_BUCKET])   # 只给"地图上完全没飞机"的桶补

    return picked[:MAP_MAX_ROWS]
```

**为什么这样能同时满足两个约束**

| 约束 | 为什么成立 |
|---|---|
| 时间覆盖到 480 | 载客起飞最晚 450 分钟、到达最晚 ~479；空桶（450–480）由配送补 |
| 53 条载客走廊全覆盖 | 载客**全量**入图（848 条），不再按"前 600"截断 |
| 体积 ≤ 1.0 MB | 880 条 × 约 300 B ≈ 264 KB，比现在的 600 条（180 KB）多约 84 KB，总包 896 → **约 980 KB** |
| 不再"配送挤占名额" | 载客先入，配送只在空桶补 8 条 |

**验收（做不到就算没修好）**

- [ ] `mapFlights` 的 `arrivalMinute` 最大值 **≥ 470**
- [ ] `mapFlights` 里 `mode=CAR` 的条数 **= 848**（等于 `flightStats.carReturned`）
- [ ] 逐 60 分钟"地图在空数 / 列表在空数" ≥ **0.4**，且任意档 **不为 0**
- [ ] session 响应 **≤ 1.0 MB**
- [ ] 时间轴 T+2:00 / T+4:00 / T+7:50 三档，地图可见载具 **> 0**

### H-2（P0）：让"切通道 → 计划重算"真的发生

**现状**：后端算对了（`sessionId` 换新、`flights` 1201→1673、`radarAvoidance` false→true），
前端拿的是缓存。三处断点全部复现（§1）。

**改法（三处，缺一不可）**

| # | 位置 | 现在 | 改成 |
|---|---|---|---|
| ① | `TrafficWorkbench.vue:663` | `seed=${input}&scenario=${scenario.value}&fields=slim` | 追加 `&mode=${weatherMode.value}`，且 `requestJson(..., { cache: 'no-store' })` |
| ② | `api.js:71` 的 `fetch` | 无 `cache` 字段 | 让调用方可以传 `cache`；对 `/traffic/session` 固定 `no-store` |
| ③ | 后端建场收口 | `planRevision: "traffic-plan-v1.3"` | `planRevision` 改为**会变的号**：`f"{algorithm}|{weatherMode}|{snapshotId}|{counter}"`；另留 `planVersion` 保算法版本 |

③ 的最小实现（不动全局状态）：

```python
plan_revision = f"traffic-plan-v1.3|{weather_mode}|{fingerprint[:8]}"
```

只要**不同通道 → 不同值**即可满足前端 `watch(plan-revision)` 的判据；
如果还要"同一快照重跑递增"，再加进程内计数器。

> ② 的一个反作用要防：`no-store` 会让 F5 刷新变慢。所以只对 `/traffic/session` 用，
> 且**保留后端 `private, max-age=600`**（对不带 `no-store` 的请求仍然秒开）。

**验收**

- [ ] 切通道后**不点任何按钮**，3 秒内地图回波与右侧数字自动变化
- [ ] 那次 session 请求 `fromDiskCache === false`
- [ ] 请求 URL 里含 `mode=virtual` / `mode=measured`
- [ ] 两个通道下 `planRevision` **不同**
- [ ] 点「重新调度」耗时 **≥ 3 秒**
- [ ] 虚拟 → 实测 反方向同样成立
- [ ] F5 刷新仍在 3 秒内出画面

### H-3（P1）：`flights?minute=` 要么生效，要么删掉

现在传什么 `minute` 都返回同一份（`total` 恒 7760）。修法二选一：

- **A（推荐，15 分钟）**：真的按 `departureMinute ≤ minute < arrivalMinute` 过滤
- **B**：从文档与请求里删掉这个参数

选 A 的理由：H-1 之后地图有全程样本，这个接口就能承担"只取某刻在飞"的第二用法。

**验收**：`?minute=0` 与 `?minute=300` 的 `total` **不同**；不传 `minute` 行为不变。

## 七、给复测方的说明（可核对）

1. BUG-A 的真实原因比报告更具体：`mapFlights` 里 **配送 494 / 载客 106**，是"载客优先"没实现，
   不只是"没做时间分层"。本方案按"载客全量 + 空桶补配送"重写，并把 `car = 848` 写成硬判据。
2. BUG-B 三处断点全部复现，其中 `planRevision` 的修法从"递增计数器"改为
   "`算法|通道|快照` 组合串"—— 后者不依赖进程状态，重启后仍然稳定。
3. 报告第 3 节的更正（首页信息密度 946→936）我接受。上一版把"建场中间态"当成稳态，
   是我们度量口径的缺口；本轮把"稳态判定"写进自查清单（等 `status=READY` 且列表非空再取 DOM）。
