## 2. 今天新发现的 P0（会被现场点破）

### 2.1 P0-1：雾天案例只换了首屏三块皮，计划本体还是实时的

**怎么发现的**：分别在实时和雾天两种模式下，抓取首页全文做逐字 diff。

雾天模式首页尾部（`?case=fog-20250105`）：

```
本轮处置（延迟优先）
放行率 98% · 时隙重排 3500 · 改航绕飞 0 · 停止放行 123
```

实时模式首页尾部：

```
本轮处置（延迟优先）
放行率 98% · 时隙重排 3500 · 改航绕飞 0 · 停止放行 123
```

**逐字相同。**

这意味着一件很严重的事：雾天案例下，**21 条走廊已达禁飞级，但没有任何一班航班因此被改航、被延误、被关闭**。处置栏目里"改航绕飞 0"。

同一屏右栏的「气象情报」卡片，在雾天模式下原文是：

> **本帧无高影响天气：36 条观测/情报全部正常，已折叠。**

也就是说，**首屏同时在说三件事**：

| 位置 | 原文 | 含义 |
|---|---|---|
| 顶部横幅 | "ZYTX 实测能见度 997.8 m、云底 152 m" | 大雾 |
| KPI | "禁飞级走廊 21 条" | 禁飞 |
| 右栏气象情报 | "本帧无高影响天气：36 条观测/情报全部正常" | 晴 |
| 页脚 | "改航绕飞 0 · 停止放行 123" | 没处置 |

**再往下挖一层**：切到「3 处置 · 调度台账」，雾天模式下第一条是

```
CAR-1-01-1-05-0-0  沈阳 ↔ 本溪  已到达
```

而首页横幅第一句就是"**沈阳 ↔ 本溪 等 21 条走廊当前观测已达禁飞级**"。

**评委只要做一次"从首页到台账"的点击，就会看到：你说这条走廊禁飞，但这条走廊上的飞机已经落地了。**

**为什么会这样（技术判断）**：`case` 只被注入到 `overview` 这一个聚合接口的渲染层（结论文案、4 个 KPI），**没有进入建场/调度管线**。所以：

- KPI 的数字来自案例
- 航班状态来自实时
- 反事实的 A/B 则来自另一套（算出来的）数字

**三套数字，一个页面。**

**改成什么**（详见执行方案 W-14）：

要么让案例**真的跑一次重调度**（推荐，半天），要么**把案例降级为"观测量回放"**，并在所有涉及航班状态的页面明确写"本案例只回放观测，不重跑调度"。**不能维持现状**——现在的状态是"看起来跑了"，这比"明确不跑"更危险。

### 2.2 P0-2：`case` 参数只有 2 个接口认，另外 4 个页签全都不认

**接口级证据**（直接 curl，绕过前端）：

```
GET /api/traffic/v2/corridor/CAR-1-01-1-05?case=fog-20250105
→ observedAt: "2026-10-20T13:00:00Z"
→ verdict: "可飞"
→ criteria[0].value: 9656.1     ← 实时的能见度，不是 997.8
```

**页面级证据**（雾天模式下进入「2 走廊 · 走廊剖面」）：

```
观测 2026-10-20T13:00:00Z          ← 实时时刻
长春 ↔ 吉林  CAR-2-01-2-02  0%  可飞
长春 ↔ 哈尔滨 CAR-2-01-3-01  0%  可飞
…（40 条全部 0% 可飞）
```

首页说"21 条禁飞"，走廊页说"40 条全部可飞"。**同一个系统、同一个时刻、两个答案。**

**受影响的四个页面**：

| 页面 | 雾天模式下实际显示 | 应该显示 |
|---|---|---|
| ② 走廊剖面 | `观测 2026-10-20T13:00Z`，全部 0% 可飞 | `观测 2025-01-05T00:00Z`，21 条禁飞 |
| ③ 预警中心 | 气象成因 **0** / 非气象成因 361 | 气象成因 21（或"涉及 N 班"） |
| ③ 调度台账 | 7760 条，沈阳↔本溪"已到达" | 该走廊班次为"已关闭/改航" |
| ① 气象监测 | 36 站晴天，能见度 20 km | ZYTX 998 m |

**做一次定量说明**：我统计了雾天模式下 13 个子页，**只有 2 个页面的文字与实时模式不同**（运行首页、反事实对照），其余 **11 个页面的正文逐字相同**。

**根因**：`case` 是"某几个组件的 props"，不是"全局上下文"。正确做法是把它提升成一次注入、全链路读取（执行方案 W-13 给了改法）。

### 2.3 P0-3：`40 / 53` 不是模型能力边界，是接口分页上限

这一条是今天最"技术性"的发现，也是**评委中最懂行的那一位最可能问的**。

**发现过程**：

```
GET /api/traffic/v2/corridors?limit=40   → 200, total=53, items=40
GET /api/traffic/v2/corridors?limit=41   → 422
GET /api/traffic/v2/corridors?limit=53   → 422
GET /api/traffic/v2/corridors?offset=40&limit=13 → 200, items=13, 但第一条还是"长春↔吉林"
```

**解读**：

1. `total` 明确是 **53**，但 `limit` 硬上限 **40**；
2. `offset` 参数**被忽略**（`offset=40` 返回的还是第 1 条）；
3. 所以 **41–53 这 13 条走廊，任何前端都无法取得**。

再看昨天那句"修好的"文案：

> 已评估的 **40** 条城际走廊（全网共 **53** 条）… **另有 13 条未评估，不计入本结论。**

这句话把"接口拿不到"写成了"模型没评估"。而同一屏右侧写的是：

> **模型覆盖 100%**

**100% 覆盖，和 13 条未评估，是同一屏上的两句话。**

同时「口径与来源」页的字典写着：

> 待处置走廊 | 不可飞概率 ≥ 50% | p ≥ 0.5 的走廊 | **全部城际走廊（当前 40 条）**

**分母也被写成了 40。** 三处口径互相打脸：

| 位置 | 走廊总数 | 已评估 |
|---|---|---|
| 结论条 | 53 | 40 |
| 走廊剖面页头 | **53 条** | 列表实际只渲染 40 |
| 口径字典 | **40 条** | — |
| 模型覆盖 KPI | — | **100%** |

**为什么这是 P0 而不是 P1**：因为"53 条走廊"是你们的规模卖点，评委一定会问"你这 53 条怎么来的、覆盖多少"。现在的答案会让人得出"他们连自己的数据都没数清"的结论——这直接打击"项目实施 15 分"。

**好消息**：这是个**半小时能修完的 bug**，修完还能变成加分项（"53 条全覆盖"比"40 条评估 13 条留白"强得多）。

### 2.4 P0-4：反事实的因果链站不住——"改判 0 架次"却"减少 3016 架次暴露"

雾天模式下的反事实页，原文并列着这两句：

> 计划 49293b6f049d… · 参评 7336 / 7760 架次 · **模型改判 0 架次**
>
> 关掉 AI：**3016** 架次暴露在禁飞级走廊上；开启 AI：**0** 架次。

**翻译一下这两句话**：模型一班都没改判，但风险暴露降了 3016 架次。

那 3016 架次是谁处置的？答案在它自己的小字里：

> **「暴露」的判据 = 走廊概率 ≥80% 或 走廊中点最近站的观测已达禁飞级（0.11.3 起）**
>
> `_decision()` 在 `observed_ban` 时把 `DIRECT` 从可执行动作里移除

**也就是说**：B 组之所以暴露为 0，是因为代码层面**把"直接飞"这个选项删掉了**，不是因为有概率预报。

**评委的追问会很锋利**：

> "A 组既然是'规则全权'，规则看得见 METAR 997.8 m 吗？看得见为什么不关闭？"

如果规则看得见 → A 组也该关闭 → A/B 没差异；
如果规则看不见 → **那 B 组的收益来自"把观测接进规则"，不来自 AI**。

**两种回答都不利。** 这是 15 分「应用成效」里最脆的一块。

**但这个问题是可以彻底修好的**，而且修完更强。正确的对照组设计应该是：

| 组 | 定义 | 它代表什么 |
|---|---|---|
| **A（现行做法）** | 只看**当前观测**，不看未来；按人工值班逻辑处置（现在什么样就停什么样） | 低空运行的真实基线 |
| **B（本系统）** | 用**未来 1–6 h 概率**提前处置 | 你们的贡献 |

这样差异**只可能来自"提前量"**——而提前量恰好是你们唯一真正赢过基线的指标（中位 60 分钟，持续性基线为 0）。**把最强的证据放到最能发挥它的对照里**，这是这次修改的核心。

另外，反事实页脚注写着：

> 延期后的风险未重算（**本版本没有逐时概率**），因此延期不会被判成降险手段

但走廊剖面页明明画着 0–6 h 逐时概率（`hourly[]`，7 个点，`MODEL` / `MODEL_EXTENSION` 分段）。**"没有逐时概率"是假话**，而这句话恰好堵死了"延误也是降险手段"这条最有说服力的结论。

## 3. 今天新发现的 P1（不致命，但会持续扣"完成度"）

### 3.1 页面上有 12 处 Markdown 没渲染，直接露出星号和反引号

这是"手工敲文案没走渲染"的典型痕迹，评委会读成"没做完"。

| 位置 | 屏幕上的原文 |
|---|---|
| 口径与来源 | 边界气象是**输入**，不是结论 |
| 口径与来源 | 收缩量是**相对侵蚀深度**，不是内核到原轮廓的距离 |
| 口径与来源 | 边界**亮温不能换算成 dBZ** |
| 口径与来源 | 边界**派生风险区不是管制命令** |
| 口径与来源 | 边界**交通数据一律是模拟的** |
| 民航情报 | 官方固定管制区与气象派生风险区**分开报** |
| 民航情报 | 登记数与已有几何数**不相等是正常的** |
| 大模型取证 | 模型只能把结论**变得更保守** |
| 大模型取证 | 本页是大模型的**证据检索** |
| 反事实（两处） | 走廊概率 ≥80% **或** 走廊中点最近站… |
| 分歧台账 | 台账按工作区隔离（`` `X-ALC-Workspace` ``） |

**修法**：全局搜 `**` 和 `` ` ``（在 JSX 文本节点里），改成 `<strong>` / `<code>`；再加一条 CI 断言：`innerText` 里不允许出现连续两个 `*`。**1 小时能清完。**

### 3.2 Ctrl+K 里 4 个页面的副标题完全一样

实拍 Ctrl+K 面板：

```
反事实对照   5 复盘   用 AI 和不用，差多少
分歧台账     5 复盘   用 AI 和不用，差多少
运行日志     5 复盘   用 AI 和不用，差多少
```

**这意味着命令面板的目录是手写的两份，不是从路由生成的。** 一份改了两份不同步。执行方案 W-20 给了"单一来源生成"的做法（约 2 小时，以后永远不用再维护）。

### 3.3 预警中心：空态指向一个不存在的 tab

原文：

> 切到「**排程冲突**」可查看这些事件。

页面上只有两个 chip：「气象成因 0」「非气象成因 361」。**没有"排程冲突"这个 tab。**

同时这个页面 80% 是空白（见 `assets/2026-10-20/alerts_empty.png`）。在**实时**模式下它永远是这个样子，而"处置"这一组是评委必然会点的一组。

### 3.4 "0%" 其实是 0.23%

首页结论条："最差为 **长春 ↔ 吉林（0%）**"。
接口里这条走廊的 `pMax` 是 **0.0023**。

**0.23% 显示成 0%** 有两个后果：一是"最差"这个说法自相矛盾（最差怎么会是 0），二是让人怀疑精度。建议一律改为 `<0.5%` 或保留一位小数。

### 3.5 判据表仍然显示 `9656.1 m`

W-08 只改了结论处（"≥ 9.7 km（6+ 为下界）"），但走廊详情的「判据（3 条）」表里，能见度仍然是 `9656.1 m`。

一个页面里两种写法，说明改的是"展示组件"，不是"数据层"。**同一个值应该只有一个格式化函数。**

### 3.6 "投影"模式没有放大字号

实测（1680×1050，统计所有叶子文本节点）：

| 模式 | 12px 节点 | <12px | <11px | 最大字号 |
|---|---|---|---|---|
| 普通 | 82 | 24 | 15 | 15px |
| **投影** | **264** | **155** | **98** | **15px** |

投影模式只是"多显示了内容"，**字号完全没变**，最大仍是 15px。而投影仪 + 会议室后排的可读下限是 18–20px。

"投影"这个按钮现在的实际作用 ≈ 隐藏子导航。要么真的做（一套 `--fs-*` 变量，投影档 ×1.45），要么删掉这个按钮。

### 3.7 冷启 30.3 秒 / 热刷 12.4 秒

| 指标 | 10-19 | 10-20 | 判断 |
|---|---|---|---|
| 首屏可读（框架出现） | 1.8s | **0.7s** | 好 |
| 计算完成（能给结论） | 26.9s | **30.3s** | 差 |
| 刷新后计算完成 | 6.9s | **12.4s** | **退步** |
| 最大单响应 | 23.8 MB | **4.04 MB**（session） | 大幅改善，但仍偏大 |

**判断**：`session` 仍是 4 MB / 9.4 秒，是冷启的主要成本。刷新反而变慢，说明缓存策略变了或快照更大了。

**这条为什么算 P1 而不是 P0**：如果演示用录屏，30 秒不是问题；如果现场打开，30 秒是致命的。**所以必须在 D5 之前决定"现场打开还是放录屏"**（执行方案 W-22）。

### 3.8 飞行中的载具高度 0 m、地速 0 km/h

调度台账首屏三张卡，状态「飞行中」，但：

```
当前距地高度   0 m AGL
升降状态/地速  爬升 · 0 km/h
```

地图标签同样：`鸡西 ↔ 七台河 · <1 m`、`七台河 ↔ 牡丹江 · <1 m`。

**评委第一眼会问**："飞机为什么在 0 米高度飞？"

技术上这大概是"推演未启动时 T+0 的初始态"，但**默认画面不该呈现初始态**。修法：未启动推演时，卡片状态显式写"待起飞 · T+0 未推进"，或者默认把时钟推到 T+5min。

### 3.9 你说的那件事（"一进去太乱、看不出有什么用、找不到功能"）——今天没有改善

这一节单独写，因为这是你唯一凭直觉就能判断、而且判断得对的部分。我用可量化的方式复核了一遍：

| 你的感受 | 量化后的实际情况 | 今天 vs 昨天 |
|---|---|---|
| "一进去太乱" | 首页 **122 个叶子文本节点**、同时铺 **6 个信息块**（结论条 / 4 KPI / 地图 40+ 标签 / 右栏 4 块 / 时间轴 / 页脚统计） | 持平 |
| "看不出来有什么用" | 结论条讲的是"发生了什么"（21 条禁飞、31% 概率），**没有一句话讲"所以你现在该点哪个按钮"** | 持平 |
| "一大堆功能叠在各种页里" | **13 个子页**（比昨天 10 页**更多**），5 个分组里"复盘"一组有 5 页 | **变差** |
| "用了半天找不到功能在哪" | 「改航 / 延误 / 采纳 / 否决」仍在地图右下角 **11px 灰按钮**；`Ctrl+K` 能用，但**界面上没有任何可见入口** | 持平 |
| "不太有观赏性" | 最小字号仍是 **9px**，1680 宽下 **24 个节点 < 12px**；"投影"模式只是隐藏子导航，**最大字号仍是 15px** | 持平 |

**一个必须说清的事实**：昨天我给的建议是"10 页 → 5 页"，队友把它理解成"5 个**分组**"，但每个分组下又长了子页，结果总数从 10 变成 13。**字面上达成了目标，反而离目标更远。**

**这不是审美问题，是"没有主线"的症状。** 系统同时在讲 6 个故事，因为每一层（规则 / 概率 / 观测 / 大模型）都想证明自己在工作，于是每一层都占一块屏幕。**砍页面砍不动，是因为没想清楚"这一屏只回答哪一个问题"。**

**所以这一条我不建议当成"美化"来做，而建议当成一个独立工单**（执行方案 W-21，拆成"首页重排 4.5h"和"13 页合并 5.5h"两段）。**首页那 4.5 小时是全部 12 张工单里对第一印象收益最高的一段——因为它不需要动任何后端。**
