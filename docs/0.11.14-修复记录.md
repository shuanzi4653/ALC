## 一、H-1（P0）地图 480 分钟全覆盖

### 改了什么

`mapFlights` 从「单遍扫描取前 600」改成三层结构：

```python
car_all   = [载客全量]                       # 848 条（含 CLOSED）
car_rows  = [有 departureMinute 的载客]       # 698 条（CLOSED 没有起飞时刻）
map_pool  = car_rows + 每个空桶补 ≤4 条配送     # → 722 条
```

**上一版真正的错不是"没做时间分层"，是"载客优先"没落地**：实现是
`for f in flights: if len(car)+len(delivery) >= 600: break`，而 `flights` 顺序配送在前，
494 条配送先占满名额 ⇒ 载客只进 106 条、航迹全在头两小时。

### 验收（线上实测）

| 判据 | 要求 | 实测 |
|---|---|---|
| `mapFlights.arrivalMinute` 最大值 | ≥ 470 | **479.8** |
| 地图里的载客条数 | = 可飞载客全量 | **698 = 698** |
| 地图载客 + 关闭无时刻 | = `carReturned` | **698 + 150 = 848** ✓ |
| 逐 60 分钟 地图/列表 | ≥ 0.4 且不为 0 | **T+0 0.48；T+60…T+420 全 1.00** |
| session 体积 | ≤ 1.0 MB | **1005.3 KB** |
| 行数 / 每行 | — | 722 行 / **451 B** |

`flightStats` 新增两个字段把账交代清楚：`mapCar`（地图里的载客）与
`carClosedNoTime`（因已关闭、没有起飞时刻而没进地图的载客）。

### 落实过程中改了两处方案

| 方案原写 | 实际改成 | 为什么 |
|---|---|---|
| 分桶 `range(0, 480//30 + 1)` = 17 个桶 | **16 个桶**（0…15） | 第 17 个桶是 [480,510)，**没有航班在那里起飞**；判据当场报「桶 16 一条都没有」 |
| 载客全量 848 入图 | **698（只收有起飞时刻的）** | 318 条是 CLOSED，没有航迹；收进来白占 150 KB，且会让"覆盖到 480"的判据失真 |
| 每行 6 个航迹点 | **4 个** | 实测每行 590 B（估算 300 B），体积 1109 KB 超标；6→4 点省到 **1005 KB** |

### 一处对方案的修正

方案里我写的是「修订号 = `算法|通道|快照` 组合串」。**实施时改成递增序号**，理由：
前端 `algorithmIdentityTitle()` 用 `Number(raw)` 读它 → 组合串得 NaN → 永远显示"计划修订未声明"；
而设置面板承诺的是"重新构建会**递增**"，序号才贴合那句话。算法版本串没有丢，挪到了 `planVersion`。

## 七、软更新（同版本号 · 2026-10-23 14:25）：预热 + 进度刻度

> **按用户要求，本轮不计入迭代**：不升版本号，线上仍是 `0.11.14-beta`。

### 7.1 先说根因：预建一直在跑，但预建的结果读不回来

`_prewarm_sibling` 从 0.9.x 就存在 —— 存一份计划后会在后台把**另一个通道**也建一遍。
按设计，切通道时应当是一次磁盘命中（约 0.5 秒），而实测要 90–120 秒。

原因在磁盘恢复那三行：

```python
if (result.get('fingerprint') == FINGERPRINT
        and result.get('planRevision') == PLAN_REVISION     # ← 这里
        and result.get('weatherMode', weather_mode) == weather_mode):
```

H-2③ 已经把建场载荷的 `planRevision` 从常量改成了**递增序号**（`'1'`、`'3'`…），
而这一行还在拿它跟常量 `'traffic-plan-v1.3'` 比 ⇒ **永远不相等，磁盘恢复永远失败**：

- 每次切通道、每次重启都要整份重建；
- `_prewarm_sibling` 辛苦建出来的姊妹计划落盘后**读不回来**，预建等于白做。

这是我在 H-2③ 里引入的回归，**修复前所有计划都不再从磁盘恢复**（只是没人注意到，
因为"重建"和"命中"在界面上长得一样，差别只在耗时）。

**修法**：比 `planVersion`（算法版本串仍发布在这里），并保留 `planRevision` 作为兼容回退：

```python
and result.get('planVersion', result.get('planRevision')) == PLAN_REVISION
```

### 7.2 预热：启动时把两个通道各建一次

进程刚起时 `JOBS` 是空的，第一个访客无论如何都要等一整次建场。启动 5 秒后（让健康检查
与 nginx 探测先过），用**未标识工作区**把 `measured` 与 `virtual` 各建一次：

```python
@app.on_event('startup')
def _on_startup():
    _startup_warm()      # 后台线程：measured → virtual → 复原 measured
```

**不常驻内存**：走 `retain=False`（一份计划约 110 MB，服务器 1056 MB）。落盘即可，
命中时一次 `json.loads` 换掉整次重建。

日志实测：

```
14:14:35 [main] INFO: startup warm: measured 已建场
14:14:35 [main] INFO: startup warm: virtual  已建场
```

### 7.4 进度：等待要有刻度

后端在 `BUILDING` 响应里补四个字段：

| 字段 | 含义 |
|---|---|
| `stage` | 当前阶段（如"逐班次规划航路与间隔"） |
| `elapsedSeconds` | 已用秒数（由 `startedAt` 算） |
| `etaSeconds` | 预计剩余，**按通道取经验值**（measured 60 s / virtual 110 s） |
| `buildChannel` | 这份计划属于哪个通道 |

响应里同时标 `etaBasis: "ESTIMATE_BY_CHANNEL"` —— 它是估算，不是进度推算，不能读成承诺。
