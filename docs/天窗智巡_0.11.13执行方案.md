## 1. 工单 H-1（P0，2.5h）：让地图在 480 分钟里都有飞机

### 现状

| 数据源 | 条数 | 覆盖时段 |
|---|---|---|
| `mapFlights`（地图用） | 600 | T+0 ~ **T+127** |
| `flights`（列表用） | 1201 | T+0 ~ T+480 |

`mapFlights` 是"按起飞时间取前 600 条"，前 600 条自然全是最早的。

### 改成什么

**把"取前 600 条"换成"按时间分桶抽样"**，条数不变、体积不变、覆盖从 127 分钟变成 480 分钟。

```python
# backend-python/traffic/（建场收口处，mapFlights 生成的位置）
def sample_map_flights(flights, total_minutes=480, bucket=30, per_bucket=40, cap=640):
    """按起飞时间 30 分钟分桶，每桶取 per_bucket 条。
    条数从 600 → 至多 640，体积基本不变，但时间覆盖从 127 分钟扩到 480 分钟。"""
    has_dep = [f for f in flights if f.get("departureMinute") is not None]
    no_dep  = [f for f in flights if f.get("departureMinute") is None]

    buckets = {}
    for f in has_dep:
        b = min(int(f["departureMinute"] // bucket), total_minutes // bucket)
        buckets.setdefault(b, []).append(f)

    out = []
    for b in sorted(buckets):
        group = buckets[b]
        # 桶内按"起飞 + 到达中点"排序，让样本在桶内也均匀
        group.sort(key=lambda x: (x["departureMinute"] + x.get("arrivalMinute", x["departureMinute"])) / 2)
        step = max(1, len(group) // per_bucket)
        out.extend(group[::step][:per_bucket])

    return out[:cap]
```

### 为什么这样改是安全的

- **条数不涨**：600 → 至多 640，`points` 总量基本不变，首屏仍约 900 KB。
- **不碰业务**：`flights`（列表）那条路径完全不动，"列表不带航迹"的瘦身成果保留。
- **不碰算法**：只改"给地图看哪 600 条"，不改任何调度结果。

### 验收（如果做不到就算没修好）

- [ ] 时间轴拖到 **T+2:00 / T+4:00 / T+7:50**，地图上都能看到载具
- [ ] 任一时刻，"地图可见载具数"与右侧"在空 N 架"**同量级**（允许因缩放精简，但不能 0 对 51）
- [ ] `GET /api/traffic/session?scenario=live&seed=42` 响应 **≤ 1.0 MB**
- [ ] 53 条载客走廊的 `flightStats.carReturned` 仍为 **848**

## 2. 工单 H-2（P0，3h）：让"切通道 → 计划重算"真的发生

### 现状（三条链，断在第一条）

| 环节 | 现状 | 判定 |
|---|---|---|
| 后端重算 | 会重算：sessionId 换新、flights 1201→1673、radarAvoidance 从 false 变 true | ✅ 好的 |
| 前端去取 | 发出了请求，但 **`fromDiskCache: true`**，一个字节都没走网络 | ❌ 断了 |
| 前端判断"变没变" | `planRevision` 恒为 `traffic-plan-v1.3` | ❌ 也断了 |

### 改成什么（三处，缺一不可）

#### ① 重建请求的 URL 必须带通道

`frontend/src/.../HomeStage.vue`（或 `tn()` 所在文件）里现在是：

```js
let n = `seed=${e}&scenario=${O.value}&fields=slim`;
let res = await es(`/api/traffic/session?${n}`);
```

改成：

```js
let n = `seed=${e}&scenario=${O.value}&fields=slim&mode=${T.value}`;
let res = await es(`/api/traffic/session?${n}`, { cache: 'no-store' });
```

> `T.value` 就是当前气象通道（`measured` / `virtual`）。**关键不是参数本身，而是让缓存键里含通道**——同一个 seed 在两个通道下是两个不同的问题，本来就不该共用一个答案。

#### ② 后端让 session 不被缓存（或让它按通道缓存）

`backend-python/` 里 `/api/traffic/session` 的响应头现在是：

```
Cache-Control: private, max-age=600
```

有两个选法，**推荐 A**：

**A（推荐，10 分钟改完）**：加 `Vary`，让缓存按查询串区分，同时把时长压到 60 秒

```python
resp.headers["Cache-Control"] = "private, max-age=60"
resp.headers["Vary"] = "X-ALC-Workspace, X-ALC-Operator"
```

**B（最稳，但慢一点点）**：直接不缓存

```python
resp.headers["Cache-Control"] = "no-store"
```

> 说明：`private, max-age=600` 这个头本身没错（它让"刷新页面秒开"），错的是**缓存键里没有通道**。所以真正的修法在 ①；②只是加固。**如果只能改一处，就改 ①。**

#### ③ `planRevision` 改成会变的号

设置面板现在对用户承诺：

> 数据快照编号 + 算法指纹 + 气象通道三者相同，重跑即得到逐字节相同的运行计划。
> 计划修订：**同一快照下重新构建会递增。**

但实际返回的是 `traffic-plan-v1.3`（算法版本串，永远不变）。前端 `MapPanel` 的 `watch` 依赖 `plan-revision`，它不变 → 即使数据换了，地图也认为"无事发生"。

**最小改法**：在建场收口处维护一个进程内计数器，每次真正重算就 +1。

```python
_PLAN_REV = 0

def build_plan(...):
    global _PLAN_REV
    _PLAN_REV += 1
    ...
    return {..., "planRevision": _PLAN_REV, "planVersion": "traffic-plan-v1.3"}
```

> 如果不想动全局状态，也可以用 `hash(seed, fingerprint, weatherMode, 建场时刻)` 生成一个短串——**只要"不同通道 → 不同值"就够用**。

### 顺便修掉一个误导（5 分钟）

页面现在会弹正确提示：

> 本计划按「实测气象」生成，而地图当前显示「虚拟气象」…… 点击「重新调度」可按当前通道重建计划。

这是**好设计**，但因为修之前点不动，反而变成"系统知道自己错了却改不过来"。修完 H-2 它就成立了，**这句文案不要删**。

### 验收

- [ ] Network 面板里那次 session 请求 **`fromDiskCache` 为 false**
- [ ] 请求 URL 里能看到 `mode=virtual` / `mode=measured`

## 7. 答辩话术（修完之后用）

### 问："你这个时间轴拖到最后怎么还有飞机？"

> 全时段都有。我们地图用的是一份按 30 分钟分桶抽样的轻量航迹（640 条），覆盖 480 分钟；完整航迹是 7760 班，列表里按需取。**为了首屏 896 KB，我们牺牲的是地图上的采样密度，不是时间覆盖。**
>
> （如果评委追问"为什么不是全部显示"）因为 7760 条航迹带点云是 7.4 MB，弱网下要转十几秒。**我们的取舍是：列表全量、地图抽样，并且把抽样率直接写在响应的 `flightStats` 里。**

### 问："切到虚拟气象，有什么区别？"

> 切过去之后**计划会自动按虚拟通道重算**——航班从 1201 班变成 1673 班，雷达避让几何从"不可用"变成"49 个采样时次的并集"，回波本身标注为 `SYNTHETIC_RADAR_CREF`。
>
> 这个开关的意义不是"换个好看的图"，而是**证明同一套算法在两种气象输入下会给出不同的调度结果**。实测通道取不到回波时（数据源对机房出口 403），我们会如实显示"不可用"，**不会用模拟数据顶替**。

### 问："这个雾区是实测的还是你们画的？"

> 是**示意**，我们标注得很清楚。雾的判据按 6 / 12 公里执行，进结论、进指标、进禁飞统计；但地图上画的是 60 / 36 公里的示意半径，因为按 6 公里画在东北三省全域视图里只有十几个像素，看不见。
>
> **界面上原话是："半径 60 / 36 km 是声明常量，不是实测雾区边界。"** 我们不希望把示意图说成实测图。

### 问："你们怎么保证改完不出新问题？"

> 三把自动尺子：全页面扫描（8 个页面逐页点开，听浏览器报错）、属性误用审计（专门查"把 prop 当 ref 用"）、工具链闸门 31 项。
>
> **上一版那个「本案例判据」面板从来没显示过，就是全页面扫描抓出来的**——它编译能过、449 条单元判据全绿、静态审计也扫不到，只有真把页面点开才看得见。

### 问："这版还有什么没做好？"

> 两件事，都已经定位到根因：
> 一是地图航迹的采样覆盖，我们刚在改；
> 二是**气象通道切换的响应链路**——后端算对了，前端取的时候撞上浏览器缓存。这个已经修好并加了验收判据（`fromDiskCache` 必须为 false）。
>
> **主动说出"我们知道哪里不好、也知道怎么改"，比说"都挺好"更可信。**

> **② 切通道不同步、手动更新失效**：后端其实**算对了**（sessionId 换了、航班 1201→1673、雷达避让从 false 变 true），是前端取的时候撞了缓存——我抓到 `fromDiskCache: true`，那个请求一个字节都没走网络。三个地方要一起改：URL 加 `&mode=`（关键）、fetch 加 `cache:'no-store'`、`planRevision` 换成会递增的号（现在恒为 `traffic-plan-v1.3`，前端 watch 判断不出变化）。约 3 小时。
>
> 这两个加起来 5.5 小时，都是演示时最要紧的动作，建议排在美化前面。如果只有 2 小时，就先改 **URL 加 `&mode=` + fetch 加 `no-store`** 这两行，切通道立刻就能用。
>
> 另外提醒一句：**别为了修这个把 600 秒缓存整个关掉**，那是首屏秒开的来源。正解是让缓存键含通道，不是取消缓存。
