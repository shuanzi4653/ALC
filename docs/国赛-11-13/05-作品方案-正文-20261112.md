## 一、作品概述

### 1.1 背景介绍

低空经济正在从飞行试验走向规模化运行。空域、航路、场站、通信导航监视、运行控制与监管构成了一条完整的技术链，而这条链上最先被"天气"卡住的是**放行**这一环：气象服务给出的是温度、能见度、风、回波等要素，运行方需要的是"这一班、这个时刻、这一段航路，能不能飞"。

现有低空气象服务大致停在三处：**看得到、算不出、不敢放**。看得到——雷达回波、卫星云图、模式产品都能上图，但图上没有一个字写"能不能飞"；算不出——即便知道前方有天气，绕过去要多花几分钟、多少电、会不会赶不上时限，没有现成的数；不敢放——放行要签字，签字的人手里只有一张彩色图，只能凭经验赌一把。真实运行因此在两个极端之间摆动：天气一变就全停，损失运力；或者硬着头皮飞，担风险。

低空运行安全保障领域的综述研究印证了这一点：气象复杂突变（强风、低能见度、局地降水）被列为基础保障类风险之一，而"安全保障体系建设不完善、复杂场景技术适配不足、实际测试验证缺失"被明确列为当前研究的共性短板（文献 [4]）。低空经济研究在 2024 年后呈爆发式增长，但研究热点集中在概念、技术与政策，**面向运行决策的闭环验证仍然稀缺**（文献 [8]）。

本作品面向上述缺口，把气象要素翻译成**可被否决的放行结论**，并为每一个结论配一份代价清单。

### 1.2 目标定位

作品定位为一套**低空交通协同运行管理系统**：以公开气象数据为输入，以逐班次、逐航段的风险概率为中间量，以四档放行结论与四种处置代价为输出，全过程可回溯、可复算。

三类使用角色与各自要回答的问题：

| 角色 | 要回答的问题 | 系统给出的东西 |
|---|---|---|
| 放行员 | 这一班现在放不放 | 四档结论（能飞 / 谨慎 / 停飞 / 数据不明）+ 依据 + 数据帧龄 |
| 现场操作员 | 现在起飞还是等这波过去 | 未来 1–3 小时的逐段风险概率与建议窗口 |
| 后台复盘 | 当时为什么这么判 | 逐条证据链、人工裁决记录、操作日志 |

目标指标分三层，均为可复算的工程指标，而非宣传口径：

| 层 | 指标 | 目标/现状 |
|---|---|---|
| 判据层 | 走廊逐段风险概率覆盖率 | 100%（每条在飞走廊每一段都有概率，缺数据时显式标"不可用"） |
| 判据层 | 概率质量（能见度 <3000 m） | AUC 0.9470、TS 0.4936、Brier 技巧 0.5053（见 §3.2） |
| 一致性层 | 云端 Python 与端侧 C 的判决一致性 | 两组各 1000 组，最大差值 6.95×10⁻⁷ / 5.73×10⁻⁷，超差 0 组，判决一致 1000/1000 |
| 工程层 | 自动化用例 | 后端 601 项、前端 506 项，全绿 |
| 效果层 | 进入不可飞走廊的架次 | 0 架次（相对关闭裁决层，−100%） |
| 效果层 | 代价 | 绕飞 2848 架次；延后 8 班共 320 分钟；延误班次占全部班次 0.1% |

**覆盖范围必须交底**：作品在竞赛阶段覆盖**全国 319 个城市、30 个省级单元、492 条航线、56 个机场**（详见 §5.1）。其中**全国层这 492 条航线为模拟派生（source: SIM），只用于态势聚合与示意，不参与运行计划与裁决**；真正跑"判据—裁决"链路的是东北运行网：36 个城市、53 条城际走廊，另含 216 条城内配送走廊。把"能算的"和"能看的"分开并各自标清楚，是本作品的一条硬纪律，而不是事后补的解释。

## 二、需求分析

### 2.1 问题剖析

作品针对的问题可以拆成三类瓶颈，每一类都能对应到已有研究的判断：

**（1）预报对象与决策对象不匹配。** 现有低空气象产品的主体是要素预报：某地未来若干小时的能见度、风、降水。近年研究把能见度预报做到了区域网格化（文献 [6]：空间分辨率 3 km、时间分辨率 1 h、时效 6–18 h）与站点级识别（文献 [7]：基于实景图像、低能见度识别准确率 95% 以上）。这些工作解决的是"这个点/这片区域未来怎样"，而运行方要判的是"这一班飞机在它预计经过的那个时刻、那一段航路上，会不会撞上危险天气"。**对象不同，中间缺一层换算。**

**（2）气象与决策之间缺一层可计算的判据。** 空域与航路规划研究已经建立了较完整的框架（空域规划、基础设施、航路构建、运行评估，文献 [1]），容量评估也形成了方法体系（文献 [3]），但研究多止于"给出规划或容量"，气象作为约束条件进入运行决策的路径仍以人工经验为主。低空运行安全保障综述同样指出，**风险识别与运行决策之间的闭环融合仍有待突破**（文献 [4]）。

**（3）缺数据时系统仍然"看着正常"。** 低空场景的观测密度远低于民航：没有每个城市的地面站，没有每条航路的实测。多数方案默认数据连续可用，一旦取不到就用默认值填、用插值补，界面上看不出差别，等于把"不知道"悄悄变成了"没问题"。这是最危险的一种失败模式，因为下游算法不认数据来源。

对应到具体攻坚难点，本作品需要解决四件事：**逐班次的时刻对齐**（不是当前时刻，而是预计经过时刻）、**沿航段的概率合成**（不是单点概率）、**规则与概率的分工**（谁一票否决、谁给概率）、**缺数据时的降级与标注**（宁可说不放行，不给一条看起来安全的路线）。

### 2.2 需求调研

需求调研分三条线，三条线互补，都不是"拍脑袋"。

**第一条，文献线。** 以"低空经济 气象保障""低能见度 机器学习 预报""低空 航路 规划 气象"三组主题在中文学术库做主题检索，分别命中 **102 条、60 条、97 条，合计 259 条**；按"是否直接对应本系统要解决的四件事"筛选，得到 14 篇作为需求与方法的参照（其中 9 篇列入 §7.3 参考文献）。文献线回答的问题是：**这个需求是否真实、别人卡在哪。** 结论是——低空气象保障是真问题（三地已在建体系，见第二条），能见度 AI 预报是真路线（已在省级业务中落地），而"气象到放行结论"这一段仍是空白。

**第二条，体系线。** 唐山、大连、宁德等地已公开低空气象保障服务体系的建设思路与实践（面向低空应用场景的气象保障服务体系建设、面向低空旅游的海雾与低能见度智能识别与短临预报等）。体系线回答的问题是：**"低空需要专门的气象保障"是否已经从研究走向地方实践。** 结论是——已经走向实践，但公开材料集中在"监测与预警"环节，"放行裁决"仍由运行方自行承担。

**第三条，自测线。** 作品在 51 天、62 个版本的迭代中保留了 **100 条问题档案**（`changelog/ISSUES.md`），其中直接来自日常使用的六类问题是需求的第一手来源：

1. 风向与航线糊在一起，看不清谁是谁；
2. 雨、雷图层把地图盖住，底图信息全丢；
3. 异常总出现在同一个地方，怀疑是固定值而非实时值；
4. 绕行线没有连到端点，看不出从哪绕到哪；
5. 同一条预警重复报，一条事件被拆成多条；
6. 停止脚本会失败，服务重启后状态不一致。

这六条都已在版本迭代中逐条修掉，并留下回归用例。自测线回答的问题是：**这些需求是不是真的有人在用的时候被绊倒过。** 辅助佐证是一份 12 题问卷（面向一线运行、气象、应急从业者与相关专业学生），回收结果以实收份数为准，列入佐证材料。

### 2.3 从需求到功能

| 需求（来源） | 功能落点 | 可验证的判据 |
|---|---|---|
| 判"这一班能不能飞"（文献线 + 自测线） | 走廊剖面：按预计经过时刻逐段给概率与四档结论 | 每条在飞走廊每段都有概率；缺数据显式标不可用 |
| 知道绕/等要付多少（自测线 3、4） | 处置代价：直飞/绕飞/延后/取消四种各算一次 | 代价清单同屏可比，绕飞里程与增时逐条可查 |

| 复盘要说得清（放行员/后台） | 证据绑定 + 人工裁决记录 + 操作日志 | 任一结论可回溯到原始数据与计算步骤 |

## 三、气象数据与人工智能技术的选择与运用

### 3.1 气象数据：三类公开源，一条处理管道

| 数据 | 来源与获取方式 | 更新粒度 | 在作品中的作用 |
|---|---|---|---|
| 逐时气象要素 | 公开气象模式接口（免密钥、逐城市） | 逐小时 | 概率模型的输入特征；逐市实况 |
| 雷达回波 | 公开雷达拼图瓦片（免密钥），像素反算经纬度 | 约 6 分钟一帧 | 直接栅格化→分级→多边形，作为"强回波禁飞区"几何 |
| 机场实测报 | 机场自己发布的观测报（公开报文） | 逐半小时/逐小时 | 端侧缓存帧的来源；模型训练标签的来源 |

处理管道（全部可复现，无人工干预）：

1. **取数**：按城市/瓦片批量拉取，失败即标记不可用，不用默认值填充；
2. **配准**：雷达瓦片为墨卡托投影，逐像素反算经纬度，与中国边界多边形求交，只保留境内回波；
3. **格网化**：按 0.04°（约 4.4 km）聚合，逐格取最大反射率档；
4. **闭运算**：栅格层先膨胀后腐蚀，补单格孔洞与缝隙；几何层再磨角，避免"方块拼出来的多边形"；
5. **分级成环**：按阈值累计成三档（弱/中强/强），保证强回波一定落在中强里、中强一定落在弱回波里——这是真实雷达回波的形态特征，也是"看起来像回波图"的前提；
6. **裁剪与限流**：按面积排序截断，截断数量在界面显式写出，不悄悄丢弃。

**数据诚实性作为设计准则**：凡是系统在缺失外部输入时仍然给出画面或结论的路径，都在界面与数据结构两处标注来源性质——虚拟雷达帧标 `SYNTHETIC_RADAR` 并显示橙色警示条；断网时的离线底图显示橙色徽标与重试按钮；取不到气象的城市不插值、不补默认值，直接标"不可用"。理由很直接：下游几何与判定代码不区分来源，不标注的合成数据会被当成实测数据算进去，这不是审美问题，是会算错的问题。

### 3.2 概率模型：三个目标、一套特征、同一段时间切分

模型为梯度提升树集成（100 棵决策树、26 维特征、公开的保序校准方法），三个目标分别对应"注意级能见度、禁飞级能见度、强阵风"。训练与验证按时间切分（不随机打乱），测试集 26193 个样本。

| 目标 | 阈值 | 正例率 | 查全 POD | 空报 FAR | TS | Brier 技巧（相对气候基准） | AUC |
|---|---|---|---|---|---|---|---|
| 能见度 <3000 m（注意级） | 3000 m | 6.33% | 0.6741 | 0.3517 | **0.4936** | **0.5053** | **0.9470** |
| 能见度 <1000 m（禁飞级） | 1000 m | 0.77% | 0.4653 | 0.6357 | 0.2568 | 0.2179 | **0.9528** |
| 阵风 >10 m/s | 10 m/s | 3.50% | 0.4460 | 0.5597 | 0.2846 | 0.2508 | **0.9358** |

三条基线同口径对照（持续性基线、公开模式产品、阈值规则），指标定义与原始混淆矩阵见 `data/training/metar/model-v2-metrics.json`。

读这张表要抓三点：第一，三个目标的 AUC 都在 0.93–0.95，说明**排序能力**（把危险时段排到前面）是可靠的；第二，Brier 技巧为正，说明概率是**校准过的**，可以直接用来做代价比较，而不是"分数越高越危险"的排序分；第三，禁飞级正例率仅 0.77%（202 个正例），TS 在这一档本身不是好指标，作品的用法是**用校准概率去算期望代价**，而不是用 TS 排名次。

### 3.3 大模型：只做取证与解释，不参与任何一次放行判断

大模型在作品中的角色被严格限定为**证据检索与语言生成**：

- 回答前，系统先执行五个取证工具（任务上下文、气象证据、候选方案、路线决定、规则引用），把证据取出来；
- 大模型只能从已取出的证据里挑选与组织语言，回答必须带引用；
- **它不改航线、不绕过禁飞区、不替人放行**。把它整段拿掉，结论一个字都不变。

实测 50 题真实调用：39 题正常返回、11 题因连接超时降级为模板回答，降级样本同样保留在记录里（`docs/evaluation-v1/ai-50-real.json`）；预设证据覆盖 50/50。作品不把"证据覆盖率"当作"回答质量评分"，两者不是同一件事。

### 3.4 端侧模型：同一份模型、两套运行时

端侧节点解决的是"断网那一小时"的问题：联网时按时间缓存机场实测帧，断网后用本地缓存帧推理，屏幕永远显示"这帧是几点、已经过了多久"，不假装数据是新鲜的。

技术上的关键不是"把模型压小"，而是**这个模型结构本来就能跑在单片机上**：导出为 float32 C 数组，用迭代下降替代递归，免栈、无动态内存；叶子存两个数（不省这 96 KiB，因为云端实现确实做了两次除法，少存一个会在最后几个 ulp 分叉）。

验证方式是对拍：同一批 1000 组特征，云端 Python 与端侧 C 各跑一遍。

| 指标 | 全国口径 | 三站口径 |
|---|---|---|
| 用例数 | 1000 | 1000 |
| 最大偏差 max\|Δp\| | **6.95×10⁻⁷** | **5.73×10⁻⁷** |
| 超差组数（容差 1×10⁻⁴） | **0** | **0** |
| 判决一致（阈值 0.3） | **1000/1000**（正例 728/728） | **1000/1000**（正例 752/752） |
| 单次判决耗时 | 端侧 C 3.93 µs ／ 云端 Python 152.36 µs | 4.18 µs ／ 182.87 µs |

**口径边界（必须与结果同句出现）**：上述结果是在 **x86 等价编译目标**上、用同一份 C 代码（MSVC /O2）跑出来的；**端侧板卡尚未烧录**，因此材料与答辩只表述为"同一份 C 代码在等价编译目标上验证通过"。20 毫秒是设计余量，不是实测值；实测端侧单次判决为 3.9 微秒。硬件状态统一表述为：**方案已冻结 · 端侧固件核心已实现 · 对拍验证通过 · 整机装配待完成。**

## 四、项目实施

### 4.1 总体方案

系统为五层结构，每层可单独打开、单独验证：

```
数据（公开模式 / 雷达回波 / 机场实测报 / 城市与机场底册）
  ↓
算（按预计经过时刻，把站点读数摊到航段上 → 逐段不可飞概率）
  ↓
判（概率 + 规则：禁飞区、净空、边界、续航、时限 → 四档结论）
  ↓
决（直飞 / 绕飞 / 延后 / 取消，四种各算一次代价，挑可执行且最省的）
  ↓
留痕（结论绑定原始数据、计算步骤、规则版本；人工裁决单独记账）
```

右侧并列一条**端侧支路**：断网时由本地节点完成单点判决，决策粒度从全网降到单点，链路不经过任何服务器。

工程实现上，前端为 Vue 单页应用（四级下钻地图、时间轴、证据面板），网关为 Java 服务（鉴权、路由、渠道切换），算法与数据为 Python 服务（几何、概率、判据、证据存储），端侧为纯 C99。

**全国网与运行网的关系（主动交底）**：全国层提供 319 城、30 个省级单元、492 条航线的态势聚合与四级下钻（全国 → 大区 → 省 → 市），航线由公开规则生成（省内连成树保证连通、无机场城市补一条接驳、跨省只留少量通道），**source 标记为 SIM，不参与运行计划与裁决**；裁决链路跑在东北运行网（36 城 53 条城际走廊 + 216 条城内配送走廊）上。这样做的原因很直接：给三百多个城市各配一份真实航班数据做不到，硬编就是造假，所以把"能算的"和"能看的"分开，并各自标清楚。

### 4.2 实施规划

### 4.3 实施过程

**数据处理。** 三类公开源分别建立取数—校验—缓存链路；雷达瓦片按墨卡托反算并裁剪到国境；城市与机场底册按"是否纳入通航范围"显式排除 4 个省级单元（台湾、西藏、香港、澳门），并把"距境外不足 50 km"的 11 个城市整体退出通航范围（避免把航路压到边界线上）。

**模型开发。** 三个目标共用一套特征与时间切分；校准用公开的保序回归；训练/验证/测试严格按时间切分，测试集只用于最终评估。

**系统实现。** 前端承担四级下钻与证据呈现；后端承担判据与代价计算；网关只做鉴权与路由，不参与判定。所有"能改结论"的开关（情景、气象渠道、运营角色）都在界面上标明影响范围。

**测试验证。** 分三层：判据层（同一条走廊、同一份气象，只按观测判 vs 加上概率判，差别同屏可比）、一致性层（端云对拍两组各 1000 组）、工程层（后端 601 项、前端 506 项自动化用例）。

### 4.4 关键环节

#### 4.4.1 核心创新层级：系统级 + 应用级

**核心创新层级：系统级 + 应用级。**

**为什么不是模型级。** 模型本身不是本作品的贡献：用的是现成的梯度提升树（100 棵、26 维特征），校准用的是公开的保序方法，特征工程参照了公开的气象与航空文献。我们没有提出新的模型结构、新的损失函数或新的训练范式，因此不主张模型级创新。

**系统级创新在哪。** 在于把"按飞行时刻沿走廊采样 → 逐段概率合成 → 四档判据 → 四种处置比代价 → 每一步绑定证据"串成了一条**能跑、能复现、能被否决**的链路。这条链的每一环单独看都不新，合起来才成立：缺了时刻对齐，概率就与航班无关；缺了代价比较，"不能飞"就只是拒绝而不是决策；缺了证据绑定，结论就无法被追责。

**应用级创新在哪。** 在于把气象从一个**图层**，变成了一个**带代价的放行结论**，并且全国、省、市、机场四种尺度用的是同一套几何与同一套判据——同一件事只有一个答案，不因页面不同而变。

一句话概括：不是造了一把更好的尺子，而是用现成的尺子造了一条能被追责的流水线。

#### 4.4.2 与主流方案的定性对比

下表每一行的左列都能指到具体文献，右列都能指到系统里具体一页。**这里写的是用途不同，不是高下之分**——单站深算与全网可下钻是分工。

| 维度 | 主流做法（有文献支撑） | 本系统 | 差别一句话 |
|---|---|---|---|
| 预报/判据对象 | 面向区域网格或站点的要素预报：能见度做到 3 km/1 h、时效 6–18 h（文献 [6]），站点级识别准确率 95% 以上（文献 [7]） | 面向**走廊逐段、按预计经过时刻**的风险 | 主流答"这个点未来能见度多少"，本系统答"这班飞机在那个时刻飞过那一段安不安全" |
| 气象与决策的关系 | 气象作为**服务与图层**，决策由人看图判断；研究亦指出风险识别与运行决策的闭环融合仍待突破（文献 [4]） | 气象直接产出**四档结论 + 代价清单** | 主流停在"给信息"，本系统做到"给结论并标代价" |
| 空间尺度 | 单城/单区域深算：航路规划框架（文献 [1]）、容量评估方法（文献 [3]）精度高、算力重 | 全国 319 城聚合 + 省市下钻，全国层只传聚合量 | 主流在单点做深，本系统在全国做**可下钻的浅层**，用途不同 |
| 数据缺位时 | 多数方案假设数据连续可用；综述亦指出实际测试验证缺失（文献 [4]） | 断网/缺数据时降级为单点判决，屏上标数据帧龄；"数据不明"本身就是一档结论 | 主流较少讨论"数据没了怎么办"，本系统把它做成一等功能 |
| 风险边界 | 风险评估多按"概率 × 后果"给出风险值（文献 [4] 的风险分类与安全保障技术体系） | 净空按等级分段、绕不开就停飞并记原因；给出可裁决的等级与台账 | 主流给风险值，本系统给**可裁决的等级与台账** |

#### 4.4.3 净空与绕飞代价：让"避开"有一个价

低空飞行最硬的约束是机场净空。作品把机场净空做成几何并参与航线计算：

- **规模**：287 个机场净空限制区（含 10 条跑道的梯形净空），合计约 35283 km²，覆盖陆域约 0.37%；
- **来源分级**：东北站点使用官方公布的几何（OFFICIAL）；全国其它机场按公开的跑道方位与机场等级**规则化推算**（DERIVED），界面与材料均标注"非官方公布"，两类**分开计数、不合并**；
- **穿越审查**：按当前等级（可申请穿越）求交，492 条航线中 113 条与限制区相交（23%），逐条列出相交的限制区与机场，作为待审清单。

代价的计算口径：关闭裁决层 vs 打开裁决层，同一份气象、同一批班次，只改这一层。

| 指标 | 结果 |
|---|---|
| 进入不可飞走廊的架次 | **0**（关闭时为正数，降幅 **−100%**） |
| 绕飞代价 | **2848 架次** |
| 延后代价 | **8 班**、合计 **320 分钟**（平均每班 40 分钟） |
| 延误班次占全部班次比例 | **0.1%** |

这是作品最想给运行方看的一页：不是"我们避开了"，而是"避开要花多少"。

## 五、应用成效

### 5.1 成果展示

系统为一套可运行的四级态势与决策系统，主要规模指标如下（全部可由数据文件复算）：

| 指标 | 数值 | 说明 |
|---|---|---|
| 覆盖城市 | **319** | 纳入通航范围的地级及以上城市 |
| 省级单元 | **30** | 明确排除台湾、西藏、香港、澳门 4 个单元 |
| 航线 | **492** | 省内 201 + 机场接驳 261 + 跨省 30 |
| 机场 | **56** | 航线网中带机场代码的城市；无机场市 263（专用接驳） |
| 边境退出通航 | **11** 城 | 距境外不足 50 km，整体退出通航范围 |
| 净空限制区 | **287** 个 / 35283 km² | 规则化推算，非官方公布 |
| 运行网（裁决） | 36 城 · 53 条城际 + 216 条城内配送 | 东北运行网，跑真实判据与裁决 |

界面四屏与各自回答的问题：**态势**（未来 6 小时哪片天不能飞）、**走廊**（这条走廊几点能飞、凭什么）、**处置**（一批事件该怎么做、谁在什么时候飞）、**推演与日志**（一条走廊怎么被判成不可飞、每次操作留痕可回放）。

### 5.2 效果验证

**（1）判据层：同一份气象，加不加概率，差别同屏可比。** 同一条走廊、同一份观测，"只按观测判"与"加上概率判"的差异摆在同一页，谁都能看，不靠叙述。

**（2）一致性层：端云同源对拍。** 两组各 1000 组（全国口径 / 三站口径），最大偏差 6.95×10⁻⁷ / 5.73×10⁻⁷，超差 0 组，判决一致 1000/1000（详见 §3.4）。跑两组的原因：模型由三个机场的数据训练，要证明它在没见过的城市上也稳。

**（3）工程层：自动化用例全绿。** 后端 601 项、前端 506 项。

**（4）服务层：云端验收 37 项通过、0 失败、0 跳过；云端历史实例连续运行约 14.9 天。**

**（5）部署口径（须与材料一致）**：**本机实例 + 云端历史实例**。现场演示跑的是本机同一套程序；云端另有一个历史实例，它的作用是证明这套服务能连续运行十几天不重启，**不表述为"线上就是本套"**。若后续重新部署并跑通远程验收，本条改为"线上即本套，验收 37 项全过"，并同步更新佐证截图。

**（6）评测的边界（主动交底）**：作品**没有真实飞行验证**，全部为离线复核——路线算完后，用独立的时间步长再检查一遍有没有穿过危险区。这能证明算法自洽，不能证明真机安全。

### 5.3 应用价值

| 对象 | 价值 | 依据 |
|---|---|---|
| 放行员 | 从"看图凭经验"到"看结论签字"，且知道数据有多新 | 四档结论 + 帧龄 + 证据链 |
| 现场操作员 | 知道"等这波过去"要等多久 | 未来 1–3 小时逐段概率与建议窗口 |
| 运行单位 | 延误与绕飞有了可报价的中间态，不再是"全停或硬飞" | 绕飞 2848 架次、延后 8 班 320 分钟、延误占比 0.1% |
| 监管/复盘 | 每一次判断可回溯，人工干预单独记账 | 证据绑定 + 裁决记录 + 操作日志 |
| 工程复用 | 同一份模型可下沉到低成本节点，断网仍可判决 | 端云对拍一致（§3.4） |

边界同样明确：**作品给建议，不给许可**；空域能不能飞，仍由空管与运行单位决定。

## 六、总结与展望

### 6.1 经验总结

三条做对了的事：

1. **先定判据，再谈界面。** 四档结论的定义、阈值来源、缺数据时的行为，都是在写第一行界面代码之前定下来的；后续所有页面只是同一套判据的不同读法。
2. **把"数据诚实"当功能做，而不是当文案写。** 来源标签、帧龄、橙色警示条、"数据不可用"的显式空态，都是代码里的一等公民，且有回归用例守着。
3. **对拍而不是"我觉得一致"。** 端云一致性用两组各 1000 组数据量出来，并且把过程中抓到的两个真问题（阈值量化方向、Python 侧读文件未量化到 float32）写进报告——首轮 40/1000 超差、修正后降到 6.95×10⁻⁷，这个顺序说明的是"错在哪、怎么改"，不是"调容差蒙过去"。

三条不足（与 §5.2 的边界同源）：

1. 没有真实飞行验证，全部离线复核；
2. 交通班次与订单为模拟生成，不是真实航班；
3. 全国 492 条航线为示意，不参与裁决；机场净空除东北外为规则推算，非官方公布；本地没有全覆盖的地形与建筑高度，净空状态显示"条件未验证"而非"已通过"；端侧固件核心已实现并完成对拍，**整机装配待完成**。

### 6.2 未来规划

1. **真实数据接入**：优先接入试点城市的真实航班与空域审批数据，把"能算的"从东北扩到有数据的地方，而不是先扩地图。
2. **整机装配与实地比对**：完成端侧节点的整机装配，在示范点做"同一天气、同一批班次"的云端—端侧实地比对，把"等价编译目标一致"推进到"实机一致"。
3. **净空几何升级**：以官方公布的机场净空数据替换规则推算几何，并把地形与建筑高度纳入，使"条件未验证"变为"已验证"。
4. **代价模型细化**：把机型风致能耗、垂直空域容量纳入代价计算，使"绕/等"的比较从里程与时间扩展到能耗与容量。
