## 0. 一句话定位

> 它是一个**低成本、可密集布点的边缘决策节点**：把机场 METAR 实测帧缓存在本地，断网时用端侧模型自己做"能不能飞"的四档判决，并外推未来 1–3 小时的风险概率；判决链路不经过任何服务器，**20 毫秒级**。

**它存在的唯一理由是**：把"断网也能决策"从**说法**变成**可当场验证的事实**。软件本身一个功能都不少——硬件不补功能缺口，只补"凭什么信"。

## 1. 是什么 / 不是什么（最先要背的一张表）

| 是 | 不是 |
|---|---|
| 地面**固定节点**（起降点值班室） | 机载设备（未做供电/振动/电磁/适航验证） |
| **离线决策**子节点 | **气象观测站**（自带 BME280 只做开机自检） |
| 云平台的**降级兜底** | 取代云平台 |
| 给出**四档建议** | **自动放行系统**（放行仍由人决定） |
| 单点可用性判断 | 全网航路重规划 |

## 2. 部署位置（三层，别混着讲）

| 层级 | 位置 | 依据 |
|---|---|---|
| **示范点**（现在做） | 沈阳 / 长春 / 哈尔滨三地**城市起降点（vertiport）值班室** | 模型只覆盖 ZYTX/ZYCC/ZYHB 三站；这三地正是三个**运行态省份**，走廊与节点对得上 |
| 扩展（讲规划） | 216 条**城内配送走廊**末端起降点 | 这些点没有气象席位、没有专线，断网即失明，是真实痛点 |
| 演进（只放展望） | 机载 / 车载 | 需先过供电与振动验证，**当前不做** |

**为什么不放机场塔台**：塔台已有气象席、备份通信与 UPS，再放一个"断网兜底"是重复建设，兜底无意义。痛点在最末端——那里没人看得懂 METAR 原文。

**物理安装**：放桌上即可。**不立杆、不布线、不改市电、不做防雷**（电池供电、USB 充电、透明盖直接看屏）。这是 372 元能密集布点的前提。

## 3. 给谁用、怎么用

| 角色 | 看什么 | 做什么决定 | 要懂模型吗 |
|---|---|---|---|
| **放行员**（值班调度） | 屏上四档 + 数据龄 | 放行 / 等待 / 转人工复核 | 不需要，只看颜色 |
| **现场操作员**（操控、地勤） | 按键切"未来 1–3 小时" | 现在起飞还是等这波过去 | 不需要 |
| **云端后台** | 恢复后看补传台账 | 复盘、追责、调走廊参数 | 需要 |

**三种状态（30 秒能讲完）**

| 状态 | 屏上 | 行为 |
|---|---|---|
| **ONLINE** | 绿点 | 每 5 min 上报；取参数指纹、校时 |
| **DEGRADED** | 黄点 + 数据龄 | 用上次帧继续算；上报进队列等重试 |
| **OFFLINE** | 红点·离线自治 | 本地判决照出；按键看推演；恢复后补传 |

## 4. 断网时到底发生什么（评委必问，逐条对应）

| 问题 | 答案 |
|---|---|
| 气象数据哪来？ | **断网前缓存的 METAR 实测帧，按原始时序存 ≥7 条**，掉电不丢，每帧带 `ts` + `source`。**不是自己采的** |
| 断网多久判定？ | 连续 **10 min** 无成功请求 → OFFLINE |
| 未来 1–3 小时怎么算？ | 模型本身是 nowcast（`t+1h..t+3h`，leadTime 中位 120 min），**从当前帧往后外推，不需要新数据** |
| 时间基准哪来？ | 断网前校时（**UTC**）；断网重启必须从 **NVS 恢复最后已知时间**，否则 `hourSin/hourCos` 整体偏 |
| 规则会不会过期？ | `rules-v1.json` **指纹校验**，不符即拒绝裁决 |
| 航路规划做不做？ | **不做全局重规划**。降的是决策**粒度**（全网最优 → 单点可用性），不是能力 |
| 数据怎么回来？ | 环形 **500 条**，去重键 `node+seq`，退避 5s→30s→120s，**时间戳原样保留** |
| 数据新鲜度怎么交代？ | 屏上永远显示**帧来源 + 数据龄**；没有来源的数字不许上屏 |

## 6. 三句可直接背的标准表述

**① 定位**
> 它是一个低成本、可密集布点的边缘决策节点：把机场 METAR 实测帧缓存在本地，断网时用端侧模型自己做"能不能飞"的四档判决，并外推未来 1–3 小时的风险概率；判决链路不经过任何服务器，20 毫秒级。

**② 断网机制**
> 联网时它取帧、校时、校验规则版本；断网后不取新数据，用本地缓存帧推理，屏上标着帧来源和数据龄——**它不假装数据是新鲜的**。

**③ 模型可移植**
> 同一份模型，两套运行时：云端 Python 与端侧 C。端侧用迭代下降替代递归，免栈无动态内存，单次完整裁决 ≤20 ms；1000 组特征对拍 `max|Δp| < 1e-6`。它不是把模型压小塞进去，是**这个模型结构本来就能跑在单片机上**。

---

## 7. 模型移植：三件真实的工程动作（不是"压缩"）

1. **导出成 C 常量数组**：`format=alc-forest-v1`，**100 棵树、26 维**，树是嵌套数组 `[特征下标, 阈值, 左, 右]`，叶子存一对概率 `[p_neg, p_pos]`（不是标量）。
2. **迭代下降代替递归**：`while (n->feature != 0xFF)` 一路向下，**免栈、无动态内存**——这是能在 240 MHz 上稳跑的关键。
3. **阈值导出时就 round 到 float32**：否则 double 阈值与 float 特征比较，边界样本走错分支，`Δp` 跳 1e-2。

**为什么不是"压缩"**：100 棵树本来就是百 KB 级；16 MB flash 装得下，**文档明确"不做体积判据"**。主动说"我们没有做无意义的体积优化"，比硬凑压缩率更像工程判断。

## 8. 明确不做的两件（已决策，不再讨论）

| 项 | 结论 | 理由 |
|---|---|---|
| **int8 量化** | 主链不做 | 会破坏端云一致性判据（对拍误差会落到 1e-3~1e-2）；flash 无收益；重做推理+对拍 1–1.5 人日 |
| **蒸馏** | 不做 | 对 GBDT 无标准做法，会换掉模型结构；92 点校准、四档阈值、`operatingThreshold=0.3` 全部要重标；2 人日以上且精度必掉 |

> 若日后要做，只能做**并列对照版**（主链仍 float32 + 1e-6），报告里报"误差 X、提速 Y、因无体积收益故不采用"。

---

## 9. 待补的两条规则（当前文档缺口）

1. **数据龄分级**：>90 min 打"时效过期"标；>180 min 只显示最后一次判决并标"不再更新"。现状只定义了 10 min 进 OFFLINE，**没定义数据龄上限**——这是个可被追问的点。
2. **NVS 时间恢复**：断网重启后必须恢复"最后已知时间 + 单调计数"，否则 UTC 时间基准丢失，全部判决作废。

## 10. 数字口径（只引稳定值）

| 项 | 值 |
|---|---|
| 端侧模型 | **100 棵树 / 26 维 / 1000 组对拍误差 <1e-6 / 单次裁决 ≤20 ms @240 MHz** |
| 缓存 | METAR 实测帧 **≥7 条**，补传环形 **500 条** |
| 状态切换 | 连续 **10 min** 无成功请求 → OFFLINE |
| 四档 | BAN ≥0.8 / CAUTION ≥0.5 / WATCH ≥0.2 / FIT；`p_unsafe = 1-(1-p_vis)(1-p_gust)` |
| 观测档直判 | `vis<1000 m` 或 `gust>11.5 m/s` → BAN；`vis<3000 m` → CAUTION |
| 两个风阈值 | 模型目标 **阵风>10 m/s**；业务限飞 **11.5 m/s**——**不要混着讲** |
| 覆盖 | 仅 **ZYTX / ZYCC / ZYHB** 三站，其他站 `stationCode = -1` |
| 成本 | **¥371.5**（13 项，实际下单口径；不再提 277） |
