## 3. 我改了执行方案的三处判断（附理由）

1. **W-14 不赌"重跑调度"**。`data/traffic/cases/fog-20250105.json` 只有 `history`（7h×3 站 METAR）与 `frames`，**没有雷达瓦片**；而 `service.session()` 的调度链里是 `_radar_avoidance → weather_control.radar_frame → cma_tiles`。真跑只有两条路：跳雷达层（处置口径与实时不同源）或造雷达帧（造假）。**两条都不接受**，所以改明写边界。

2. **W-17 先修计数，不重写对照**。P0-4 的直接病因是 `diverged` 漏计 `obs_ban`，30 分钟能修。修完后"改判 3048 / 暴露 −3016"自洽，代价是必须承认"这一天概率档贡献 0"——但这是**真话**，比一个 8 小时新写的对照组更可信。

3. **W-13 只改前端 + 修网关**。执行方案建议新建 `app/traffic/context.py` 统一解析 `case`。架构方向对，但后端 4 个接口本来就有 `case_id` 形参 —— 缺的是前端没传、以及 Java 网关没透传。新建一层是重构，不是修 bug。
