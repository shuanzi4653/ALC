# AIC V1.0.2 更新方案

> 编制：2026-11-11　|　基线：V1.0.1（`dd1fdde` / tag `v1.0.1`）
> 依据：① 用户 2026-11-11 提出的 11 条问题；② `docs/国赛方案-v3-全国净空与端云.md` 比对；③ **外部测试报告 7 条 + 2 条口径已并入（见 §1.3 / §12）**
> 状态：**已合并，可开工**
> 范围约定：硬件/端云节点本版**不做**（只保留已落地的 `/api/edge/*` 接口，`edge.enabled=false`），版本号推进到 1.0.2

---

## 0. 一句话结论

V1.0.1 的问题不是"全国层没做好"，而是**全国层只做成了一个 tab，整个系统仍然是东北那套**。

11 条问题里有 8 条是同一个根因的变形：`home` / `overview` / `weather` / `alerts` / `assistant` / `profile` / `card` / `reference` / `history` 这 9 个视图全部由 `OperationsConsole` 渲染，而它只吃东北的 `session` / `network` / `flights` / `weather`；全国能力只铺到了 `national` 一个 tab，外加 `briefing` / `schedule` 靠 `scope==='nation'` 分支蹭进去。

所以 V1.0.2 的主线不是"再修几个 bug"，而是：

> **把"全国 → 大区 → 省 → 市"从一个页面，提升为贯穿全部五个入口的统一作用域。**

在此之上叠加**两项主增量**（来自 v3 与用户新诉求）：

1. **机场净空扩到 240 机场**（v3 §3，现只有东北 69 站点），并给出穿越台账与绕飞代价；
2. **三维全层级**（用户定：全国/大区/省/市都能立体，不是东北特供）。

**外部测试补了一刀**：报告实跑确认了 12 条核心断言全部成立（319 城 / 492 航线 / 18.2 km 几何越界 / AUC 0.9488 / 22.7 万样本），底子是扎实的；但它同时戳中 7 处**降级表达的造假**——最典型的是"雷达抓不到数据"和"雷达抓到了但这一帧没压线"在取证链里输出完全一样，而且都标 `DERIVED`。这类问题不修，整条证据链的可信度就不成立。所以本版新增一条硬纪律（§2.1 降级三态），它是修 bug，也是修方法论。

### 1.1 关于问题 1 的"比例失调"（单独说）

截图里首页的问题是**两个叠加**：

- **纵向被指标卡吃掉**：顶部三张大数字卡（需复核走廊 / 已触发放行 / 平均提前量）各占约 90 px，地图只剩约 300 px 高；
- **横向比例不匹配**：中国版图宽高比约 1.28，容器是 2.4 以上，SVG 只能居中，两侧各留一大条黑边——不是"没铺满"，是**版图装不进这个扁容器**。

V1.0.2 的处置不是继续调 `max-width`（V1.0.1 期间为这件事反复了四轮），而是换布局范式：**地图占左列、按容器高度反算宽度；指标与分级块进右栏**。即沿用 `NationPanel` 已经验证过的那套（`grid-template-columns: minmax(0,1fr) 560px`），让首页与全国台**用同一个壳**。

### 1.2 关于问题 7 的"处置没跟随"（需要额外说明一个级联）

截图里 269 个合并事件、7760 班全部停飞、8 张卡片内容完全相同（"气象中断 / 影响班次 32 班 / 走廊 1.01→1.01"）。这**不是 269 个真实事件**，是同一事件被逐走廊复制：

- `OperationsConsole` 在 `session.scenario !== 'live'` 时，对每条走廊各生成一条"气象中断"记录；
- 卡片字段全部取自走廊模板，走廊里程相等（1.01→1.01），所以看上去一模一样。

治本有两条，缺一不可：

1. **全国层不依赖东北 session**（一个城市的低能见度不该让 7760 班全停）；
2. **事件按成因+空间聚合**：一条"气象中断"覆盖 N 条走廊时，合成一张卡，卡内列影响清单（前 5 条 + 展开）。

### 2.1 降级三态纪律（本版新增，硬约束）

外部测试报告指出的 B01 / B02 / B07（外加 B06 的一半）是同一个病：**数据没了，界面上说的还是"有"**。
V1.0.1 里这类地方不止三处，所以本版不逐条打补丁，先立一条纪律，再按纪律全仓过一遍。

**三态定义**（缺一不可，且必须能区分）：

| 态 | 含义 | 界面必须写 | 来源标签 |
|---|---|---|---|
| **OK** | 拿到了，且算过 | 具体数值 / 具体结论（"穿回波 12 km"） | `PUBLIC` / `DERIVED` |
| **EMPTY** | 拿到了，但确实没有 | "本帧无回波压线"（是**结论**） | `DERIVED` |
| **ABSENT** | **没拿到** | "回波数据不可用（本帧未取到）" | `ABSENT` |

**三条落地规则**：

1. **禁止用"没有"描述"没拿到"**。`EMPTY` 与 `ABSENT` 的文案必须不同，且 `ABSENT` 一律用 `ABSENT` 标签（已有 `SOURCE_BADGES.ABSENT`，V1.0.0 就定义了，一直没被用起来）。
2. **降级要留原因**。`except` 不许静默返回空——至少把异常摘要挂到载荷里（`modelCard.error` / `radar.error`），前端能显示"取不到，因为 429"。
3. **降级要有年龄**。任何"旧数据"必须同时给"旧到什么程度"，超过硬线（气象 6 小时）就不交旧数据，如实返回空。

**适用范围（本版必查）**：雷达回波、模型概率、逐市实况、净空几何、METAR 报文、大模型取证、边缘节点状态。
每一处在验收时都要能回答："这里如果是没拿到，界面上写的是什么？"

> 这条纪律比修三个 bug 重要——V1.0.1 的口径标签（`SIM/PUBLIC/DERIVED/OFFICIAL/ABSENT`）设计是对的，
> 问题是 `ABSENT` 从来没被真正用上。用起来，标签体系才成立。

## 3. 架构主线：全局作用域（Scope）总线

这是 V1.0.2 唯一的结构性改动，其余都是在它上面挂东西。

### 3.1 状态定义

```js
// frontend/src/traffic/scope.js（新建）
export const SCOPE = {
  level: 'nation',   // nation | region | province | city
  id: '',            // region: 'north' | province: '河北省' | city: '石家庄市'
  label: '全国',
}
```

**唯一来源**：`store.scope`。任何页面要"当前看哪一级"，只读这里，不许自己从 URL 或 props 推断。

### 3.2 三条规则

1. **写在 URL 里**：`#/situation/home?scope=province:河北省`。刷新、分享、评委点链接都能还原同屏——V1.0.1 的下钻状态一刷新就丢，这在现场演示是硬伤。
2. **切层即清选择**：换 scope 时清空 `selectedId` / `selectedCorridor` / `followId` / 取证结果，避免"跟着上一级那架跑"（V1.0.1 已在 `NationPanel` 内做过，现在提升到全局）。
3. **下钻只有一个入口**：地图点区块、右栏点条目、命令面板输入地名，三条路径都调 `setScope()`，不许各自 `router.push`。

### 3.3 各视图的作用域行为

| 视图 | 全国 | 大区 | 省 | 市 |
|---|---|---|---|---|
| `home` 态势首页 | 全国航线图 + 分级块 + 气象 + 一屏结论 | 本区放大 + 本区各省 | 本省城市 + 跨省对端 | 本市 + 相邻 |
| `overview` 运行总览 | 全国放行队列 | 本区 | 本省 | 本市 |
| `weather` 气象监测 | 全国逐市实况 + 回波 + 雾区 | 本区各市 | 本省各市 | 本市 |
| `profile` 走廊 | 全国 492 条可选 | 本区 | 本省 + 跨省 | 本市出发 |
| `briefing` 运行情报 | 全国班次 | 本区班次 | 本省班次 | 本市班次 |
| `alerts` 处置 | 全国事件 | 本区 | 本省 | 本市 |
| `schedule` 台账 | 全国 106 在飞 + 90 待飞 | 本区 | 本省 | 本市 |
| `assistant` 取证 | 全国任意班次 | 本区 | 本省 | 本市 |
| `card` 推演 | 全国任意城市/班次 | 本区 | 本省 | 本市 |

### 3.4 导航重组（回应问题 1 / 2 / 3）

现状：`态势` 下有 4 个 tab（`home` / `overview` / `national` / `weather`），全国藏在第 3 个。

改为 **3 个 tab，全国是默认**：

```
① 态势
   ├─ 全国态势   ← home（吸收 national，成为默认首屏）
   ├─ 运行总览   ← overview（当前作用域的全域视图）
   └─ 气象监测   ← weather（当前作用域）
```

- `national` 从导航移除，**深链 `#/situation/national` 保留并重定向到 `home`**（外部测试说明里给过这个链接，不能让同学点到 404）；
- `home` 不再用 `HomeStage` 的三省壳，改用全国壳：布局见 §1.1（左图右栏），三维见 §5.4（四级通用）。

> **已定（用户 2026-11-11 确认）**：三维**不是东北专属**，要升级为**四级通用** ——
> 全国能立体、大区能立体、省能立体、市能立体。`HomeStage` 那张东北三维图不作为"东北特供"保留，
> 而是被**通用的三维视图**取代（见 §5.4）。

## 5. 1.0.2 新增能力

### 5.1 机场净空扩到 240 机场（v3 §3，本轮主增量）

### 5.4 三维全层级（用户 2026-11-11 确认，本轮第二个主增量）

**目标**：全国、大区、省、市**四级都能立体**，不是东北特供。

**必须先说清 V1.0.1 的失败原因**，否则会重犯。V1.0.1 期间做过 `NationGlobe.vue`（maplibre + pitch 52 + `fill-extrusion` 城市体块），两次把 Edge 主线程拖到完全无响应——截图、点击、扩展通信全部超时，只能手动关标签。

当时的判断是"全量重建太频繁"，但那只解释了一部分。真正的怀疑是：**这台机器的 Edge 跑在软件渲染（SwiftShader）上**，没有 GPU 加速，WebGL 三维的每帧 depth buffer 都在 CPU 上算。所以 V1.0.2 的第一件事不是写三维，是**先测**：

```js
const gl = canvas.getContext('webgl2') || canvas.getContext('webgl')
const info = gl.getExtension('WEBGL_debug_renderer_info')
const renderer = gl.getParameter(info.UNMASKED_RENDERER_WEBGL)  // 含 "SwiftShader" 即软件渲染
```

**四条护栏，缺一条就会重复上一次的卡死**：

| # | 护栏 | 判据 |
|---|---|---|
| 1 | **能力探测** | 软件渲染一律不进三维，直接平面 + 明确提示"当前浏览器未启用硬件加速" |
| 2 | **要素按层级裁剪** | 见下表，全国层**不画** 319 个城市体块 |
| 3 | **帧率看门狗** | 连续 3 秒 fps < 20，自动降级到平面并提示原因，不在卡死里耗 |
| 4 | **DEM 只在近层用** | 全国层地形起伏在屏幕上不到 2 px，纯耗带宽；只在省/市层挂 `raster-dem` |

**每级画什么**（这是不卡的关键）：

| 层级 | 面 | 线 | 体块 | 地形 |
|---|---|---|---|---|
| 全国 | 34 省界 + 南海 inset | 492 条航线（line） | **不画**（只 31 省会做柱） | 不挂 |
| 大区 | 本区省界 | 本区航线 | 本区省会 | 可选 |
| 省 | 本省省界 + 邻省淡底 | 本省 + 跨省航线 | 本省地级市 | 挂（R=8/5 km 净空圈一起立起来） |
| 市 | 本市范围 | 本市出发航线 | 起降点 + 净空区 | 挂 |

> 净空区在三维里立起来（`fill-extrusion` 圆柱），是这一版最好的演示点：**"绕开机场"这句话在平面上是两条线，在三维里是一个柱子和一条绕开它的弧**。

**技术选型**：继续用 maplibre（已在 `package.json`，V1.0.0 的 `CityTrafficMap` 在用），不引入 three。`fill-extrusion` + `terrain` 够用，且省一套渲染管线。

**"暂不考虑服务器压力"的处理**：用户已明确本轮不管服务器。但这里要区分两件事——**卡死的不是服务器，是浏览器**。服务器侧三维不产生任何计算（只有瓦片请求），所以这条不需要"不考虑"，它本来就不构成问题；真正要防的是 GPU 侧，靠上面四条护栏。

## 6. 性能与载荷（回应问题 6）

> **2026-11-11 03:00 用户追加约束**：本版**全部内容不上云服务器**，载荷不再设上限，传输速度不受限。
> 因此**不再追求 <30 KB**，改为**只优化响应时间**：瓶颈从"带宽"变成"后端算多久、前端解析多久"。

### 6.4 冷启动从 13.2 秒降到 3.4 秒（本轮实测）

`cProfile` 显示 12 秒全花在 `_live_stations()`：它为了数"各省实况点数"，
去拉东北 METAR（`national()` 5.1 s）+ 模型实况（`model_stations.fetch()` 6.9 s），
**而且被调用两次** → 4 次 HTTP。

但全国层已经有 319 城逐市实况，这份 METAR 既慢又不全。

**处置**：`_live_stations()` 改为直接用逐市实况生成（`source: PUBLIC`），不再发任何 HTTP。

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| 冷启动（全量） | 13.2 s | **3.4 s** |
| 热路径 | 19 ms | 41 ms（多带 80 个实况点） |
| 后端 nation 用例 | 13 s | 4.3 s |

**载荷**：净空几何仍走独立接口 `/traffic/v2/nation/zones`。理由不是"要压体积"，
而是**前端目前不画净空圈**——放回主载荷只是让每次请求多解析 250 KB，没有收益。
等地图上要画净空时再决定是放回还是按需取。

**下一步可做的**（本轮未做）：雷达与模型概率并行（两者无依赖，约再省 1 秒），
但雷达内部走 shapely，跨线程要确认 GEOS 安全，不冒险。


### 6.1 分层载荷

| 端点 | 内容 | 预算 | 用途 |
|---|---|---|---|
| `/traffic/v2/nation?level=nation&detail=summary` | 大区/省聚合 + 计数 + 气象摘要 | **<30 KB** | 首页首屏 |
| `/traffic/v2/nation?level=nation&detail=full` | 现行 479 KB 全量 | 现状 | 全国台完整视图 |
| `/traffic/v2/nation/flights?level=..&id=..` | 只回班次 | <60 KB | 时间轴推进 |
| `/traffic/v2/nation/events?level=..&id=..` | 只回事件（已聚合） | <20 KB | 处置页 |
| `/traffic/v2/nation/corridor/{id}` | 单条走廊 + 逐公里剖面 | <5 KB | 走廊下钻 |

**首屏只拉 summary**，用户点"全国台详细"或下钻时才拉 full。这一条同时满足 v3 红线与本条性能诉求。

### 6.2 前端请求纪律

现状问题：`NationBriefing` 的 `watch(localMinute, () => load())` 每动一格发一次 45 秒超时的全量请求，拖动滑杆能瞬间堆几十个，全部排在 `_NATION_LOCK` 后面。

四条修法：

1. **滑杆防抖 300 ms**，且只在 `change`（松手）时请求，`input` 时只本地预览时刻文本；
2. **取消在途**：`AbortController`，新请求发出前 abort 上一个；
3. **同 key 缓存**：`level+id+minute+radarTs` 相同直接返回上次结果，5 分钟内不重取；
4. **降级可视**：请求超过 3 秒就在页面上显示"正在算，已用 N 秒"，而不是干等（V1.0.1 的"正在加载全国数据…"没有任何进度，用户只能猜）。

### 6.3 后端

- `_NATION_LOCK` 保留（shapely 非线程安全，段错误教训），但要**缩短临界区**：把雷达/气象/模型三类取数移出锁，只锁 shapely 相关段落；
- 加 `detail` 参数分流，summary 路径完全不碰 shapely；
- 冷启动预热继续（后台线程 + 延时 6 秒）。

## 7. 其余问题的具体修法

### 问题 8 / 9 / 11 的 tab 高亮（B 类，用户指示"照态势界面的做法补齐"）

**根因代码**：`TrafficWorkbench.vue:596`

```html
<!-- 左侧子项 -->
:class="{active: entryKey===sub.key}"
<!-- 页内 tab -->
:class="{active: activeSection===tab.key}"
```

`entryKey` 是"当前 section 所属入口的锚点"，`activeSection` 是"当前视图"。

**为什么态势看起来正常、处置看起来异常**（这是本轮才查清的一层）：

```js
export const ENTRY_LABELS = Object.freeze({ card: '推演' })   // ← 只有 card，没有 alerts

// NAV_GROUPS 构建时：
label: spec.label || sectionName(spec.key)
// NAV_SPEC 里处置入口写的是 label: ENTRY_LABELS.alerts  →  undefined
// 于是回落 sectionName('alerts') = '事件处置台'  ← 一个「成员名」，不是组名
```

- **态势组**的三个入口 `home` / `overview` / `weather`，label 恰好都是**入口级名字**。左侧高亮表达"我在这一组"，读者不会把它当成"当前页面"。
- **处置组**只有一个入口，label 回落成 **"事件处置台"**——**成员名**。而右侧 tab 条（`entryTabs` 明确排除锚点）列的是"调度台账 / 大模型取证"。于是屏幕上并排出现「事件处置台（亮）」和「调度台账（亮）」两个名字，读者自然判定"事件处置台没暗下去"。

**真正的缺陷是**：左侧那个按钮表达的是"你所在的分组"，却挂着成员视图的名字，而且永远高亮（`entryKey` 恒等于它自己）。名字骗人 + 状态骗人，两者叠加。

**修法（三项，一并做）**：

1. `ENTRY_LABELS` 补齐多成员入口的**组名**：`alerts: '处置'`（与一级导航标签一致）。左侧从此显示"处置"，不再出现成员名。
2. 左侧 active 保留 `entryKey===sub.key`，但**样式改成"所在组"的弱指示**（左侧竖条 + 淡底），不与页内 tab 的实心高亮同色同形。
3. 页内 tab 条保持 `activeSection===tab.key`，作为**唯一的"当前视图"**指示。

改完后：点调度台账 → 左侧"处置"只是淡底（表示你在这组），页内"调度台账"实心亮。**同一个名字不会再一亮一暗并排。**

> 这一项不需要用户再决策，按上述三项直接改。`assistant`（大模型取证）与 `reference`（口径与来源）表现相同，也是 `ENTRY_LABELS` 缺条目导致，一次修全。

### 11.2 仍待确认（一条）

**`overview` 与 `home` 是否还有必要并存？**

现状两个都在讲"总览"。两个选项：

- **并存**：`home` 只做全国一屏结论 + 全国图；`overview` 只做当前作用域的铺开视图（含放行队列）。
  好处是"一屏结论"和"全域铺开"各自有地方，不抢屏。代价是左侧会多一项，读者要分清两者差别。
- **合并**：只留 `home`，把放行队列挂到它下半屏。好处是导航更短；代价是首页要同时承担"结论"和"明细"，
  在 1366×768 上会挤。

**默认按"并存"推进**，若你无异议就不改；若觉得导航啰嗦，说一声我合并。
