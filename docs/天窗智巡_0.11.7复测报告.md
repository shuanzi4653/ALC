## §2 本次抓到的 5 个问题（含证据）

### 2.1 P0-1 气象通道开关：用户按不动，而且无解

#### 现象

你打开气象监测页，能看到这一组控件（截图 `crop_legend_097.png` 同期页面，气象监测页 e2e 定位）：

```
气象通道  [实测气象·当前(disabled)]  [虚拟气象(可点)]
当前为实测气象，数据来自公开观测源
```

点「虚拟气象」，红字弹出：

> **切换失败：本操作需要管理员及以上；当前身份：值班员（请求头 duty）**

#### 根因（这是重点）

这个 bug 的根因**不是权限设计错误，是两套枚举撞车**。

后端只认三个角色，写在 `X-ALC-Operator` 请求头里：

```
observer（观察员） / duty（值班员） / admin（管理员）
```

切天气通道需要 **`admin` 及以上**。

前端有 **两个都叫"身份"的下拉框**，但它们是两回事：

| 前端概念 | 变量 | 取值 | 用途 |
|---|---|---|---|
| **信息密度** | `nu` 枚举 | `duty` / `command` / `demo` | 只控显示详略，**不发请求头** |
| **操作员角色** | `alc-operator` | `observer` / `duty` / `admin` | 发 `X-ALC-Operator` 头 |

关键证据在打包后的 JS 里：

```js
// 发请求时读角色
function zo(){
  try{ let e=localStorage.getItem(`alc-operator`);
       return [`observer`,`duty`,`admin`].includes(e) ? e : `duty` }
  catch{ return `duty` }
}
async function Bo(e,t={}){ ... c.set(`X-ALC-Operator`, zo()) ... }

// 页面上的"信息密度"下拉框
var nu=Object.freeze([
  {key:`duty`,   label:`值班员`, note:`原始要素全开…`},
  {key:`command`,label:`指挥`,   note:`收起原始报文…`},
  {key:`demo`,   label:`演示`,   note:`默认展开术语释义…`}
]);
```

**问题在于**：`localStorage` 里的 `alc-operator` 在整个前端包里**只有读取，没有任何写入**（`setItem('alc-operator', ...)` 零次命中）。

也就是说：这个值永远是默认的 `duty`，除非用户**打开浏览器控制台手敲一行** `localStorage.setItem('alc-operator','admin')`。

#### 实测矩阵

| 请求头 `X-ALC-Operator` | 切到虚拟气象 | 消息 |
|---|---|---|
| `duty`（默认） | **403** | 本操作需要管理员及以上；当前身份：值班员 |
| `observer` | **403** | 本操作需要管理员及以上；当前身份：观察员 |
| `command`（前端下拉框里的值） | **403** | 请求头 `X-ALC-Operator` 的值 `command` 不认识（可选：observer / duty / admin） |
| `demo`（前端下拉框里的值） | **403** | 请求头 `X-ALC-Operator` 的值 `demo` 不认识 |
| `admin` | **200** | 切换到虚拟气象 ✅ |

#### 死锁

更糟的是：**从虚拟气象切回实测气象，也需要 `admin`**。

所以如果哪天真的用 `admin` 切过去了，普通用户在页面上**再也切不回来**。这是一个单向门。

我在测试中确实用 `admin` 切到了虚拟气象，验证完立刻用 `admin` 回滚到 `measured`（`changedBy: "复测·回滚"`）。当前线上状态是干净的，你可以自己查：

```
GET /api/traffic/weather/mode → {"mode":"measured", "changedBy":"复测", ...}
```

#### 这件事有多要命

双气象通道是你这个项目**创新性分（25 分）里最有力的主张**：能证明"我们分得清实测和模拟，而且不拿模拟冒充实测"。

现在的情况是：**这个主张在页面上完全无法演示**。评委问"虚拟气象怎么用"，你只能打开控制台敲代码——这在比赛现场基本等于没有。

#### 更反讽的是

页面其实为虚拟气象写了**很好的一段解释**。我用 `admin` 切过去后，页面上出现：

> 本计划按「实测气象」生成，而地图当前显示「虚拟气象」：画面上的回波不是这份计划避让的那一片，绕飞的缺席属于口径差异，不是算法失效。点击「重新调度」可按当前通道重建计划。
>
> 按虚拟通道重新调度

这段话写得**非常专业**——它预判了"为什么切了通道地图没变"这个必然的疑问，并且把"重新调度"这个动作摆在旁边。**这段文案的价值，被一个按不动的按钮全废了。**

### 2.2 P0-2 雾天案例页：左右各说各话

#### 现象

打开 `https://tianchuang.shuanzi.site/?case=fog-20250105`，页面右上方写：

> **2025-01-05 沈阳大雾**
> ZYTX 实测能见度 **997.8 m**、云底 152 m；同一小时哈尔滨 1593 m、长春 2993 m。
> 沈阳 ↔ 本溪 等 **21 条走廊当前观测已达禁飞级**（三站最低能见度 998 m）

同时，页面底部状态条写：

> **低能见度：本帧无**

地图上**一个雾区都没有**。

#### 证据（网络层，浏览器实测）

雾天案例页发出的请求：

```
/api/traffic/v2/overview?seed=42&scenario=live&case=fog-20250105    ← 带了 case
/api/traffic/weather?seed=42&scenario=live&minute=60                ← 没带 case ！
```

抓到的 weather 响应：

```
case = None
scenario = live
validAt = 2026-10-21T17:00          ← 2026 年，不是 2025-01-05
weatherMode = measured
lowVisibility.available = true
lowVisibility.regions = 0
lowVisibility.reason = NO_LOW_VISIBILITY_READING
cells = 0
```

#### 根因

前端构造 weather URL 的函数（打包后 `Mt()`）：

```js
let r = await Bo(`/api/traffic/weather?seed=${x.value.seed}&scenario=${x.value.scenario}&minute=${n}${k.value?`&cityId=`+encodeURIComponent(k.value):``}`);
```

参数只有 `seed` / `scenario` / `minute` / `cityId`，**没有 `case`**。

所以：**左侧结论来自 2025 年的雾（走 `/v2/overview`，带了 case），右侧地图来自今天的天气（走 `/weather`，没带 case）。两个数据源撞在一起，就是你现在看到的自相矛盾。**

#### 后端也有责任

我直接打 `GET /api/traffic/weather?case=fog-20250105&minute=0`，后端返回：

```
case = None
scenario = live
validAt = 2026-10-21T17:00
```

**后端也静默忽略了 `case` 参数**，不报错、不提示，直接回实时数据。这是比前端更坏的行为——前端至少还有个"忘了传"的理由，后端这是"传了也不认还不吭声"。

#### 这件事有多要命

雾天案例是**全站最有说服力的一页**。它的结论写得很漂亮：

> "此刻已在阈值内"与"未来会不会"是两件事，本系统按前者处置

这句话就是整个项目的方法论核心。但页面上"本帧无雾"五个字，把这页的价值直接清零。**评委会认为：你连自己的案例页都没跑通。**

### 2.3 P1-1 图例写"实测雷达回波"，雷达其实取不到

#### 现象

图例第 6 项写的是 **「实测雷达回波」**，但：

- 用 `curl` 打 `/api/traffic/weather`：`radar.available = false`，`error = "最近 12 个时次均不可用：... HTTP 403"`
- 用浏览器打同一个接口：`radar.available = true`，`slotAgeMinutes = 12.2`

#### 为什么不一致

因为**瓦片回传通道（clientRelay）在起作用**：

- 服务器出口被中国气象数据网按 IP 封了（整站 403，连 `/robots.txt` 都拒）
- 浏览器在住宅网络上能直取，取到后 POST 回 `/api/traffic/radar/tiles`

`/api/traffic/weather/mode` 的元数据里说得很明白：

```json
"clientRelay":{"supported":true,"present":false,"ttlSeconds":600,
  "postTo":"/api/traffic/radar/tiles",
  "why":"瓦片源对数据中心出口整站 403（连 / 与 /robots.txt 都拒），但对住宅 IP 正常…"}
```

**这个设计本身是聪明的**，属于工程巧劲。但由此带来三个问题：

**问题 A：图例和实际来源不符。**
`radar.watch.source = "CMA_DATA_NET_RADAR_CREF"`——这是真实的中国气象数据网组合反射率。所以"实测"这个字是对的。**但只有浏览器开着的时候才是实测**，命令行/服务端/离线包里都是 403。

**问题 B：地图上找不到它。**
实测到的 3 块回波中心在：

| 多边形 | 经度范围 | 纬度范围 | 大致位置 |
|---|---|---|---|
| poly0 | 129.64–129.74°E | 42.43–42.49°N | 吉林珲春以东，俄罗斯境内 |
| poly1 | 124.19–124.37°E | 43.90–44.02°N | 辽宁北部 / 内蒙边界 |
| poly2 | 122.43–122.61°E | 44.78–44.90°N | 吉林白城西南，内蒙境内 |

**三块全在东北三省主体的边缘或境外**，总面积只有 434.9 km²（`echoFraction = 0.0025`，占画面 0.25%）。在当前缩放级别（东北三省全域）下，用淡紫色画出来，**基本看不见**。

**问题 C：状态条文案的歧义。**
写的是"仅层状降水 434.9 km²"，没说是"境外"。你在地图上找橙色/紫色找不到，会以为是 bug。

#### 一个必须说清的判断

**上次你投诉"橙色阴影没了"，这一版的回答是对的。** 我核对了原始几何：

```json
"bands": {"STRATIFORM": {"components": 3, "areaKm2": 434.9},
          "CONVECTIVE": {"components": 0, "areaKm2": 0},
          "STRONG":     {"components": 0, "areaKm2": 0}}
```

`CONVECTIVE = 0`、`STRONG = 0`，**≥35 dBZ 的对流回波一个都没有，橙色按设计就该不出现**。这是诚实的设计，不是遮丑。

问题只在于：**这个诚实没被讲清楚**。"本帧无对流"讲清楚了，"回波在境外、占比 0.25%、所以你看不见"没讲。

### 2.4 P1-2 分页做了，瘦身没做

#### 现象

新接口确实上线了：

```
GET /api/traffic/flights?page=1&size=100
→ 200 / {"page":1,"size":100,"total":7760,"pages":78,"items":[100条]}

GET /api/traffic/flights/points?ids=CAR-1-01-1-05-0-0
→ 200 / {"requested":1,"found":1,"items":{...},"missing":[]}
```

`points` 接口也是对的——它是**批量取轨迹**，配合分页列表用，设计路子正确。

#### 但 `points` 没裁

`items` 里每条航班仍然**完整携带 `points` 数组**：

```
首条 keys = ['id','name','mode','fromCity','toCity','fromPad','toPad','status',
             'reason','separationAction','clearanceStatus','requestedDepartureMinute',
             'departureMinute','arrivalMinute','delayMinutes','detourMinutes',
             'maxAltitudeM','points','slim']
首条含 points: True  点数=6  单条 856 B  points 占 395 B
```

体积解剖（1,010 条）：

| 项 | 字节 | 占比 |
|---|---|---|
| 去掉 `points` 后 | 452,428 B | 53.7% |
| `points` 合计 | 389,566 B | **46.3%** |

**结论：分页生效了（7,760 → 1,010），但`points` 这个 46% 的大头一点没动。**

更矛盾的是：`slim` 字段在每条里都是 `true`（硬编码），但 `slim` 的语义应该是"精简版不带轨迹"。**字段说自己是瘦的，实际是胖的。**

而且前端也**没用**这个新接口——首页翻页是纯本地切片：

```js
// 前端现有分页
disabled: de.value*20 >= Ce.value.length     // Ce.value.length = 1010（本地数组）
```

也就是说：接口做了、前端没用、`points` 没裁。三件事各干各的。

#### 附带：`fields` 参数校验

```
GET /api/traffic/session?scenario=live&fields=list
→ 422 / {"code":"DECISION_REQUEST_FAILED",
         "message":"query.fields：String should match pattern '^(slim|full)$'"}
```

这个 422 **是正确行为**（`list` 确实不是合法值），但错误码用了 `DECISION_REQUEST_FAILED`，语义不对——这不是"决策请求失败"，是"参数校验失败"。答辩演示时如果你打错参数，看到这个消息会一头雾水。

### 2.5 P2-1 老问题还在

#### `operations` / `journal` 仍 422

```

→ 422 / {"code":"DECISION_REQUEST_FAILED","message":"query.sessionId：Field required"}

GET /api/traffic/journal
```
