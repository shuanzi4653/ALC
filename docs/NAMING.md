# 系统命名规范（官方口径）

**系统正式名**：天窗智巡 · 低空交通协同运行管理系统
**适用范围**：界面文案、接口字段、证据文档、报告与答辩材料。命名改动必须与本文一致，避免同一事物出现两个名字。

## 0. 命名四原则

1. **删掉形容词式修辞**。"空管式""智能式""电子"这类词描述的是做法，不是功能；标题里只留功能本身。
2. **去掉没有对应实现的词**。"三维"已在 0.9.8（Beta） 全部改为平面渲染，标题不得再写"三维"；"立体"同理。
3. **同名同物**。导航名、面板标题、文档章节名三者必须一致。
4. **官方空域与系统派生不得共名**。法定的部分用法规用语，系统推演的部分必须自证是派生的。

## 2. 风险与空域术语（分层最严格的一组）

两套图层来源不同、法律地位不同，**名称必须能一眼区分**：

| 图层 | 正式名 | 语义 | 配色 |
| --- | --- | --- | --- |
| 系统派生 | **派生飞行风险区** | 本系统按气象阈值推演得出，**非官方空域管制** | 暖色：红＝禁止进入 / 橙＝谨慎进入 |
| 法定 | **固定管制区** | 取自法规与公开数据 | 冷色：洋红＝禁入 / 靛蓝＝须批准 |

- 派生区的两个等级写作 `派生飞行风险区（禁止进入）` 与 `派生飞行风险区（谨慎进入）`，
  分别对应内部键 `BAN` / `CAUTION`；`FIELD` 为 `气象影响范围`。
- **只有回避性质的那一级能出现"禁入 / 禁止进入"措辞**；谨慎级不得宣称禁入。
- 派生区**不得**使用 `管制空域`、`禁飞区`、`官方` 等词；固定管制区**不得**使用 `派生`。
- 由官方发布的灾害预警是第三类，标注 `OFFICIAL_GOVERNMENT_ALERT`，独立于以上两者。
- 雷达回波接入后仍属派生区；**标定完成前不得把"回波强度"写进风险区名称或阈值口径**。

## 3. 气象通道与底图状态（0.9.12（Beta） 新增）

这两组词描述的是**数据来源性质**，与"风险等级"是不同维度，**不得混用**。

| 概念 | 正式名 | 禁用措辞 | 依据 |
| --- | --- | --- | --- |
| 实测雷达源 | **实测气象** / **实测雷达回波** | 不得简写为"雷达"（会与固定管制区的雷达站用语混淆） | 数据来自 CMA 公开组网 |
| 程序生成的雷达成像 | **虚拟气象** / **模拟雷达回波** | 禁用"仿真雷达"「合成回波」等混称；**不得写成"实测"** | 见 `docs/radar-channels.md` §6 |
| 断网时的内置底图 | **离线底图** | 不得写"本地地图"「缓存地图」（会让人以为与在线底图同精度） | 1 km 简化省界 |

**三条硬约束**：

1. **虚拟通道的措辞必须始终带"虚拟/模拟"**，且界面提示与数据结构字段
   （`provider` / `synthetic` / `source`）**必须同时生效** —— 只改界面文案不算数。
2. **离线底图必须与在线底图在视觉上可区分**（橙色徽标 + 提示条），
   因为两者精度差三个数量级（1 km vs 城市道路级）。
3. **"实测"一词只能用于确实来自外部观测的通道**；程序生成的任何回波都不得使用。

守卫测试：`frontend/tests/offlineBasemap.test.mjs`（通道三态与措辞）、
`frontend/tests/weatherModeSwitch.test.mjs`（虚拟通道标注）。

### 7.1 正式版之后怎么递增

| 位 | 名字 | 递增条件 |
| --- | --- | --- |
| 第一位 `1` | 主版本 | **对外契约不再兼容**才 +1：库结构不兼容、HTTP 端点语义变更、判定链路换了角色。 |
| 第二位 `0` | 次版本 | 新增功能、新增端点、新增数据源 —— 旧调用方不改也能跑。 |
| 第三位 `0` | 修订号 | 缺陷修复、文案与界面调整、性能优化，一律 +1（`1.0.1`、`1.0.2` …）。 |

**不重置历史**：`V1.0.0` 之后的版本照旧逐行追加到 `changelog/CHANGELOG.md` 的版本总览表，
不改旧行标题。按 `0.9.` / `0.11.` 前缀做匹配的脚本，从这一版起要改成读 `VERSION`。

### 7.1.1 软著登记号与产品版本号（2026-10-27 起合并）

此前仓库里并存两个号：登记材料里的 `V1.0`（受理号 `2026R11.3476201`，2026-10-09）与
代码里的 `0.9.x-beta`。用户 2026-10-27 决定**产品版本正式定为 `V1.0.0`**，两者自此是
**同一个号**，不再有"两套编号不得互写"的问题。

保留三条落笔纪律（与登记状态有关，与版本号无关）：

1. **登记材料的措辞是"受理"不是"已获证"** —— 手上是受理凭据；写"已取得软件著作权"
   属于把未发生的事写成了事实。
2. **`V1.0.0` 是产品版本，不是登记结论** —— 它表示本版对外可用，不改变登记的受理状态。
3. 历史文档里出现的 `0.9.x` / `0.11.x` 是当时的事实，**不回改**。

### 7.2（历史）Beta 线的代位规则 —— `0.11.27` 之后不再使用

`0.9.35` 之后的版本是 `0.10.1`，不是 `0.9.36`。为什么允许动第二位、以及什么时候才该动它，
写在下面 —— 因为「只递增第三位」这条旧规矩如果只是被例外掉一次，下一个人就会再有第二次。

| 位 | 名字 | 递增条件 |
| --- | --- | --- |
| 第一位 `0` | 主版本 | **恒为 0**。理由不是"还没做完"，而是：`1.x` 应当意味着**对外契约稳定**，而本项目的契约（数据源、判据、规则文件）每一代都还在动。把功能多当成升 1.x 的理由，等于给使用者一个不成立的承诺。 |
| 第二位 `代` | 代位 | **架构换代**才 +1。判据只有一条，可逐条核：**这一版的改动，是否让旧版的运行数据或对外契约无法沿用？** |
| 第三位 `序` | 序号 | 同代内的**一切**发布都只递增它：新功能、缺陷修复、文案调整，一律 +1。 |

**「无法沿用」的三种具体形态**（满足任一即构成换代）：

1. **库结构变更** —— 新增迁移脚本（`V7`）。旧库直接启动会缺表，必须走 Flyway。
2. **判定链路的分工变更** —— 新增一个参与定档的角色。0.10.1 把轨道 1 从"纯规则"变成
   "规则（硬底线）+ 模型（能力增量）"，判定结果的来源变了，而不只是阈值变了。
3. **对外契约的字段语义变更** —— 同名不同义（单位、取值范围、是否可空）。

反面清单（**这些不是换代理由**，别拿它们动第二位）：功能条数变多、界面改版、
新增几个 API、代码重构、依赖升级、文档重写。

**0.11.1 只动第三位 `z`**：本版换的是**标签来源与指标体系**（判据 → METAR 实测，macroF1 → TS/POD/FAR/Brier），但**对外契约没破** —— 运行数据（快照号 / 算法指纹 / 计划修订）与既有 HTTP 端点全部沿用，新端点一律走 `/api/traffic/v2/*` 新增路径。判据见 §7.2：代位看的是「旧版的运行数据或对外契约能不能沿用」，不是「改动大不大」。

**不存在 `0.10.0`。** 代位递增时序号从 **1** 起：`0.9.35 → 0.10.1`。
写 `0.10.0` 会让"0.10.0 是不是比 0.10.1 旧"变成需要靠约定回答的问题，而它本该靠数字回答；
而且 `0.10.0` 与 `0.9.0` 在语义上不对称（后者是历史线回归的起点，不是为了"新开一代"而造的）。

**换代不重置历史**：`0.10.1` 之后是 `0.10.2`，`0.9.36` 不再出现；
`changelog/CHANGELOG.md` 的版本总览表照旧逐行追加，不新开一篇、不改旧行标题。

**这一条的代价要记住**：代位一升，凡按 `0.9.` 前缀做匹配的脚本（打包、校验、文档引用）
都会失配。所以升代时必须同一次改完 §7 表格里的五处落点，并跑一遍 `_verify_doc_links.py`
与打包闸门 —— 只改 `VERSION` 而漏掉 `pom.xml` 会让 `mvn package` 打出一个版本号与产品
对不上的 jar，而它在服务器上照样能启动。
