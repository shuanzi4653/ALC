## 3. 0.11.13 —— 全仓扫描，抓到一个从来没显示过的面板

**新增两把尺子**：
| 工具 | 作用 | 结果 |
|---|---|---|
| `_probe_all_pages.py` | 8 个页面逐个点开，听浏览器报错 + 收集 4xx/5xx | **抓到真 bug** |

⇒ **「本案例判据」整块从来没加载出来过**。

**为什么长期没被发现**：编译能过、449 条前端判据全绿、`_audit_unbound_names.py` 是 **Python AST**
扫不到 JS 的 `ReferenceError`（MEMORY ㉓ 记过这条盲区）。只有真把页面点开才看得见。

**走弯路的两次**：验证面板时先试首页（组件根本不渲染）→ 再试「2 走廊」（面板不在这个 view）
→ 最后才定位到「3 处置」（`view==='alerts'` 才渲染）。**"问错了地方"的症状长得像"功能没修好"。**

**读数**：前端 449/449、后端 520 passed / 1 skipped、闸门 **29 → 31 项**（新增 prop-ref 两条）。

## 6. 0.11.14 —— 两个 P0（H-1 / H-2）

**H-1 地图 T+2 之后没飞机**
- 现象：`mapFlights` 600 条，`arrivalMinute` 最大 **127.3**，而时间轴开到 480。
- 报告归因"没做时间分层"，**实际比这更具体**：我上一版写的"载客优先"是
  `for f in flights: if len(car)+len(delivery) >= 600: break` —— 单遍扫描 + 提前 break，
  而 `flights` 顺序配送在前 ⇒ **配送 494 条先占满名额，载客只剩 106 条**。
  "优先"只写在注释里，没落地。
- 改法：`car_all → car_rows（有起飞时刻）→ 每空桶补配送`。
- 验收：`arrivalMax 479.8`、逐 60 分钟 地图/列表 **T+0 0.48 / 其余全 1.00**、
  体积 1005.3 KB、`mapCar 698 + carClosedNoTime 150 = 848`。

**H-2 切通道不生效（三重原因）**
| # | 原因 | 改法 |
|---|---|---|
| ① | 建场 URL 不含通道 ⇒ 浏览器把 10 分钟前的旧结果给它 | 追加 `&mode=` |
| ② | `api.js` 的 fetch **没有地方能表达"别用缓存"** | `cache` 经 fetchOptions 透传；建场处传 `no-store` |
| ③ | `planRevision` 恒为 `traffic-plan-v1.3`（算法版本串） | 改成**进程内递增序号**，算法串挪 `planVersion` |

浏览器 CDP 实测：`fromDiskCache **False**`（复测是 true）、`encodedDataLength 264`（复测 0）、
耗时 **3.8 秒**（复测 0.5）、两通道 rev **1 / 3** 不同。

**H-3**：`flights?minute=` 真过滤（0/60/300 → 23/92/103 班；不传仍 7760）
**H-4**：地图 KPI 副行 9.5 → 11 px

**落实时改了方案三处**（都有实测依据）：分桶从 17 个改 16 个（第 17 桶 [480,510) 没有航班起飞）；
载客不收 CLOSED 的 318 条（无航迹，白占 150 KB 且让判据失真）；航迹点 6 → 4（实测每行 590 B 而非估算 300 B）。

## 7. 软更新（同版本号，不计入迭代）—— 预热 + 进度刻度

**真根因是我在 H-2③ 引入的回归**：
```python
and result.get('planRevision') == PLAN_REVISION   # ← 已改成递增序号 '1'、'3'
```
磁盘恢复**永远失败** ⇒ 每次切通道/重启整份重建（虚拟 90–120 秒），
`_prewarm_sibling` 辛苦预建的姊妹计划**落盘后读不回来，预建等于白做**。

修法：比 `planVersion`（算法串仍发布在这里）。

**启动预热**：`@app.on_event('startup')` 后台线程 5 秒后用**未标识工作区**依次建
measured / virtual 并复原（`retain=False`，不常驻内存，一份约 110 MB）。

**进度刻度**：BUILDING 响应补 `stage / elapsedSeconds / etaSeconds / buildChannel` +
`etaBasis: ESTIMATE_BY_CHANNEL`。前端实测文案：
```
 8 秒: 正在按实测气象重建 · 45% · 已用 3 秒 · 约剩 57 秒 · 逐班次规划航路与间隔
20 秒: 正在按实测气象重建 · 89% · 已用 15 秒 · 约剩 45 秒 · 逐班次规划航路与间隔
```

**验收**：未标识工作区首次取计划 60 s → **1.32 s**；**切通道 90–120 s → 1.07 s**。

**教训**：把常量改成会变的值时，**所有拿它当"版本标识"做比较的地方都要一起改**
（本轮只改了发布侧，忘了校验侧；而"重建"和"命中"在界面上长得一样，只有耗时暴露它）。

## 10. 这一段最贵的四条教训

1. **"看不见"与"没有"是两件事**（雾 60 px、地图 0 架、面板从未渲染）——
   三者都让判据全绿，只有像素/截图/浏览器报错能抓到。
2. **归因不能从"关了一个开关没变化"推到"它是别的东西"** —— 那只证明"不是这个"，
   没证明"是哪个"。要把所有开关逐个关一遍量权重。
3. **改常量要考虑所有拿它当"标识"做比较的地方**（`planRevision` 从常量改递增序号，
   忘了磁盘校验那一行，预建白做一整天）。
4. **"对齐"不等于"改成同一个数"** —— 两个阈值不同时，要补的是关系声明，
   而不是把它们强行统一（统一后关闭班次涨到 55%）。
