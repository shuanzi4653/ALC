## 2. N-1（P0）：雾天案例页画不出雾

### 2.1 现象

雾天案例页（`?case=fog-20250105`）上：

- KPI 写着 **53 条待处置、18 条禁飞级走廊**
- 顶上一句结论：「沈阳 ↔ 本溪 等 18 条走廊当前观测已达禁飞级（三站最低能见度 998 m）」
- 底栏写「实测 4 站 · 最低 998 m」
- 图例里「低能见度（雾）」是开着的
- **但地图上找不到雾在哪。** 沈阳上空、长春上空，都没画任何雾区

### 2.2 证据：像素差分

做法：在同一个页面、同一帧、只点一次「低能见度（雾）」开关，前后各截一张 1680×1050，逐像素比。

| 图层 | 图例行 y=430–460 | **地图区 y=480–880** | 底栏 y=880–1000 |
|---|---|---|---|
| 关「低能见度（雾）」 | 110 px | **60 px** | 6,746 px |
| 关「实测雷达回波」 | 110 px | **0 px** | 5,652 px |
| 关「观测等级点」 | 119 px | **0 px** | 0 px |

对照基线：单纯点亮/熄灭图例标签本身约 **110–119 px**。

所以：

- 「低能见度（雾）」在地图上只改了 **60 px**（比一个图例标签的变化还小），**等于没画**
- 「实测雷达回波」和「观测等级点」在地图上是 **0 px**（这个是对的：案例下 API 已经诚实地说 `CASE_NO_RADAR_TILES`）
- 那几千 px 全在底栏（y>880），是底栏文案跟着图层状态换字，不是地图内容

### 2.3 根因

接口是诚实的，前端没接住。

```json
// GET /api/traffic/weather?case=fog-20250105
"lowVisibility": {
  "included": false,
  "reason": "CASE_OBSERVATION_ONLY",
  "detail": "本案例只有 4 个机场站的实测能见度，没有城市格点场，因此不产出雾区面
             —— 图上按站点画的是**影响范围示意**，不是实测雾区边界。",
  "stations": 4,
  "cities": 0
},
"stationVisibility": [
  {"station":"ZYTX","visM":997.8,"visLevel":"BAN","lat":41.6398,"lon":123.4833,...},
  {"station":"ZYCC","visM":2993.4,"visLevel":"CAUTION",...},
  {"station":"ZYHB","visM":1593.3,"visLevel":"CAUTION",...},
  {"station":"ZYTL","visM":2800.3,"visLevel":"CAUTION",...}
]
```

后端明确说了两件事：① 不产出雾区面（`included:false`）；② **图上按站点画影响范围示意**。

前端只读了 `lowVisibility.regions`（空数组）→ 什么都没画；`stationVisibility` 这 4 条带经纬度和能见度的数据，**没有一条被用上**。

**于是页面上出现了一句"描述了一个不存在的东西"的话。** 这句话是这版最严重的自伤：评委按着字面去找，找不到。

### 2.4 为什么这条是 P0

雾天案例是全站最有说服力的一页：真实历史（2025-01-05 沈阳大雾）、真实报文（ZYTX 997.8 m、云底 152 m）、真实结论（18 条走廊禁飞、53 条待处置）。**它唯一的失败点是"看不见"。**

评委看这一页的心理过程是：数字很硬 → 地图在哪？→ 没有 → 这些数字凭什么？→ 怀疑全部。

一条 3 小时的前端改动，能救回这一页的全部说服力。

## 3. N-2（P0）：虚拟通道下接口自己打自己脸

### 3.1 现象

管理员切到虚拟气象后，同一次 `GET /api/traffic/weather?seed=42&scenario=live&minute=60` 的响应里：

| 字段 | 值 | 说明 |
|---|---|---|
| `weatherMode` | `virtual` | 虚拟通道 |
| `radar.mode` | `virtual` | 虚拟通道 |
| `radar.watch.source` | `SYNTHETIC_RADAR_CREF` | 合成数据（诚实） |
| **`radar.summary.channel`** | **`CMA_RADAR_TILES`** | ← **自称中国气象局雷达瓦片** |
| **`radar.summary.note`** | **「本通道几何为实测雷达反射率经阈值分类与配准后生成」** | ← **自称实测** |

同一条响应里，`source` 说"合成"，`summary` 说"实测"。

### 3.2 顺带一个更小的破绽

`radar.summary.slot = "2026-10-21T11:00:00Z"`，`slotAgeMinutes = 0.0`。

虚拟数据的时次是**昨天 11:00**（UTC，即昨晚 19:00），但"时次年龄"报 0 分钟。也就是说，这个"新鲜度"字段在虚拟通道下是**硬算出来的**，不是量出来的。

### 3.3 为什么这条是 P0

不是因为界面难看，是因为**一查就穿**。

答辩现场最容易被问的问题是「你怎么证明这不是编的」。队友现在做了一大堆防伪设计（`source`、`qualityFlags`、`reason`、`detail`），这些都很值钱。但评委只要在虚拟通道下点开一次网络面板，就会看到 `channel=CMA_RADAR_TILES` 和 `source=SYNTHETIC_RADAR_CREF` 同时存在。

**一条字段名对不上，会把前面十条诚实设计一起废掉。**

## 4. N-3 / N-4：虚拟通道的两处"说法打架"

### 4.1 N-3（P1）：走廊概率走哪条通道，两个页面说法相反

同一时刻（`mode=virtual`）两页的原文：

- 首页：「当前为模拟气象通道：**走廊概率仍按三站 METAR 实测计算**，与地图上的虚拟回波不是同一份气象。」
- 气象监测页：「通道是「虚拟气象」：本页天气场与**走廊概率都走模拟通道**，不是实测，仅供演示。」

前者是对的（走廊概率确实是 METAR 插值，不受通道开关影响），后者是错的。

差别在于：首页那句是这版新写的（写得非常准确），气象页那句是上一版留下的旧文案，**改通道开关的时候没同步改这句**。

**这条改起来 10 分钟，但留着就是答辩时被追着问的那种问题。**

### 4.2 N-4（P1）：虚拟通道下"分档统计"和"避让几何"对不上

虚拟通道下的气象监测页，同一屏里：

| 位置 | 数字 |
|---|---|
| 15–35 dBZ 层状降水 | **176,411.4 km²**（2 个单体） |
| 35–45 dBZ 对流回波 | **45,376.7 km²**（7 个单体） |
| ≥45 dBZ 对流内核 | **941.4 km²**（2 个单体） |
| 本计划的避让几何：并集 | **0 km²（内核 0 · 谨慎 0 · 层状 275.4）** |

有 941.4 km² 的"禁止进入"内核，避让几何里内核却是 0；层状写 275.4 km²，而分档写 176,411.4 km²。

`275.4` 是**实测通道**那本账的数字。也就是说：**分档统计随通道换了，避让几何没换。**

后果：切到虚拟后，地图上会看到一大片橙色回波（我实测虚拟通道有 7 块对流 + 2 块强对流），但系统的航线避让用的还是实测那本账 → **看见橙区却飞进去**，这在演示里是硬伤。

上一版的自曝（`"llm probe not wired"`、`"store dir not exposed"`）都清掉了，这版换成真实数据，方向完全对。但把部署绝对路径也一起吐出来了 —— 改成 `".run/traffic"` 相对路径即可，信息量不减，暴露面归零。

### N-6（P2）底栏最关键的几句解释是 9px

小字号抽样（<12px 共 49 个）里，最扎眼的是底栏那三句：

```
9px  雷达：仅层状降水 542.9 km²（15–35 dBZ，可飞越）· 本帧无 ≥35 dBZ 对流，橙色按设计不出现（回波占本帧画面约 0.3%，全域缩放下基本看不见）
9px  低能见度：深灰 1 处
9px  运行事件 3 个 · 停止放行 123 班
```

这三句恰恰是**替系统解释"为什么没有橙色""为什么看不到回波"的关键文案**。9px 在投影仪上基本读不出来，等于白写。

其余 46 个 <12px 集中在**地图标注**（10px 城市名、10px 走廊标签、10px 视角按钮），这些属于可接受的图层标注，不用动。

**建议只改底栏这三句：9px → 11px，行高从 13 → 15。** 一行 CSS。

### N-7（P2）`session` 还是 1.24 MB，`fields=slim` 只是回显标签

| 接口 | 体积 | 是否带 `points` |
|---|---|---|
| `/api/traffic/session?scenario=live&seed=42` | **1,239,265 B** | 是（1,010 条 `flights` 全带） |
| `/api/traffic/flights?page=1&size=100` | **45,013 B** | **否**（已瘦身） |
| 响应里的 `fields` 字段 | `"slim"` | 只是个回显，没生效 |

同时 `session` 里还有 `mapFlights`（600 条），说明**地图用 600 条、表格用 1,010 条，但两条都带 `points`**。地图只需要 600 条带 `points` 的，表格那 1,010 条不需要。

按上一版测出来的比例（`points` 占单条 46.2%），把 `flights` 的 `points` 去掉，包体能从 1.24 MB 降到 **约 0.68 MB**。

### N-8（P2）冷启动遮罩 15–25 秒，首屏被一块大遮罩挡住

实测：进入首页后 8 秒，页面还是 `RUNNING PLAN 62%` 的居中遮罩（截图 `n1_home.png`），遮罩盖住整张地图，文字是「逐班次规划航路与间隔 / 已用 12 秒 · 首次加载需要展开雷达回波时轴并逐班次复核间隔」。

缓存是生效的（`/metrics`：`prepared_hits_total 14` / `prepared_builds_total 1`），所以第二次进会快。但**评委第一次进就是这 15–25 秒**。

不需要改性能，只需要改遮罩：从"盖住全图"改成"图例上方一条进度条"，让评委在等待时能先看地图和结论条。

### 6.1 视觉上还剩一个真问题：地图主次颠倒

首页地图上，最抢眼的是 9 个**淡紫色大圆环**（城市站点光环），每个直径约 80 px；而真正的业务对象——走廊航线——是 1px 的青色细线。

## 9. 三个方法上的坑（写给自己，也提醒队友）

1. **工作区不等于账号。** 页面用的是自动生成的 `alc_ws`（本次 `d6667f1097854e518153829d`），不是 `M6699`。用 `M6699` 调接口改通道，页面完全看不到 —— 我一开始就被这个骗了一轮，以为"切虚拟后页面还显示实测"是 bug。**凡是改状态，必须在页面里改。**
2. **`phase` 字段改名了。** 建场响应从 `{phase, session:{...}}` 改成**扁平结构**：`status`（`READY`）+ 顶层 `sessionId` / `flights` / `stats` / `flightStats`。旧脚本还按 `phase` 轮询，结果永远等不到 READY。**判 READY 请看 `status`。**
3. **判"图层有没有画"只能靠像素差分，不能靠 DOM。** 图层的开关是自定义 `div`，DOM 里查不到对应要素；唯一靠得住的证据是"关掉之后地图区变了多少像素"。本次 N-1 就是靠这个抓出来的。
