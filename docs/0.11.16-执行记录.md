## 一、§七 收敛：**1430 → 123 与概率阈值无关**（候选原因被实测证伪）

### 1.1 §七 给的候选原因

> 关闭班次减少，是因为 `P_PROB_BLOCK/WATCH` 从 `0.8/0.5` 降到 `0.25/0.15`，
> 让 `v2._fuse()` 的「降级为可飞」分支走进更多班次。

这条**必须先被证伪或证实**，不能照它去调参。工具：`tools/maintenance/_probe_0116_close_cause.py`。

### 1.2 实验 A（静态）：计划路径根本不读这两个常量

AST 扫 `backend-python/traffic/service.py`（计划构建唯一入口 `_plan_trajectory` 所在模块）：

```
计划路径读到的 operations 键：['crossingZone', 'delivery', 'maxFlightMinutes', 'riskCeilingAglM']
service.py 是否 import v2：False
```

`_fuse()` 住在 `traffic/v2.py`，只有 `v2.counterfactual()`（反事实重放页）调它。
**`accepted/closed` 与 `P_PROB_*` 之间没有边** —— 候选原因在结构上不成立。

### 1.3 实验 B（动态）：同一份冻结快照，三档各建一次计划

快照冻结在 `.run/threshold-lab/snapshot.json`（2026-10-23 16:45，36 城，gustMax 15.5 m/s）：

| P_BLOCK / P_WATCH | accepted / closed | closedByReason |
|---|---|---|
| 0.50 / 0.30 | **7641 / 119（1.5%）** | CLEAR 7641 · BEYOND_PLANNING_HORIZON 65 · SEPARATION_RESOURCE_OR_TIME_LIMIT 48 · WEATHER_BLOCKED 6 |
| 0.27 / 0.18 | **7641 / 119（1.5%）** | 同上 |
| 0.25 / 0.15 | **7641 / 119（1.5%）** | 同上 |

**三档逐字相同（`tiersIdentical: true`）。** 候选原因到此被证伪。

> ⚠️ 跨进程读数的 ±1 抖动（另一次运行是 7642/118）来自**实时雷达瓦片**：`_radar_avoidance`
> 每次建场都会去取一次公开雷达帧，帧一变，`WEATHER_BLOCKED` 就 ±1。所以对照必须
> **同进程、同一份冻结快照**，否则差异不可归因（M27）。

### 1.4 那么 123 是什么？（关闭原因拆开看）

当期 119 个关闭里，**只有 6 个是气象**：

| 原因 | 班次 | 是否是气象 |
|---|---|---|
| `BEYOND_PLANNING_HORIZON`（超出 8 h 规划时域） | 65 | 否 |
| `SEPARATION_RESOURCE_OR_TIME_LIMIT`（间隔/资源/时长上限） | 48 | 否 |
| `WEATHER_BLOCKED` | 6 | **是** |

**112 / 119（94%）根本不是天气事件。** 换句话说，§七 里"演示没事件"的直觉抓对了现象，
但抓错了对象：少掉的不是"被阈值挡住的气象事件"，而是**当天本来就没有城市低于 1000 m**。

### 1.8 定档：**维持 0.25 / 0.15**，并把"为什么另外两档是死的"写成算式

| 项 | 值 | 依据 |
|---|---|---|
| `P_PROB_BLOCK` | **0.25** | 与 WATCH 保持"两段有序"，且 BLOCK 分支的可达区见 §二 |
| `P_PROB_WATCH` | **0.15** | 三档中**唯一**能让概率档真的改判的一档（404 架次）；0.27/0.18 与 0.50/0.30 都是 0 |

| `extremeGustMps`（几何） | **17.0** | 不动（§1.6 的杠杆表留给下一轮，安全语义不做演示调参） |

## 二、本轮新发现：**概率档的可达窗口被置信门夹成两条窄带**

`_fuse()` 的顺序是：`rule==2 → 低置信(conf<0.65) → BLOCK → WATCH`，而
`confidence = |p−0.5| × 2`。于是"置信门"等价于：

```
conf ≥ 0.65  ⇔  p ≤ 0.175  或  p ≥ 0.825
```

推论（都能用 §1.7 的数对上）：

1. **WATCH 的可达窗口是 `[P_WATCH, 0.175]`**。取 0.15 → 窗口宽 0.025，案例场里命中 404 架次。
   取 0.18 → **窗口为空**，因为 0.18 > 0.175 ⇒ 全部走"低置信转人工复核"。
   这就是 §七 表里「0.27/0.18 只让 2 条走廊触发」今天变成 0 的原因 —— 不是天气变了，
   是那一档**在数学上永远碰不到**。
2. **BLOCK 的可达区只有 `p ≥ 0.825`**：`p ∈ (0.175, 0.825)` 的高概率样本一律先被置信门拦下。
   所以 `P_PROB_BLOCK = 0.25` **永远不可能触发**（它是"承诺了一个做不到的升级"）。
   这一点写在这里，是因为它解释了两件旧事：原来那对 `0.8 / 0.5` 里，**0.8 是可达的、
   0.5 是不可达的**；而 0.11.15 把两个数一起降到 0.25/0.15 时，把"可达的那个"也弄丢了。
3. 结论：**改 P_PROB_BLOCK 不会改变任何观测到的数字**（它是死区里的常量）。
   真要让它可达，得改的是置信门（手册 §9.1 的定义），属独立一轮 —— 本轮不擅自改。

新判据：`test_概率升档的两条线不互相覆盖` 已去掉硬编码的 0.80/0.50，只钉"两段有序 + 两段各有
不同说明 + 档位不越界"；数值由 `_probe_0116_prob_tier.py` 与案例场负责。

## 三、K-8 / K-9 / K-10

### K-8 雷达徽标 PENDING 态（状态机 + 5 秒超时）

**改前**：`radarState(null) === DOWN` —— 页面刚打开、请求还在路上时，徽标已经在写
「雷达回波不可用」，而它一次失败都没发生过。「还没问」与「问了没人答」被合并成一句话。

**改法**（纯函数全在 `frontend/src/traffic/runtime.js`，`.vue` 只做接线）：

| 位置 | 变化 |
|---|---|
| `RADAR_STATE` | 三态 → 四态：`PENDING / READY / QUIET / DOWN` |
| `radarState(radar, {waitedMs, timeoutMs})` | 无载荷 + 未超时 ⇒ `PENDING`；超时 ⇒ `DOWN`；**载荷到了但 `available!==true` 仍立刻 `DOWN`**（显式拒绝不许伪装成加载中） |
| `RADAR_PENDING_TIMEOUT_MS` | **5000**（实测首包 0.3–1.6 秒；5 秒短于操作员开始怀疑的时间） |
| `radarUnavailable(radar, opts)` | 新增。语义 = 「非 READY 且非 QUIET」。三处 `===DOWN` 守卫改用它 —— 不这么改，新增状态会让 `null` 漏进 `radar.regions` 直接抛异常 |
| `radarSummaryText` | PENDING 单独一句：`实测雷达正在读取：…（超过 5 秒未到按不可用处理）` |
| `CityTrafficMap.vue` | 等待计时器（250 ms 一跳）+ 徽标印**已等秒数**；`pending` 用中性石板灰 + 虚线边框，**刻意不与 `down` 同色**（等待不是故障） |

### K-9 走廊能见度下界标记

**问题**：METAR `6+` 换算成 9656 m 是**下界**，判据行印「9656 m」等于把"至少"读成"恰好"。
后端 `_criteria` 从 0.11.1 起就发 `display`/`lowerBound`，但**走廊行与详情从来没带**，
前端也一直自己拼 `value + unit`。同一屏上判据说「≥」、走廊说「恰好」。

| 层 | 改动 |
|---|---|
| 后端 `_idw_visibility` | 返回新增 `visLowerBound` / `visRaw`（来源 = 最近站自己的报文），缺测时 `False` + `''`（不是"下界 0 米"） |
| 后端走廊行 | `visLowerBound` / `visRaw` 随行发布 |
| 前端 `criterionValueText(row)` | 新增纯函数：优先用后端 `display`，没有才退回 `value+unit` |
| 前端 `visibilityText(visM, lowerBound)` | 新增纯函数；**1000 m 以下改用米**（998 m 原来印成「1 km」，会被读成"满足 ≥1000 m"） |
| 前端走廊面板 | 列表一格 `≥9.7 km`；判据格用 `criterionValueText`，下界加 `title` 说明报文原文 |

## 四、顺带修掉的六个真缺陷

前三条是本轮**要改的东西**（K-8/9/10）在修的过程中暴露的；后三条是**跑全量套件**才暴露的
——0.11.15 §六 的"后端判据 13/13"只统计了 H 系列，那 13 条之外的四条**从 0.11.14/0.11.15
起一直是红的**，而没有任何人看见（M95：判据的期望值是易腐品）。

| # | 缺陷 | 怎么被发现的 | 改法 |
|---|---|---|---|
| 1 | `test_概率升档的两条线不互相覆盖` 里硬写着 **0.80 / 0.50**，而 K-1 已改成 0.25/0.15 | 全量 `pytest` | 去掉数值硬编码，只钉"两段有序 + 说明不同 + 档位不越界" |

### 4.1 K-10 第一版放错了位置（教训：默认视图就是优先级声明）

第一版把"训练阈值 / 运行阈值 / 两者一致"这一行放进**每个任务的页脚**，
而模型卡默认停在「三目标对比」视图 —— 那一视图里整块**不存在**。

这与 §十一 那条是同一条：**"有内容" ≠ "够得着"，默认状态下不存在就等于不存在。**

## 七、这一轮的方法论增量（写进下一轮的纪律）

1. **候选原因必须先在结构上验一遍"有没有边"**。§七 猜的是"阈值 → 班次关闭"，
   而那条边在 AST 上就不存在 —— 一次 `ast` 扫描比三次重建便宜两个数量级。
2. **对照实验必须冻结输入**。实时雷达瓦片让同一份快照的读数抖 ±1；实时 METAR 让
   `peakUnsafe` 从 0.1563 漂到 0.1080。**用会漂的量定档，等于让结论跟着天气走**，
   所以概率档的判据落在**历史案例场**上（可复现），实时场只当"当期读数"。
3. **"没触发"要先问是"没到线"还是"到不了线"**。0.27/0.18 与 0.50/0.30 的 0 不是天气平静，
   是**置信门把窗口夹没了**（§二）。这两个 0 长得一模一样，修法完全不同。
4. **加一个状态，就要把所有逐值比较改成语义判断**。K-8 加 PENDING 后，三处
   `=== DOWN` 会漏掉它并让 `null` 进到几何生产者里 —— 这类漏没有编译错误，
   只有 `radarUnavailable()` 这种具名语义能兜住。
