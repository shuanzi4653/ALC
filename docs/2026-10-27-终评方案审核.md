## 二、P0-a 属实，但 E-1 的改法无效（这条必须先纠正，否则白改）

### 2.1 现场复核（线上，`minute=0`，`case=fog-20250105`）

```
conservative  incident=20000  A=2402  B=0  rerouted=2848  delayed=8/320min
balanced      incident=10000  A=2402  B=0  rerouted=2848  delayed=8/320min   ← 与上一条逐字段相同
efficiency    incident= 4000  A=2402  B=0  rerouted=2656  delayed=8/320min
```

报告结论成立。

### 2.2 为什么「20000 改 15000」一定不会变

`_choose_action()` 里只有一项随 `incident` 变动，且是**线性的**：

```
DIRECT  = p_unsafe · I
DELAY   = 40 + p_delay · I
REROUTE = 25 + p_alt  · I
CANCEL  = 180（有可绕飞时直接排除；观测已不可飞时 DIRECT 直接排除）
```

于是"选绕飞"的条件是 `I · (p_delay − p_alt) > 25 − 40`。**对每一架航班，这个条件对 I 单调**（p_delay 与 p_alt 固定），所以：

> 若 `I=10000` 与 `I=20000` 给出同一批结果，则 **I 在 [10000, 20000] 区间内任何取值都给出同一批结果**。

15000 落在这个区间里。**改完一定还是 2848，白改一次并且会误以为修好了。**

要让 conservative 真的"更保守"，只能动**别的旋钮**，而每个都有代价：

| 做法 | 效果 | 代价 |
|---|---|---|
| 把 I 降到 10000 以下（如 7000） | 确实会变 | **方向反了**：绕飞更少 = 更不保守，语义错 |
| `cancel` 门限放开（例如 p ≥ 0.5 时允许取消） | 真的会拉开差异 | 会改掉 **2848 / 8 / 320**，也就是所有材料里的代价数字 |
| 降 `delay` 成本 / 升 `reroute` 固定成本 | 会变 | 注释里明确写了"三档动作成本相同，否则说不清差异来自哪" |

**赛前 3 天的建议：不改逻辑，改展示。** 在三档按钮下方加一行动态说明（数字由接口算，不写死）：

> 「本案例下**保守与均衡拦到同一批航班** —— 雾最重那段，绝大多数班次的损失量已远超两个门槛；差别出现在效率档：**少绕 192 架次**。」

理由：① 零风险，0.3h；② 它把"按钮是装饰"转成"我们知道为什么一样"，和本项目一贯的"承认边界"是同一条主线；③ 答辩话术从"这不是 bug"变成"这是数据分布的真实结果"，比硬造差异稳。

## 三、P0-b：现象对，机制判断错，改法会误伤

### 3.1 复核到的

```
实时通道（无 case）minute=0 / 180 / 360
→ timeBase 恒 2026-10-27T02:30:00Z · pending 恒 53 · 结论恒「未来 3 小时内…」
```

**报告说得对：实时态拖时间轴，气象侧的数不会变。**

### 3.2 但两点判断要纠正

**① 滑块不是假的。** 时间轴在同一条链路上还驱动**航班位置与空域四态**（计划本来就是 8 小时窗口），这一点在案例态和实时态是同一套代码。**按方案把实时态的滑块整个换成一句话，会把"看航班推进"这个功能一起砍掉**——而这是实时通道唯一的演示价值。

**② `max=480` 不是越界。** 480 是实时通道真实的 8 小时计划窗口；案例窗口是 360，两者本来就该不同（上一版已按案例收口）。报告把"实时 max=480"和"案例窗口 360"放在一起比，是**跨模式比较**。

### 3.3 建议改法（0.2h，不砍功能）

滑块保留，只在**实时态**加一行字：

> 实时通道的气象只有当前一份观测（`{{obsTime}}`），**走廊判据与结论不随推演时刻变化**；时间轴只推进航班位置。要看气象驱动的改判 → 「切到 2025-01-05 沈阳大雾」。

判据：实时态拖到 T+06，屏幕上必须能看到这句话，且同时能看到四态/航迹在变。这样"时间轴是假的"这个读法就不成立，因为页面自己先说了它能干什么、不能干什么。

## 四、新发现：材料里的"硬数字"今天复现不出来

报告 2.3 与执行方案第 6 节都要求材料**只用**这几个数：`2613` / `3044 = 2640 + 404` / `2848` / `8 班 320 分钟` / `0.1%`。

今天同一 URL、同一构建实测：

| 数 | 报告（10-26 21:10–23:30） | 今天（10-27 11:0x） | 判定 |
|---|---|---|---|
| A 组暴露 | 2613 | **2402** | ❌ 变了 |
| AI 改判 | 3044（2640 + 404） | **3030（2640 + 390）** | ❌ 概率档少了 14 |
| 绕飞 | 2848 | 2848 | ✅ 稳定 |
| 延误 | 8 班 / 320 分钟 | 8 班 / 320 分钟 | ✅ 稳定 |
| B 组暴露 | 0 | 0 | ✅ 稳定 |

A 组暴露的判定是 `rule_level < 2 and current_ban`（`v2.py:1574`），依赖**建场时的运行计划**；而建场会拉实时雷达做避让，计划随当天环境重建。同一构建、同一 seed，跨天能给不同结果。

**所以：**

1. `2613` 与 `3044/404` **不能写死在 PPT、视频、简介里当常数**——评委自己打开会看到别的数。
2. 稳定的那组（`0` / `−100%` / `2848` / `8 班 320 分钟` / `0.1%`）可以放心用。
3. 如果一定要用 2613：**录屏/截图与文案必须在同一次会话里完成并当天锁定**，且文档里写成"本次运行测得 2613 架次"，不写成"系统固定值"。
4. 这一条也顺带说明"可复现"要写成"操作可复现（同一路径能复现同一量级）"，不要写成"同一组数逐位相同"。

## 五、上一轮遗留：1366 仍然是 0.5 倍缩放（第二次同一错误）

实测（Edge headless，`--window-size=1366,768`，视口 1336×673）：

```
body zoom          : 1
.hstage transform  : matrix(0.502778, 0, 0, 0.502778, -1280, -540)
hstage 内最小字号   : 9.5（CSS px，未含 transform）
横向溢出            : scrollWidth 1336 = clientWidth 1336
```

`zoom=1` 与"最小字号 10 px"都是**不含 transform 的量**。整站缩放在 `.hstage` 的 `transform: scale()` 上（`runtime.js::stageBox`，逻辑高恒 1080）。真实观感是 **0.50 倍**。

这条已经连着两轮被记成"已修"。**结论：F-10 仍开着；任何关于字号的结论都必须写成 `CSS px × scale`。** 赛前不动它（要改 `STAGE_H`，牵动全部版面，溢出是 `overflow:hidden` 静默裁切、测试不会红），但**不能写进"已修好"清单**——报告 1.1 的 #3 要划掉。
