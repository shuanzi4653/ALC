# 0.11.9 修复记录（2026-10-21）

> 触发：线上首页顶部横幅「气象图层读取失败，本帧已作废（推演继续）：activeCaseId is not defined」
> —— 实时首页的气象层整块失效，而构建、445 条前端判据、端到端验收当时全是绿的。

## 一、根因：两个「跨文件取变量 / 越界写函数」

### 1. `activeCaseId is not defined`（横幅那句话）

`TrafficWorkbench.vue:426` 的 weather 请求里写了：

```js
${activeCaseId ? `&case=${encodeURIComponent(activeCaseId)}` : ''}
```

而 `activeCaseId` **只在 `OperationsConsole.vue` 里声明过**。实时首页（URL 不带 `?case=`）
走到这一行必然抛 `ReferenceError` —— 请求根本没发出去，于是：

- 气象层整块为空（`weather.value = null`）
- 状态条写「低能见度不可用」，雷达/雾全部消失
- 顶部横幅写「本帧已作废」，**看起来像后端坏了**，实际后端一直是好的

`traffic/caseMode.js` 里本来就有 `caseQuery()` 这一个唯一来源（`&case=xxx` 或空串），
手写变量名等于绕开它。已改回 `caseQuery()`，并顺手给 `preflightRadar()` 的同一条请求补上
（案例模式下不该去中继实时瓦片）。

### 2. `paintFogCircles` 等三个函数被写到 `</script>` 之后

0.11.7 的补丁把 `FOG_RING_KM / fogRing / fogFeatureCollection / paintFogCircles`
追加到了 **`</script>`（原 1287 行）之后、`<template>` 之前**。那一段不属于模块：

- 函数不在作用域里 → 每次 `rebuild()` 调用都抛 `ReferenceError`
- 而且它被排在重画链**最后**，抛错连带跳过了 `map.triggerRepaint()`

Vite 照样打包成功，`dom` 也照常渲染 —— 只有运行时每次重画失败一次。

## 二、为什么 29 项闸门都没抓住

| 检查 | 为什么漏 |
|---|---|
| `vite build` | 只解析语法，不做未绑定名检查 |
| Vue 模板 | 未知名字退化成 `_ctx.x`（渲染成空，不抛错） |
| `_audit_unbound_names.py` | **Python AST**，射程之外（M23 记的就是这条） |
| 445 条前端判据 | 全都是「读源码字符串」与「纯函数单测」，没有一条会执行组件 |

**今天同一个形状出现了五次**：`verdictTone`（写了没接）、`scheduleRelayRetry`（同上）、
`setOperatorRole`（同上）、`paintFogCircles`（写了但不在模块里）、`activeCaseId`（借了别人的变量）。

## 三、补上的网：`js unbound names`（闸门第 29 项）

`tools/maintenance/js_unbound_scan.mjs` + `_audit_js_unbound.py`：

- 用 `@babel/parser` 解析每个 `.js` / `.vue` 的 `<script>` 块
- 一遍遍历收集「文件里声明过的名字」与「引用位置的名字」，未声明的报 `UNBOUND`
- 另查 **`</script>` 与 `<template>` 之间是否还有可执行代码**（`STRAY`）——这正是第 2 个 bug 的根因
- 三出口：**0 干净 / 1 有发现 / 2 无法测量**（找不到 node 或 parser 时不许报"通过"）

**负向自检 4 条**（`--self-test`）：正常 `.js` 通过、未绑定名被抓、正常 `.vue` 通过、越界块被抓。
接进闸门那一刻它就抓出了线上这个 bug（`activeCaseId`）和两个 `paintFogCircles` 调用点。

边界写在代码里：**只查"这个名字在本文件有没有声明"**，不做作用域解析 ——
于是它只会漏（作用域外引用），不会误报。会误报的闸门两天内就会被加白名单。

## 五、两件我先判错、后来自己纠正的

**① 我把"看不见"判成了"图层没建起来"。**
我以为是 `line-dasharray` 塞了 `['case',['get',…]]` 导致 `addLayer` 抛错，
还把三处（雷达描边 / 气象风险区描边 / 运行事件线）都拆了层。
查 MapLibre 26 的规格表后发现：`line-dasharray` 的 `property-type` 是
**`cross-faded-data-driven`** —— 数据驱动是**允许**的，不会抛。
真正原因是**对比度**（见上表）。拆层本身不亏（每层只描述一件事），但注释已改成如实表述，
不再拿"会抛错"当理由。

**② `validateStyleMin` 查不出这件事。**
我把数据驱动的 `line-dasharray` 喂给它，它返回 **0 个错误** ——
"官方校验通过"并不能证明运行时不抛。这条记在 `fogRings.test.mjs` 里，免得下次又靠它下结论。

## 六、判据（可复算，不靠人眼）

`frontend/tests/fogRings.test.mjs` 10 条，其中：

- **对比度 ≥ 3:1**：用 WCAG 相对亮度算描边色 vs `#102536`；并把 `#4A5568` 作为负向样本，
  断言它不达标 —— 阈值选得没意义的话这条会红
- 圈的几何：24 外点 + 闭合、`[lon,lat]` 顺序、6 km 南北直径 ≈ 0.1078°、高纬度经度跨度更大
- 缺席：缺坐标的站不画、`CLEAR` 的站不画、入参不是数组返回空集合
- 结构：`paintFogCircles` 必须在 `</script>` 之前、必须接进 `rebuild()` 的重画链
- 规格表事实：`line-dasharray` 是 data-driven（防止再有人用"会抛错"解释代码）

## 八、仍然只能由人确认的一件事

**雾圈的观感**。全域视图下 6 km / 12 km 的圈只有 7–13 px，那是**尺度**问题不是数据问题；
要看圈请：

1. 打开 `https://tianchuang.shuanzi.site/?case=fog-20250105`
2. 右上「运行区域」选 **省会 · 沈阳**（或点地图右下「定位雾区」再放大）
3. 沈阳处应有一个**浅灰实线圆**（6 km），哈尔滨/长春/大连各一个**灰色虚线圆**（12 km）
4. 状态条应写「实测 4 站 · 最低 998 m」，鼠标悬停可看到四站逐项读数与
   「圈由机场实测按阈值派生，是影响范围示意，不是格点雾区面」

若仍看不到，按这个顺序查：`showFog` 开关 → `stationVisibility` 是否有 `lat/lon`
→ `fog-rings` source 是否建立（`map.getSource('fog-rings')`）。
